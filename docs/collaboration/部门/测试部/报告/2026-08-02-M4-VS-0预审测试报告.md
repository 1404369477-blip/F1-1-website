## 4. P0：数据 bridge 已 accepted，但 app 仍停在旧 33 列门禁

### 4.1 事实

当前 Spec 已把 `ADR-M4-VS0-SEED-002` 和 `e7a...` 作为 VS-0 M3→Source 投影入口（`docs/spec.md:8-12,80-87,206`）。bridge 的当前机器产物已经能在只读内存渲染中得到 59 行、39 字段、59/59 `enabled=false`。

app 没有消费该 bridge：

- `app/src/server/providers/fixture.ts:154-170` 明确返回 `fixtureContract="m3-shadow-33-column"`、`dataGate="blocked-by-data"`、`fieldCount=33`，读取路径仍指向 `data/m3-base-shadow-import-v0/main-source-record-batch.json`。
- `app/src/server/db/seed.ts:18-21,54-67` 只向 `fixture_seed_ledger` 写 33/59/59 的 gate 记录，没有 `Source` 表或 39 字段插入。
- `app/migrations/0001_local_foundation.sql:1-20` 只创建 `migration_ledger` 和 `fixture_seed_ledger`，注释仍要求等待 data-team revision，未创建 Source domain seed migration。
- `app/scripts/seed-fixtures.ts:16-18` 在 gate 为 `blocked-by-data` 时明确设 `process.exitCode=2`；`app/package.json:24` 的 `check` 在 seed 后才会继续 test/lint/typecheck/build，因此不会假装全链路 PASS。
- 现有测试 `app/src/tests/vs0.test.ts:84-95,173-186` 反过来断言 33 列和 blocked gate，并断言没有 `source_config_fixture` 表；这些断言证明旧阻断实现可重复，不能证明当前 accepted bridge 已集成。

## 5. P1：代码缺陷、可测试性和证据闭环

### P1-01：migration ledger 缺失或 user_version 超前时 fail-open（代码缺陷）

`app/src/server/db/database.ts:127-140` 只有在 `migration_ledger` 表存在时才比较 checksum；当表不存在时会跳过校验。代码也没有拒绝 `PRAGMA user_version` 高于本地 migration 最大版本的数据库。

独立临时 DB 探针（Node 24，exit 0）得到：

```text
正常第一次：applied=[0001_local_foundation.sql], userVersion=1
正常第二次：applied=[], userVersion=1
删除 migration_ledger 后再次 migrate：accepted, applied=[], userVersion=1
手动 PRAGMA user_version=2 后再次 migrate：accepted, applied=[], userVersion=2，ledger 仍只有 0001
```

这两个损坏/篡改状态应拒绝并产生非零退出，当前实现允许继续。建议改为 ledger 缺失、记录缺失、hash 不匹配、版本超前均 `MIGRATION_DRIFT`/`MIGRATION_ORDER` fail closed，并补测试。

### P1-02：bridge validator 没有测试专用安全输出入口

当前 `seed-enrichment-validator.py:519-541` 的 `run()` 固定调用 `atomic_write()` 写入 bridge 目录的 `source-seed-enriched.json` 和 `manifest.json`；CLI 只保留 `--repeat` 和 `--require-product-decision`，没有临时输出根参数。早期版本的 `--root <temp>` 入口已不再存在（当前调用得到 argparse exit 2）。

因此本任务没有直接运行会覆写共享 bridge 的 CLI，而是 import 模块、调用无写入的 `render_once()` 两次，并单独调用 `verify_manifest_artifacts()`。后续应给 validator 增加显式临时输出/只读模式，避免测试只能依赖内部函数。

### P1-03：Vitest 通过的是旧 gate 契约，无法捕获 bridge 接入回归

当前 `npm run test -- --reporter=dot` 为 **16/16 PASS**，覆盖了环境拒绝、fixture 路径、日志脱敏、health DTO、WAL/FULL、迁移一次重复、rollback 和旧 gate 幂等。测试没有覆盖：

- 当前 v0.3 bridge 文件的 39 字段投影和 `e7a...` hash；
- 59 个 Source 行插入、Source required/enum/唯一性和 `enabled=false`；
- bridge 后 seed 的无半写、重复重放和旧 artifact hash 拒绝；
- dual connection lock、checkpoint/reopen、SIGKILL recovery、sidecar 清理；
- migration ledger 缺失/user_version 超前的 fail-closed 路径。

16/16 只能说明旧 33 列 partial 逻辑内部一致。

### P1-04：bridge 与任务/报告状态没有同步

- 当前 bridge manifest/mapping 已是 v0.3/ADR-002/e7a…（稳定 SHA 见第 3 节）。
- `TASK-20260802-6DAEAE.json` 仍为 `execution_state=claimed`、revision 2、`updated_at=10:02`、`report=""`，其数据部报告仍写 v0.2/ADR-001 的旧说明。

这会让开发、数据和测试使用不同的 last-known-good 事实。完成 bridge task 的报告、任务 JSON、开发 task 的 unblock/remaining implementation scope 后，才能重新建立可追踪门禁。

### P1-05：现成安装树有 extraneous 目录，clean-install/build 本任务未复验

`npm ls --depth=0 --json` 在现成 `app/node_modules` 上 exit 0，但 `problems` 列出 15 个 extraneous 空目录（例如 `array.prototype 2.flat`、`react 2`、`available-typed-arrays 2` 等）。本任务禁止清理共享依赖，也禁止 `npm ci`；因此不能把这棵现成树当作干净安装的等价物。
