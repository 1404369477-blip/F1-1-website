# TASK-20260803-FB0D41：v0.4 公开数据机器合同与 12 条发布图独立测试报告

## 1. 唯一结论

`decision=FAIL`。

本轮严格只读审核 accepted `ADR-M4-PUBLIC-READ-001`、`data/mvp-contract-v0.4-public-synthetic/` 八项机器产物和数据部 final 报告。双轮隔离生成、每轮两次 validator、8 项字节 SHA、12 套完整发布图、schema、DTO 映射、v0.3/M3 零漂移与 12 类临时故障注入均取得通过收据。

发现 1 个 P1：生成器把 `app/src/features/stories/demo-data.ts` 的精确 SHA 设为再生成前置条件，却没有解析该文件；实际公开内容来自生成器内另一份硬编码 `STORIES`。前端按 accepted ADR 切到 API 后，保留该文件会留下第二份可维护内容副本，删除或任何编辑又会使生成器拒绝再生成。该问题直接影响机器合同的持续可复现性与单一真值边界。任务规定只有 `P0=0 且 P1=0` 才能 PASS，因此本轮不能放行给后续 SQLite/API 开发。

## 2. 审核范围与独立方法

### 2.1 审核输入

- accepted 系统合同：`docs/decisions/system/2026-08-03-F1+1-公开读模型与API接线-v0.4-successor-accepted.md`；

- 前端转移输入收据：`app/src/features/stories/demo-data.ts`。

### 2.2 独立执行方式

1. 创建两个彼此独立的临时项目根目录，只复制 v0.3、M3 seed、v0.4 包和当前 `demo-data.ts`；
2. 每个临时根目录各运行一次生成器、连续运行两次 validator；
3. 对每轮生成后的 8 个 `.json/.py` 文件逐字节计算 SHA-256，并比较两轮与正式目录；
4. 使用独立只读结构检查器核对 schema 的 required/enum/additionalProperties、13 个继承领域定义、实体计数、public ID 和 DTO 字段集合；
5. 每个故障场景重新复制一份干净临时项目，修改故障目标后重绑非目标 artifact/manifest/ledger hash，避免只依靠最外层文件 SHA 形成“假拒绝”；
6. 单独审查生成器对前端文件的读取路径，并在临时副本中只给该文件追加一个换行，验证 API 切换/清理后的再生成行为；
7. 运行结束后检查正式 data 范围没有 `__pycache__` 或 `.pyc`。

所有 Python 执行均设置 `PYTHONDONTWRITEBYTECODE=1`；没有联网、安装依赖、读取 Base、调用 provider、访问真实平台、生成真实媒体、运行 AI 或发布动作。

## 5. DTO 字段唯一来源/派生

`public-dto-mapping.json` 的 feed 字段键集合精确为 17 项，detail 扩展精确为 3 项，JSON 对象不存在重复键。独立核对 accepted DTO 后，来源闭合如下：

- `publicId`：Publication 与 Projection 等值绑定；
- `contentType`：唯一来自 Content.editorial_category；
- `titleZh/summaryZh/leadZh/bodyZh/keyPointsZh`：唯一来自 approved Summary 对应字段；
- `publishedAt`：Publication.published_at；
- 来源发布时间与时间状态：approved Bundle.time_snapshot；
- source ID/platform/displayName/byline：approved Bundle.source_snapshot；
- state/source.accessStatus：只由 access snapshot 和 media presentation 按 accepted 优先级派生；
- media：只由 media presentation 与被 Bundle 选中的 MediaCandidate allowlist 构造；
- originalLink：本 synthetic 子集固定 disabled/null，reason 只来自 access snapshot 的封闭原因码；
- related、排序和 page size：同一批已验证候选、固定 DESC 顺序和 12 条页大小。

映射同时列出 canonical/external/evidence URL、hash/fence、reviewer/reason、profile ledger、raw payload 等 never-public 字段。删除 `source.byline` 并重绑 mapping artifact/manifest/ledger hash 后，validator 仍以 `DTO feed field mapping incomplete` 拒绝，证明字段完整性不是只由最外层 artifact SHA 阻挡。

## 8. P1/P2

### P1-01：生成器依赖待退役前端静态文件，但实际不从它生成内容（FAIL）

生成器当前同时存在以下事实：

1. `UI_INPUT` 固定指向 `app/src/features/stories/demo-data.ts`，并要求 SHA 精确为 `e6a8fb65374ec71722f8cf0c3234dfdef4ea8df691991d3f6615fdbf6de9881b`；
2. 对该文件的唯一运行时操作是 `sha256_file(UI_INPUT)`，没有 read/parse/AST/字段抽取；
3. 12 条标题、正文、状态、时间和媒体描述另行完整硬编码在 `generate_public_fixture.py` 的 `STORIES`；生成循环只遍历该列表；
4. manifest 把前端文件描述为 UI transfer input，容易让后续实现者误认为生成器会从该文件派生数据；
5. 临时副本只给 `demo-data.ts` 追加一个换行，生成器即 exit 1：`UI demo input drifted; review and deliberately update the transfer before regenerating`。

accepted ADR 要求前端接线后页面不得导入 `DEMO_STORIES`，并禁止静态第二公开真值。按当前实现，后续有两条路径：

- 保留精确旧前端文件：再生成可继续，但同一 12 条内容长期同时存在于 `app` 静态文件和生成器 `STORIES`，形成维护双源与误用静态 fallback 的风险；
- 删除、重命名或清理旧前端文件：运行时单一数据源更清楚，但已交付生成器立即失去可再生成能力。

这不是已发生的运行时数据泄漏，也没有造成当前 8 项字节不确定；它会在下一阶段 API 切换/清理时实质阻断可复现生成或破坏单一维护来源，因此定为 P1。

建议由数据部在不触碰 v0.3/M3 的前提下建立一份 data 目录内的封闭、机器可读、冻结转移输入，让生成器实际解析该输入并派生 12 条图；移除对 `app/src/features/stories/demo-data.ts` 的持续运行前置与内嵌重复内容。旧前端 SHA 可作为一次性迁移证据保留在 manifest/report，但不再作为未来生成依赖。修订后需重跑双轮 8/新增 artifact SHA、全部故障注入与本测试任务后继复验。

### P2-01：未使用原生 Draft 2020-12 校验引擎

当前系统 Python 没有安装 `jsonschema`，本轮没有为审核新增依赖或联网安装。项目 validator 的本地解释器覆盖当前 schema 实际出现的全部验证关键字；另有独立结构检查和 missing-required/illegal-enum/additional-property 等反向注入，当前验收指定的 required/enum/additionalProperties 已得到机械证据。

仍未取得原生 Draft 2020-12 引擎对完整 schema 的规范兼容性收据，保留为 P2。若后续应用层采用 Zod/TypeScript 或正式 JSON Schema validator，应在 SQLite seed/API 合同测试中增加交叉验证；该 P2 不改变本轮由 P1 导致的 FAIL。
