# M4 A 轴 Spec / ADR / 数据 v0.2 跨合同定版复验报告

## 1. 唯一结论

`decision=fail`。

本轮复验确认了若干 v0.2 机械产物和发布链路证据；补充对抗复验发现这些机械结果不能覆盖当前文件之间的语义漂移。A 轴仍有跨合同 P0 未闭合项，暂不能将 Spec/ADR 标记为 A 轴合同定版 Go。已定位的 A 轴问题为：

1. 新信源入队的 `enabled` 条件形成循环门禁；`pending/needs_review` 查重状态仍可通过 validating guard，且 Source `onboarding_operation_id` 与激活 TaskEnvelope 的 `operation_id` 不一致，三门与唯一激活操作合同均未闭合（P0-01）。
2. `reconcile_wait` 的重试/失败出边不完整；同一 Bundle 在主发布与对账 fixture 中出现两个 Publication/public_id，Publication、reconcile 与 outbox job 使用了不同幂等键，重试不能证明保持唯一公开身份（P0-02、P0-08）。
3. `runtime-envelope.schema.json` 的 lease 正则允许仅 3 个字符后缀，无法表达合同要求的 live ≥128-bit CSPRNG opaque lease；当前 schema 没有把 synthetic fixture 与 live envelope 分开（P0-03）。
4. M4 ADR 的 `SourceObservation`、`SummaryDraft`、`AuditEvent` 未在 v0.2 schema 或 `base-mapping` 的领域实体清单中定义；同时 R10/ADR 承诺的 hash 覆盖范围超过 generator 实际输入，物理映射、唯一身份与 hash 合同均有第二落点或范围漂移（P0-04、P0-09）。
5. Spec/ADR 声明五层 seed，`seed-layers.json` 和 manifest 只有三层，`published-projection-seed` 与 `snapshot-failure-seed` 没有独立层级的 manifest/hash/count 证据（P0-05；同时影响 P0-08 的层级声明）。
6. Spec/ADR 要求所有信源 onboarding 状态有 fixture/API/UI 可达路径；当前 v0.2 主 fixture 只提供 6 种 Source 状态，另外 11 种声明状态没有 Source fixture，`paused` 还缺少 `collection_onboarding_status` enum；blocked/queue/collection/publication/outbox 的恢复出边也不完整（P0-07）。API/UI 尚未初始化属于 B/C 未验证，不作为 A 轴阻断依据。
7. 数据任务已完成并 ACK，但 progress/ADR 仍称 v0.2 并行未核收；runtime schema minimum=1，文档对 epoch=0 的 expected-reject 例外没有对应 invalid fixture 或 validator 证据（P1）。

P0-06 的 Node 24、package/lockfile、`app/` 和运行时收据缺失被保留为 B/C 门禁，不计入 A 轴失败。当前 `app/` 只有 README、现场 Node 为 `v25.5.0`，这些事实仅说明 C 轴尚未开始验收。

### P0-01 详细定位：入队前 `enabled=true` 的循环条件

当前产品合同在两处给出了顺序：

- `docs/spec.md:37`：三门通过后创建唯一入队激活操作，“队列确认后启用并开始采集”。
- `docs/spec.md:38`：新信源初始 `enabled=false`；三门通过后进入 `queued → collecting`。

机器状态机却把 `enabled=true` 写进 `activation_pending → queued` 的 guard（`state-machine.json:74-76`）。在初始 `enabled=false` 且没有中间 `enable` 转换的条件下，三门通过仍无法入队；已有 `active` fixture 的 `enabled=true` 只能证明已完成状态，不能证明新信源路径。

最小修订方向是二选一并同步 Spec、ADR、state machine、fixture：

- 保持“队列确认后启用”：从入队 guard 移除 `enabled=true`，在队列确认/collecting 前定义原子启用转换和 CAS；或
- 保持“入队前启用”：改写 Spec 的时序和初始状态，显式定义启用操作及其审计/失败状态。

在未选定单一时序前，P0-01 不能关闭。

### P0-01 追加：查重门与 activation operation 不一致

`state-machine.json:39-42` 的 validating guard 只写 `dedup_status != linked_existing`，没有排除 `pending` 或 `needs_review`。这与 Spec `:37-38,62` 所说的规范化、查重完成后才入队不相容；`fixtures.synthetic.json:20-45,61-86` 仍以 `dedup_status=pending` 作为 active/ready 样例，无法作为已完成查重的入队证据。另，`src-ready-001` 在 `fixtures.synthetic.json:43` 使用 `onboarding_operation_id=op-src-ready-001`，其 source activation TaskEnvelope 在 `:955-978` 使用 `operation_id=op-synth-001` 和同名 job key。`state-machine.json:381-388` 明确要求重试复用同一 operation 且不得创建第二 activation job；当前样例没有证明这一不变量。

### P0-02 / P0-08 追加：对账身份和幂等键分裂

`fixtures.synthetic.json:825-837` 的 `publication-synth-001` 与 `:921-934` 的 `publication-synth-reconcile` 共享 `release_bundle_id=bundle-synth-001`、content/summary 与相同 approved bundle hash，却分别使用 `public-synth-001`、`public-synth-reconcile` 两个公开身份和两套 Publication/reconcile key。`state-machine.json:407-413`、Spec `:66`、ADR `:263-265` 要求同一 approved bundle/reconcile retry 保留同一 `public_id`。

job-synth-003（`fixtures.synthetic.json:1031-1054`）的 envelope/job key 是 `publish:publication-synth-001`，job-synth-005（`:1107-1130`）是 `publish:publication-synth-reconcile`；对应 Publication 的 key 还包含 `:bundle:<approved_hash>`（`:836,932`），因此跨 Publication、TaskEnvelope、OutboxJob 的幂等键没有统一。状态机虽然列出 `reconcile_wait` 的确认成功、未提交、终态失败、急停方向（`state-machine.json:278-310`），但 `publication.retryable_failed` 没有出边，`outbox_job.retryable_failed` 也没有重试/恢复出边（`:314-377`）。这同时使 P0-02 的可重试合同和 P0-08 的稳定公开身份子条件失败。

### P0-03 追加：live lease 与 synthetic fixture 未分层

`runtime-envelope.schema.json:62-64` 允许 `synthetic:lease-` 后仅 3 个字符，现有 `synthetic:lease-001` 等值也满足该模式；Spec `:107,123` 与 ADR `:276,314` 对 live envelope 要求至少 128-bit CSPRNG opaque lease。当前 schema 没有 `fixture-only` 标记或单独 invalid/live schema 来排除短 synthetic 值，因此五 fence 的字段存在不能推出 live lease 门禁已实现。epoch、deadline、attempt 的静态样例仍保留为已验证范围。

### P0-04 详细定位：三类未定义对象是否属于领域

这是本轮新增的统筹部疑点，结论为 **确实构成 P0-04 未闭合项**。原因有两层：

1. ADR §4.6 的表格直接把三张物理表的“领域实体”写成 `SourceObservation`、`SummaryDraft`、`AuditEvent`，并在 §4.1、§4.5 继续以对象名引用；这些名字不是当前 v0.2 schema 的 `$defs`，也不在 `base-mapping.json` 的领域实体列表中。
2. 如果三者只是运行时/运营记录，当前文字仍未声明它们为非领域实体、不得形成第二真值，也没有说明它们如何仅以既有 Source/Content/Summary/ReviewDecision/OutboxJob 引用承载。`audit_event` 虽然被描述为脱敏审计，仍缺独立审计结构或边界合同。

最小修订方向：将三者明确标为内部运营/审计表，写出读写 owner、允许的既有领域 ID 引用、不得成为领域状态/真值的规则，并在内部合同中给出最小字段校验；或者把它们正式加入新的数据合同版本并补齐 schema、manifest、mapping、fixture 和迁移。保持 ADR、Spec、数据 schema 三处单一选择。

### P0-04 / P0-09 追加：hash 承诺覆盖范围超过生成器输入

ADR `:261,265`、Spec `:102-106` 与 R10 `:315` 文字承诺 canonical payload 覆盖内容、摘要、source provenance/original_url、rights、media、policy、版本、schema、五 fence 与 `release_bundle_id`。`data/mvp-contract-v0/generate_contract.py:715-727` 实际只将 content/summary ID 与 version hash、`source_evidence_url`、空 `media_refs`、canonical rule 和五 epoch 放入 Bundle payload；`:690,705` 的 content/summary version hash 仅计算 `id + version`，正文、标题及权利/政策/schema 快照没有进入输入。当前生成器重算结果与现有 artifact 相等，证明内部确定性；它没有证明文档承诺的字段覆盖已经兑现。因此 P0-09 的 R10 实现覆盖失败，并与 P0-04 的唯一领域/hash 落点问题共同阻断 A 轴定版。

### P0-05 详细定位：五层声明与三层 manifest 不相等

主 fixture 中确实存在 3 个 published projection、独立 `snapshot_reconciliation` 对象和 13 个 case；这能证明样例存在，不能替代 ADR/Spec 要求的两层独立 seed manifest。当前 `seed-layers.json` 的 `isolated_from` 只在三层之间声明隔离，manifest 的 `seed_layers` 也只有三项。实现方无法从现有清单机械确认公开投影和 snapshot failure 的来源、计数、hash 和互斥边界。

### P0-07 详细定位：状态机可达不等于 schema/fixture 可执行

本轮独立 BFS 检查确认 6 组 state machine 的所有声明状态均从 initial 状态可达；这项结果只覆盖转换图。`paused` 在转换图中可达，却不在 `Source.collection_onboarding_status` enum 中，schema 无法承载该状态。按 Spec/ADR 的验收合同，状态还需在 fixture/API/UI 有观察路径；当前 Source fixture 另缺 10 个非 `paused` 状态。API/UI 仍属于 B/C，报告不以 app 尚未初始化作为 A 轴失败理由。

此外，状态机的恢复出口本身没有闭合：source 的 `blocked_adapter_missing`、`blocked_authorization`、`blocked_platform`、`queue_failed`、`stopped`、`cancelled`、`dead_letter` 等状态在 `state-machine.json:59-127` 没有后续恢复/重试出边；publication 的 `retryable_failed`（`:268-285`）与 outbox 的 `retryable_failed`（`:339-342`）也没有对应出边。Spec `:45` 与 ADR `:242-253` 要求失败可观察、可重试或人工恢复，当前转换图只覆盖失败进入，未覆盖恢复出口，属于 A 轴状态合同缺口。
