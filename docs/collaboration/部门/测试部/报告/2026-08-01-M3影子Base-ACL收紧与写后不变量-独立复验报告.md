# M3 影子 Base ACL 收紧与写后不变量独立复验

## 审核范围与边界

- 任务：`TASK-20260801-508D03`，已从测试部收件箱领取。
- 审核对象：`F1+1 信源库｜M3影子` 的六项公共权限、`manage_public`、资源目录、表单边界、主表 59×33 导入不变量、手机捕获 0 条和业务切换边界。
- 证据指针：统筹部 M3 影子 Base 执行收据、安全部最小 ACL 方案审核报告、`data/m3-base-shadow-import-v0/main-source-record-batch.json` 及相关字段/manifest。
- 执行边界：测试部只读复验；没有使用浏览器，没有执行 `permission.public patch`、协作者修改、OAuth 重授权或任何飞书写入；没有输出或持久化 Base token、open_id、appId 或认证原始 JSON。
- 当前能力限制：本地非提权 `lark-cli auth status --json --verify` 返回 `keychain Get failed: keychain not initialized`。没有请求或执行提权命令，也没有切换 bot。依据任务失败路径，审计统筹部已提交的用户 CLI fresh-read 收据，并将“测试部独立现场重读”单独标为未验证。

## 结论

`decision=pass`（公共 ACL 与写后不变量范围）。

统筹部收据记录用户明确授权后的单次 typed `drive permission.public patch --as user --yes`，写后立即 fresh read；六项公共权限和 `manage_public=true` 均命中目标，且没有重试、回滚或越界写入。收据同时记录资源、表单、59×33 数据、手机捕获表和业务链路不变量保持。该 PASS 建立在带来源的 fresh-read 收据上，不等同于测试部在当前受限环境完成了第二次现场读取。

直接协作者清单在当前授权下不可读，相关身份、数量、外部协作者和继承权限继续为 `Unknown`。本结论不扩写为“仅 owner/个人维护者可访问”。OAuth 用户令牌仍有 142 个 scopes，继续作为独立 P1 预防性授权风险，不影响本次六项公共权限的目标值判定。

## 已验证

### 1. 六项 public permission 与 manage_public

统筹部 fresh-read 收据记录的写后值如下，顺序与任务验收出口一致：

| 设置 | fresh read 值 | 结果 |
|---|---|---|
| `link_share_entity` | `closed` | 通过 |
| `external_access` | `false` | 通过 |
| `invite_external` | `false` | 通过 |
| `share_entity` | `only_full_access` | 通过 |
| `security_entity` | `only_full_access` | 通过 |
| `comment_entity` | `anyone_can_edit` | 通过 |
| `manage_public` | `true` | 通过 |

本机 CLI schema 的只读检查确认六字段及目标枚举仍可表达：`link_share_entity` 支持 `closed`，`share_entity` 与 `security_entity` 支持 `only_full_access`，`comment_entity` 支持 `anyone_can_edit`，两个外部开关为布尔值。未把 schema 或 dry-run 误写成实际 ACL 变更。

### 2. 资源目录与视图不变量

统筹部 fresh read 收据记录以下资源目录保持不变：

- 1 个目标 Base；
- 2 张业务表：主信源 33 字段、手机捕获 9 字段；
- 3 个长期视图，全部 `type=grid`：`M3｜影子59对账`、`维护｜门禁待复核`、`手机捕获｜待处理`；
- 1 个手机表单：`新增信源（手机）`。

三张 grid 的名称、类型、筛选器和 visible field 顺序与 M3 产品合同逐项一致。收据对以下合同差异作了明确说明：手机捕获视图的两个 `empty` 条件由平台序列化为带尾部 `null` 的三元组，按 CLI 官方可选值规则去除尾部 `null` 后，语义和顺序与合同一致。

### 3. 表单与手机捕获表不变量

- 表单 `shared=false`，`submit_limit_once=false`。
- 问题集合顺序严格为两项：
  1. `raw_url`，描述为“粘贴 X 账号页或帖子分享链接”，`visible=true`、`required=true`；
  2. `capture_note`，描述为“可选：简要说明为何希望加入”，`visible=true`、`required=false`。

- `capture_id` 和 `captured_at` 不在问题集合；手机捕获底层字段仍完整保留 9 个字段。
- 手机捕获表全表记录数为 `0`，`has_more=false`；统筹执行边界还记录未执行真实表单提交或自动入表，因此当前收据支持“无真实表单提交”的不变量。

### 5. 无业务切换与本地配置边界

- 统筹收据记录没有把 Base 设为业务真值，没有连接 `base_direct`、`base_snapshot`、Collector、采集、同步或发布链路，没有启用任何信源，没有创建 workflow，也没有改变人工审核门禁。
- 当前工作区 `app/` 只有占位 `README.md`，没有运行时代码或相关运行时配置；非文档区域未发现 `active_source_config_provider`、`source_config_epoch`、`base_direct`、`base_snapshot`、Collector、采集器、同步器或发布器实现。
- 上述结论覆盖本地工作区及统筹收据所述执行范围；不推断仓库外独立部署环境的状态。

### 6. OAuth 风险独立披露

- 统筹收据记录当前用户 OAuth scope 总数为 `142`，Base 相关能力包含广泛的 create/read/update/delete 范围。
- 本轮没有利用额外 scope 执行业务动作；ACL 收紧不等于 OAuth 权限最小化。
- 重新授权、缩减 scope、撤销旧 token 或保留窗口均需用户另行确认，不能由本测试任务自动执行。
