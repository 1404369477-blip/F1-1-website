## 3. P1-01：delivery receipt 对账——CLOSED

已确认：

- `ENDPOINTS.delivery(deliveryId)` 精确构造 `/api/admin/deliveries/{encoded-id}`；
- `checkDelivery` 的 deliveryId 只能来自当前 `state.detail.delivery.id`，并要求 `op-snapshot-<64 hex>`；
- `RealAdminAdapter.checkDelivery(candidateId, deliveryId)` 先 GET delivery endpoint，再回读同一个 candidate detail；
- receipt 必须为 `admin-public-projection-receipt-v1`，且逐项校验请求/响应 deliveryId、snapshot/active generation、两个 manifest hash、`active|superseded`、`reasonCode=null` 与两个时间戳；
- active 要求 active generation/hash 与当前 receipt 精确一致；superseded 要求 active generation 不早于当前且指向另一非空 hash；
- receipt 与 private detail 分别存储和展示，没有把 receiver receipt 推断为 private DB 已回写；
- 404/409/503/401/网络失败只保留同一 delivery 的失败提示；该路径没有 `executeMutation`、`publishMutation` 或 `adapter.mutate` 调用。

结论：原 P1-01 关闭。

## 4. P1-02：401/409 后内存草稿恢复——CLOSED

已确认：

- 草稿只存放在页面状态的 `new Map()`，字段限定为 candidate/source/Bundle 绑定与 `titleZh/summaryZh/notes`；
- localStorage 仍只读写 `f1-admin-theme`，没有 sessionStorage、console、URL 或日志草稿出口；
- 用户输入变化时 `rememberDraft()` 保存内存草稿；401 后 passkey 登录执行真实 list/detail 回读，`renderActions()` 随后显示“重新套用草稿”和“明确丢弃草稿”；
- 409 的“加载最新状态”同样回读真实详情并复用该恢复出口；
- source revision、source versionTag 或 Bundle versionTag 变化时，只显示人工合并警告；`restoreDraft()` 只回填三个表单字段、标记 dirty，仍需用户手动保存新 revision；
- restore/login/refresh 路径没有 mutation 调用；成功 revision 或用户明确丢弃后才删除相应草稿。

结论：原 P1-02 关闭。

## 5. busy 重入 P2——CLOSED

已确认：

- `saveRevision`、`confirmAction`、`executeMutation` 三个 mutation 入口均先检查 `state.busy`；
- 确认提交同步禁用 dialog confirm/cancel，`setBusy` 同步禁用编辑控件和工作区动作；
- `executeMutation` 只使用调用者已生成的唯一 mutation/operationId，不在等待期间再生成；
- success、401、409、503、网络失败及其他异常都经 `finally` 恢复 busy 与控件；
- delivery 查询有独立 busy 闸和 finally，且不进入 mutation。

结论：原 busy P2 关闭。
