# 0C206C 正式 Admin UI 独立接口与安全静态验收报告

## 1. 结论

**FAIL；P0=0，P1=2，P2=2。**

正式 Admin UI 的三份输入和证据 manifest 均命中任务冻结 SHA。审核队列、编辑、批准、拒绝、批准后第二次手动发布、operation 对账、passkey 登录/注册/fresh re-auth、fixture 警告、XSS 基础防护和 1440/390 响应式证据大部分成立。

当前候选仍有两项会影响真实运营闭环的 P1：

1. “检查同一投递结果”没有调用 B2CB5F 已冻结的 delivery receipt 端点，无法取得 `active/superseded` 公开投影收据；
2. mutation 遇 `401` 后重新登录会直接重载详情，覆盖尚未保存的中文标题、摘要和私有备注。

因此，当前静态 UI **不放行与 `127.0.0.1:3101` 正式服务集成**。完成下述最小 successor 后，再做一次绑定新 JS SHA 的聚焦静态复验即可；无需重跑全套浏览器截图，视觉结构未发生变化时可沿用现有四图作为历史视觉证据。

## 4. 已验证项

### 4.1 独立静态入口与公开路由边界

- 正式 UI 位于 `app/src/admin-ui/`，资产路径精确为 `/admin/assets/app.css` 和 `/admin/assets/app.js`；B2CB5F 服务端静态映射一致。
- `app/src/app` 中没有 `/admin/reviews` 页面，也没有本轮 review/passkey 静态 UI 接线；仓库存在的 source-management Admin API 属于既有独立切片，本轮没有把 0C206C UI 编进公开 Next 页面。
- 0C206C 的三份正式文件不包含外部 script/style/font URL；HTML CSP 将 script/style/connect 限制在同源。

### 4.2 Passkey、session、CSRF 与手动发布顺序

六个 passkey endpoint 均与 B2CB5F 一致：

- bootstrap options / verify；
- login options / verify；
- fresh options / verify。

静态调用链证明：

1. `publishMutation()` 先生成一份完整 `PublishRequest`；
2. fresh options 与 fresh verify 均发送同一对象；
3. fresh verify 成功响应由浏览器接收旋转后的 `Secure/HttpOnly` session cookie；
4. 随后用同一 mutation 申请一次性 CSRF；
5. publish 同时提交 `x-csrf-token` 与 `x-f1-fresh-reauth`。

批准、拒绝和发布为三个独立 mutation。批准成功只进入 `approved_waiting_publish`，页面随后才显示“手动发布当前批准版本”；没有 approve 自动调用 publish 的代码路径。

### 4.3 Review DTO 与状态

- revision 使用 `detail.integrity.versionTag` 构造 12 位 `sourceVersionTag`；客户端没有读取、显示或发送完整 64 位 `sourcePayloadHash`。
- approve/reject 绑定 `candidateId/sourceRevision/bundleId/bundleVersionTag`；reject 原因在客户端做非空和 500 字上限约束。
- publish 包含 `publicId/publishGeneration=1/publicationStatus=queued/approvedBundleVersionTag`；现行服务 schema 同样把 `publishGeneration` 冻结为 literal `1`。
- loading、empty、详情加载失败、`source_updated`、`reconcile_wait`、terminal、emergency stopped、blocked 均有静态文案和 fail-closed 动作集合。
- `401` 会进入 passkey 登录出口；`409` 显示加载最新状态；`503` 当下不改输入值且不自动重试；网络结果未知时保留同一 operationId 并只提供 operation 对账。

### 4.4 XSS、链接、浏览器存储与 fixture

- 未发现 `innerHTML`、`outerHTML`、`insertAdjacentHTML`、`document.write`、`eval` 或 `new Function`；服务数据均通过 `textContent`、表单 `.value` 或固定 class 写入 DOM。
- 原文链接只接受 `https:`、精确 `www.motorsport.com`、无用户名/密码/hash，并固定 `target=_blank`、`rel="noopener noreferrer"`；`javascript:`/跨 host 无法写入 href。
- localStorage 只保存 `dark|light` 主题；bootstrap token、session、fresh receipt、CSRF、私有备注和正文没有进入 localStorage/sessionStorage/console。
- 未发现 console 日志。
- `FixtureAdminAdapter` 只有 URL 显式 `fixture=review-ui-v1` 且来源为 `file:` 或 loopback host 时启用；无参数时固定 `RealAdminAdapter`。fixture 模式持续显示页头 badge 和底部“当前页面没有连接真实 API”警告。

### 4.5 既有视觉与响应式证据

- 既有四图覆盖 `1440×900`、`390×844`，深浅主题各一张；PNG 像素、viewport、theme、fixture state 与 manifest 一致。
- 四图收据均为 `scrollWidth=clientWidth`，未观察到页面级横向溢出；可见交互目标最小高度为 `44px`。
- CSS 为 button/input/textarea 提供 44px 下限、3px focus-visible、390 单列切换、safe-area 底部间距、reduced-motion、reduced-transparency 与 forced-colors 规则。
- HTML 含 skip link、主要 section/aside label、aria-live status、dialog label/description、显式 form label；Mac 双栏与 iPhone 单列使用相同 adapter、mutation 和动作语义。

## 5. Findings

### P0

无。

### P1-01：delivery 对账用户出口没有接入冻结服务端点

证据：

- UI 的 `ENDPOINTS` 没有 `/api/admin/deliveries/{deliveryId}`；
- `RealAdminAdapter.checkDelivery(candidateId)` 直接调用 `detail(candidateId)`；
- 动作按钮却标记为“检查同一投递结果”；
- B2CB5F 服务已经冻结 `GET /api/admin/deliveries/{deliveryId}`，返回 `admin-public-projection-receipt-v1`，其中含 `deliveryId/status=active|superseded/activeSnapshotGeneration/activeSnapshotManifestHash`。

影响：UI 只能看到 private candidate detail 内的 delivery 摘要，无法读取 receiver 的真实 active receipt。若 receiver 已激活而私有 detail 仍停留在 pending/leased，运营者会持续看到“尚未确认”，也无法区分当前 delivery 已 active 或已被后继 snapshot supersede。该缺口破坏 `ADMIN-RECOVER-008` 的同一 delivery 对账出口，但不会触发第二次 publish。

最小修正：

1. 增加 `ENDPOINTS.delivery(deliveryId)`；
2. `checkDelivery` 必须从当前 detail 取得非空 `delivery.id`，GET 精确 delivery endpoint；
3. 严格校验 `schemaVersion=admin-public-projection-receipt-v1`、返回 `deliveryId` 与请求一致、status 仅 `active|superseded`，并校验 generation/hash 字段基本形状；
4. `active` 明确显示已激活收据；`superseded` 明确显示已被后继快照替代；404/409/503/网络失败继续保留同一 delivery 查询，不创建新 publish；
5. 收据确认后可再回读同一 candidate detail，两个读取结果必须分开展示，不能把 receipt 推断成 DB 已回写。

### P1-02：401 重新登录会覆盖未保存编辑草稿

证据：

- revision/approve/reject/publish 任一请求收到 `401` 时，`handleError()` 直接调用 `showAuth()`；
- 当前表单值只存在 DOM input/textarea，没有另存一份受控内存 draft；
- 登录成功固定执行 `loadList()`，随后 `selectCandidate() → renderDetail()`；
- `renderDetail()` 用服务端 detail 重新赋值 title/summary/notes，并把 `state.dirty=false`。

影响：运营者编辑较长中文标题、摘要或私有备注后，如果 session 在保存时过期，passkey 重登录会静默覆盖未保存输入。页面已显示“会话已失效”，但没有“恢复草稿/明确丢弃”出口；该行为不满足失败后回到可继续操作位置的门禁。私有备注不会泄漏，但用户输入会丢失。

最小修正：

1. 在发起 mutation 前只用页面内存保存 `{candidateId, editable, sourceVersionTag, latestBundleVersionTag}`；禁止 localStorage、sessionStorage、URL 和日志；
2. 401 重登录完成后先回读当前 detail，再让用户选择“重新套用草稿”或“明确丢弃”；
3. 来源/Bundle 已变化时把草稿标为待人工合并，继续禁止自动 mutation 重放；
4. 关闭页面仍沿用 `beforeunload`，不得把私有备注持久化到浏览器存储。

### P2-01：mutation handler 缺少最终重入闸

`setBusy(true)` 会禁用工作区按钮，但 `confirmAction()` 和 `saveRevision()` 入口没有 `if (state.busy) return`，dialog confirm 也没有在提交同步边界显式禁用。普通指针操作因 dialog 立即关闭而较难重复；程序化 submit、辅助技术重复事件或极端事件队列仍可能生成第二个 operationId。服务端 CAS/唯一约束会阻止重复业务身份，故当前定为 P2。

最小修正：两个 handler 开头增加 busy 闸；确认提交时同步禁用 confirm/cancel；一次动作只生成一次 operationId，直到结果或对账出口建立前不创建第二个。

### P2-02：现有静态视觉证据不能替代 1024 与真实设备/服务验证

既有 manifest 覆盖 1440 和 390 的四张 fixture 截图，没有 1024；也没有真实 Mac/iPhone passkey 系统面板、软键盘、屏幕阅读器、200% 缩放、真实 401/409/503、真实 delivery receipt 或真实服务整合。任务明确禁止重跑浏览器，本轮保持 **Unknown / P2**，不把缺失运行证据写成当前 CSS 已发现缺陷。

## 6. 放行条件与聚焦复验

本轮不要求大范围返工。最小 successor 完成后，测试部只需一次只读聚焦复验：

1. 绑定新 `app.js` SHA，确认 HTML/CSS 未漂移；
2. 静态证明 delivery endpoint、receipt identity/status 校验、active/superseded/404/503 恢复链；
3. 静态证明 401 内存草稿恢复/显式丢弃，且 token/notes 仍不进浏览器存储或日志；
4. 静态证明 confirm/save 的 busy 重入闸；
5. 若 CSS/HTML/布局不变，无需重新生成四张视觉图；正式 3101 集成任务再对真实服务做一次运行冒烟。

P0=0 且 P1=0 后，才可放行 0C206C UI 与 B2CB5F `3101` 服务集成。
