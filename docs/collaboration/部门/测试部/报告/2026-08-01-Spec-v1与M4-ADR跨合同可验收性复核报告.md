# Spec v1 / M4 ADR 跨合同可验收性只读复核

## 1. 结论与边界

- `decision=fail`。
- **M4 正式实现 Go/No-Go：NO-GO。** 结论受合同 P0 缺口和 C 轴 Node 24/工程入口门禁共同影响；Node 24 不作为 A 轴合同定版或 B 轴最小脚手架前置。
- 本报告仅对定版前的合同一致性、可执行出口和当前环境证据负责，不放行实现、部署、真实外部调用、真实 Base/provider、Collector、真实采集、真实表单提交或自动发布。
- 本轮只读取任务 JSON、Spec、progress、M4 proposed ADR、设计 Token/map、MVP 数据合同、开发预检和既有测试矩阵；只运行本地静态检查与不绑定端口的 disposable probe。没有修改被审文件、`app/`、数据产物、设计产物或安全产物。
- `decision=fail` 的含义是“定版前跨合同尚未达到可安全开工的验收条件”，不等同于真实平台或 M3 Base 存在缺陷。

## 3. P0 阻断项

以下任一项未闭合，都不得把 Spec/ADR 定版为可实现合同，也不得进入正式 Build Loop。

### P0-01：信源适配器/授权门禁顺序与 Spec 冲突

**证据：**

- `docs/spec.md:37-38,133-135` 要求规范化、查重、可用适配器和合法授权均满足后才创建唯一入队操作；身份与相关性 `unknown` 不阻断，适配器/授权失败必须阻断并记录。
- `data/mvp-contract-v0/state-machine.json:28-40` 将 `activation_pending → queued` 的 guard 仅写为 outbox 已确认，把 `queued → collecting` 的 guard 仅写为 `enabled=true and stop_status=clear and epoch matches`，适配器和授权检查被放到 `collecting → active`（:38-40）；其中 `stop_status` 也没有与 schema 的 `source_stop_status` 对齐（schema `:329-337,414-415`）。
- 同一状态机虽声明 `blocked_adapter_missing`、`blocked_authorization`、`blocked_platform`（:6-19），实际只有 `activation_pending → blocked_authorization`（:53-56），没有适配器缺失或平台受限的进入路径。
- `data/mvp-contract-v0/fixtures.synthetic.json:7-35,47-75` 中 Source 的 `adapter_status` 均为 `unchecked`、授权均为 `unknown`；第三条 Source（:87-115）只有 `adapter_authorization_status=expired`，没有 `ready/missing/unavailable` 或授权有效的成功/缺失 fixture。
- Spec `:38` 要求队列确认后才置为已入队并启用；状态机 `:28-35` 没有定义 `enabled=false → true` 的转换或事务边界，当前三条 synthetic Source 也都保持 `enabled=false`（`fixtures.synthetic.json:31,71,111`）。

**风险：** 实现可在适配器/授权门禁完成前入队或开始采集，也可能在确认后无法按合同置 `enabled=true`；失败路径无法稳定落到 Spec 要求的阻断状态，存在未经授权访问或队列永远不工作的合同歧义。

**必改：** 在唯一状态机中明确 `activation_pending` 的全部入队谓词（adapter ready、authorization valid、platform allowed），补齐 adapter/platform/authorization 的阻断转换，统一 `source_stop_status` 字段；定义队列确认后 `enabled` 的同事务更新与回滚；明确 `queued → collecting` 是否允许再次检查以及任何 provider 调用前的 fail-closed 语义；为每条转换提供合成 case 和拒绝断言。

### P0-02：发布未知结果的状态名称和状态模型不一致

**证据：**

- `docs/spec.md:124` 和 ADR `:289-293` 要求发布超时进入 `publish_unknown`/查询分支，禁止直接产生第二个 `public_id`。
- 既有测试矩阵使用 `reconcile_wait`（矩阵 `:150,176,197,284`），没有使用 `publish_unknown`。
- `data/mvp-contract-v0/schema.json:1060-1069` 的 `Publication.publication_status` 只有 `queued/publishing/published/retryable_failed/terminal_failed/blocked`；`data/mvp-contract-v0/state-machine.json:183-218` 也没有 `publish_unknown` 或 `reconcile_wait` 转换。

**风险：** 同一个超时/提交未知结果有两套名称，领域 schema 不能承载验收矩阵要求的查询等待态，测试无法证明“同 key 对账后再重试”且可能错误生成第二个公开 ID。

**必改：** 产品、数据、开发、测试共同冻结一个 canonical 状态（包括是否为 `publish_unknown` 或 `reconcile_wait`），定义进入、查询、确认成功、确认未提交、终态失败和急停转换；把状态、错误码、查询凭据和幂等 key 写入唯一 schema 与 fixture。

### P0-03：版本围栏字段出现第二套命名和覆盖范围

**证据：**

- Spec/ADR/领域 schema 使用 `source_config_epoch`：Spec `:119,122`，ADR `:159,166,172-179,280-281`，schema `data/mvp-contract-v0/schema.json:339-345` 及 OutboxJob `:1210` 附近。
- 既有测试矩阵仍使用 `source_config_version`（`:49,129,141,158-162`），另列 `summary_draft_version`、`release_bundle_id`、`publish_generation`。
- 矩阵 `MockAdapter.poll` 签名（`:129-133`）只接收 `source_config_version`、`authorization_version`、cursor、lease 和 deadline；ADR provider 合同（`:170-179`）要求 `source_config_epoch`、`source_safety_epoch` 以及 `runtime_fence={authorization_version,policy_epoch,recovery_epoch}`，参数集合也没有一一对应。
- ADR `:162,166` 要求 `source_safety_epoch` 加上 `authorization_version`、`policy_epoch`、`recovery_epoch` 进入任务 envelope；领域状态机的 stale guard 只比较 `source_config_epoch`（`state-machine.json:316-319,248-252`），没有 canonical envelope schema 或这些版本的组合拒绝条件。

**风险：** 开发者可能实现两个字段或只校验配置 epoch，遗漏安全、授权、策略和恢复围栏，陈旧任务仍有机会写入当前结果；测试报告也无法对齐字段来源。

**必改：** 将矩阵中的 `source_config_version` 统一为 `source_config_epoch`，明确所有 runtime fence 的内部 envelope schema、比较时点、递增方和拒绝分支；保留领域 schema 与内部 envelope 的边界，给每个 fence 增加旧值回放 fixture。

### P0-04：Bundle、审核决定、hash 和 public identity 未与唯一数据合同对齐

**证据：**

- ADR `:146-160,283-293` 以 `release_bundle`、`review_decision`、`public_id`、Bundle Hash 为纵向切片对象。
- 既有测试矩阵 `:47,147-150,158-162` 断言 `release_bundle_id + payload_hash`、`ReviewDecision`、`publish_generation` 和稳定 `public_id`。
- `data/mvp-contract-v0/schema.json:778-855,1046-1159` 只有 `Summary`、`Review`、`Publication`；Review 只有 content/summary 两个批准 hash，Publication 只有 `publication_id`、版本 hash 和 `idempotency_key`。这三个对象没有 `ReleaseBundle`、`ReviewDecision`、`release_bundle_id`、`publish_generation` 或 `public_id`；`payload_hash` 目前只出现在 OutboxJob，未出现在审核/发布对象中。
- `data/mvp-contract-v0/schema.json:789-855` 的 Summary 使用 `summary_version`/`summary_version_hash`，没有矩阵 `:158` 使用的 `summary_draft_version`；ADR 的 `summary_draft`、矩阵的 `summary_draft_version` 与领域名称没有映射。
- `state-machine.json:287-294` 的 publication 幂等 key 也只列 `publication_id + approved_content_version_hash + approved_summary_version_hash`。

**风险：** “Bundle Hash 绑定”可被不同实现解释为摘要 hash 对、payload hash 或 release bundle 行；稳定公开身份也可能被 `publication_id` 或另一个 `public_id` 表达，形成第二套发布真值。

**必改：** 选择一种数据模型并写入 `data/mvp-contract-v0`：要么把 Bundle/ReviewDecision/public identity 映射为现有实体和字段，要么升级 contract version 添加实体；同步 ADR、Spec、测试矩阵、幂等 key、状态机和 fixture，明确 payload hash 的规范化输入与发布重试对账规则。

### P0-05：P0 安全与失败 fixture 未进入唯一 fixture 合同

**证据：**

- 既有矩阵 `:127-135,169-197` 要求 429、5xx、超时、授权过期、恶意 URL、提示注入、恶意 HTML/Markdown、XML 资源耗尽、恶意媒体、开放重定向、CSRF/越权和 secret 扫描样本；这些路径多为 P0。
- `data/mvp-contract-v0/fixtures.synthetic.json` 的 8 个 case 仅覆盖 source seed、规范化失败、重复摄取、幂等重试、stale review、发布重试、stale epoch、snapshot failure（`manifest.json:59-75` 记录 8 case）；没有上述安全 payload 与网络错误样本。
- ADR `:164` 将 `data/mvp-contract-v0` 声明为唯一领域合同输入，当前没有另一个带 manifest/hash 的安全 fixture 合同。

**风险：** P0 安全边界和错误恢复只能依赖临时自造输入，无法在定版前保证输入稳定、可审计、无真实外联，也可能出现测试覆盖声明与实际 seed 不一致。

本项按 P0 判定的依据是 ADR `:164` 对领域字段/状态/fixture 输入的唯一性要求和矩阵 `:127` 对“固定 fixture、稳定 seed 与 hash”的要求；若团队决定允许代码内确定性生成安全 payload，也必须先把生成器、输入 hash、预期状态和零外连约束写入同一版本化合同。当前没有这份等价合同。

**必改：** 扩展同一 fixture contract 或建立明确版本化的本地安全 fixture manifest；为每个 P0 输入写稳定 hash、预期状态、零外连断言和脱敏规则。禁止通过真实 URL、真实平台、真实 AI 或真实媒体补齐样本。

> 下列 I-01 是 C 轴实现验收门禁，特意不归入 A 轴 P0；它不阻断合同定版后的最小脚手架许可。

### 实现门禁 I-01：当前环境未满足 Node 24；工程入口尚待初始化（不阻断合同定版或最小脚手架）

**证据：**

- ADR `:61,235-242`、Spec `:118` 要求 24.x Active/Maintenance LTS，并在 `verify:env` 拒绝非允许版本。
- 当前现场为 Node `v25.5.0`。`app/package.json` 和 `app/package-lock.json` 尚不存在；它们属于定版后最小工程初始化应产生的结果，不能作为拒绝创建最小脚手架的理由。初始化后的实现验收仍必须拥有 lockfile 并执行 `npm ci`、`verify:env`、`build`、`lint`、`typecheck`、`test` 和 `check`。
- 开发预检 `2026-08-01-M4工程开工预检报告.md:3-9,113-124` 只证明 disposable Python/SQLite 探针，明确未证明 Node LTS、真实端口、依赖安装或正式 app。

**风险：** 在当前 Node 25 环境直接宣称实现或 Build Loop 通过，会绕过 ADR 的运行时门禁；最小目录/配置脚手架可以在合同定版后创建，业务实现和验收仍需等待 Node24 与 lockfile。

这是实现验收环境阻断，不把 Node 25 反推成 Spec/ADR 的语义冲突，也不阻断合同定版后创建最小脚手架；前述 P0-01 至 P0-05、P0-07、P0-08、P0-09 属于独立合同可验收性阻断。

**实现前置：** 合同定版后可创建最小 `app/` 脚手架；在实现验收前切换到受支持的 Node 24.x LTS，提交 lockfile，记录 `process.versions.node`、package manager 和 `node:sqlite` spike，再执行候选命令。Node 25/Python probe 结果只能保留为环境/逻辑参考。

### P0-07：P0 状态存在于 enum，却没有可达转换

**证据：**

- `state-machine.json:6-19` 声明 `linked_existing`、`blocked_adapter_missing`、`blocked_platform`；机械读取发现三者不在任何 transition 的 `to` 集合中（`blocked_authorization` 以外无 adapter/platform 路径）。
- `state-machine.json:221-257` 声明 outbox `cancelled`，但没有任何 transition 进入 `cancelled`。
- Spec `:62-64,134-135` 与矩阵 `:107,151,171-178` 要求重复归属、适配器缺失、平台受限、停用/授权过期、取消和 dead-letter 均可观察、可恢复或安全阻断；矩阵 P-11 的 `task blocked/cancelled` 也没有说明应落到 Source、OutboxJob 还是独立任务实体。

**风险：** schema 可以接受状态，但实现无法按合同进入状态，导致 P0 失败路径成为不可测的死分支或被错误地映射为普通失败。

**必改：** 为每个 enum 状态提供至少一个合法入口和出口（或删除状态并升级 contract version），补充 fixture、API/页面显示和恢复断言；统一 `source_stop_status`、OutboxJob `cancelled` 与 P-11 的任务停止落态，`cancelled` 必须由 source stop/急停或人工取消路径明确产生。

### P0-08：唯一 synthetic fixture 没有本地发布成功和公开信息流 happy path

**证据：**

- 矩阵 U-01 要求 `feed` 有 3 条已发布 fixture（矩阵 `:103`），P-09/P-12 要求人工 approve 后形成一个 active local projection（矩阵 `:149-152`）。
- `data/mvp-contract-v0/fixtures.synthetic.json:219-311` 的 4 个 Content 状态只有 `review_pending`、`dedup_pending` 和 `publish_queued`，没有 `published` Content。
- 同一 fixture 的唯一 Publication 为 `retryable_failed` 且 `published_version_hash=null`（`fixtures.synthetic.json:486-504`）；schema 也没有 public projection/public_id 实体或字段（`schema.json:1046-1159`）。

**风险：** 四页 feed/detail 的正常出口和“人工审核→本地发布→公开投影”无法由唯一 fixture 直接执行。只保留失败发布样例会让 P-09/P-12 依赖临时 seed，无法验证稳定 `public_id`、已发布状态和正常详情跳转。

**必改：** 在同一版本化 fixture 合同中加入至少 3 条已发布、可从 feed 进入 detail 的合成 projection，以及对应 approved Bundle、public identity、source evidence 和无图/有图样例；保留当前 retryable_failed 作为独立失败 case。所有 projection 必须 `synthetic_only=true`、无外部调用。

### P0-09：安全部 A 层指出的 fail-closed 文字尚未成为可机械引用合同

**证据：**

- 安全部报告 `2026-08-01-M4本地安全门禁与外部IO隔离-审核报告.md:28-30` 将门禁分为 A（ADR/Spec 定版前）和 B（app/Build Loop 实现后），并明确 A 层仍缺可机械检查的安全文字。

**风险：** 仅凭“loopback、CSRF nonce、fixture/mock、safe DTO、security 模块”等宽泛表述，无法在定版前机械拒绝单变量外部 IO 绕过、Origin/代理头绕过、nonce 重放、日志/SQLite 泄露、恶意 URL/媒体解析或旧 fence 写入。

## 4. P1 重要缺口

### P1-01：59 条 M3 seed 与 3 条 synthetic Source 的选择和顺序未冻结

- ADR/Spec 要求 fixture provider 能读取 59 条 M3 脱敏载荷且全部 `enabled=false`（ADR `:273-281`、Spec `:120-122`）。
- `fixtures.synthetic.json` 只有 3 条合成 Source；`manifest.json:65-75` 的 entity counts 也只有 3 Source。两者可以共存，但当前没有明确 `seed:fixtures` 的分层顺序、表名、迁移批次和“59 条 M3 seed 不被 synthetic seed 覆盖”的断言。
- manifest 对上游 M3 payload 有 hash，但对 `schema.json`、`base-mapping.json`、`state-machine.json`、`fixtures.synthetic.json` 本身没有逐项 hash；既有矩阵又要求 fixture seed/hash 稳定。

**要求：** 固定 `m3-shadow-seed` 与 `synthetic-case-seed` 的独立命名、输入 hash、行数和 isolation；所有 M3 URL 只作离线字段，provider/adapter 必须对网络零命中。

### P1-02：ADR 物理表/内部表与领域实体缺少一份映射

ADR `:146-160` 列出 `source_config_fixture`、`source_observation`、`content_item/content_version`、`summary_draft`、`release_bundle/review_decision`、`inbox/outbox/task_attempt/dead_letter/audit_event` 等物理或内部对象；数据 schema 只有 Source、CapturedItem、Content、Event、Summary、MediaCandidate、Review、Publication、OutboxJob、FixtureCase。ADR 已声明领域 schema 唯一，但没有说明每个物理表如何映射、哪些是内部 envelope、哪些字段不得成为第二领域事实。

**要求：** 在代码 ADR/数据迁移合同中增加 table-to-domain map、读写 owner 和内部 envelope 边界；未形成映射前，相关表不进入正式实现。

### P1-03：`node:sqlite` Release Candidate 和真实 Node24 行为尚无证据

ADR `:62,69,345` 允许 Node `node:sqlite` 作为本地状态库，但要求隔离 repository 并以 spike 验证事务、锁等待和 crash/recovery。当前 Python sqlite 探针不能覆盖 Node API、Next server 生命周期、WAL/锁语义或迁移脚本。完成 Node24 入口后需执行同一事务、双 worker、崩溃恢复和 stale fence 证据。

### P1-04：路由、后台角色和页面权限仍是 unknown

Token/map `source.route_names_are_hints=true`，设计合同的 `/`、`/feed`、`/story/:storyId`、`/admin/review`、`/admin/sources` 仅为提示；ADR `:75,135-140` 也保留审核布局、信源操作权限和路由为 unknown。现有矩阵以 `feed/detail/review/sources` 逻辑 ID 测试，这是合理的静态策略，但正式实现前必须登记实际路由、角色、loopback、local-dev session、Origin 和 CSRF 的映射。

### P1-04a：领域状态到页面 status alias 的映射未冻结

`state-machine.json:6-19` 的 Source 状态包含 `validating`、`activation_pending`、`queued`、`collecting`、`active`、`normalization_failed`、`dedup_needs_review`、`linked_existing`、`blocked_adapter_missing`、`blocked_authorization`、`blocked_platform`、`queue_failed`、`collection_failed`；Token/map `business_state_aliases.source`（约 `:162-183`）只列 `proposed`、`normalization_pending`、`dedupe_pending`、`adapter_check_pending`、`enqueued`、`enabled`、`manual_only`、`restricted`、`failed`、`disabled`、`unknown`。矩阵 U-05 也只要求 normal/unknown/restricted/failed。未写明 blocked adapter、授权、平台、队列失败和采集失败应落到哪个 UI alias，正式页面可能显示错误状态或隐藏安全阻断。

**要求：** 在数据/设计合同中建立逐项 domain-state → UI-alias → 可见文案/图标/恢复动作表；所有安全阻断态必须可见，未知不得被降级成正常或已启用。

### P1-05：依赖安装、锁文件、许可证和目标网络未验证

开发预检 `:55-83` 记录无 package manifest/lockfile、公共 registry、无目标依赖安装证据；在 B 轴脚手架阶段应产生 package manifest/lockfile，缺失本身不阻断 B 轴许可。ADR `:248-267` 给出 `npm ci` 等命令，却明确标为候选。需要在 Node24 环境中以 locked install 复现，并保留依赖、许可证、secret/漏洞扫描和无外连证据；不能以当前 npm 缓存或 Python probe 推断安装成功。

### P1-05a：snapshot failure case 缺少可对账的 snapshot / last-known-good 事实

`fixtures.synthetic.json` 的 `case-stale-epoch` 与 `case-snapshot-failure` 都引用 `job-synth-004`；该 job 是 `snapshot_sync` 且 `job_status=stale_epoch`，但 schema/fixture 没有 Snapshot 实体、snapshot manifest 或 last-known-good 载荷。ADR `:159,189,293,317-320` 和状态机的 snapshot 幂等键要求部分/空/过期快照保留上一份完整读模型。当前 case 只能触发 stale epoch，不能独立复现“部分 snapshot 不替换 last-known-good”。

**要求：** 增加脱敏 snapshot manifest、完整/部分/空/过期版本和 last-known-good 指针，或明确其为内部 envelope 并补映射、hash 和断言；两个 case 必须互不覆盖。

### P1-06：实现后的页面无障碍与真实媒体/字体仍未验证

Token/map `validation` 将 `voiceover_nvda_talkback`、`production_fonts`、`production_media` 标为 `unverified`；矩阵 `:114-121,210-215` 要求人工键盘、屏幕阅读器、最差裁切、深浅主题、强制色和 200% 缩放。设计规范、深浅主题样板和首批实现级合同已经用户授权固定并核收，可作为开工输入；当前没有 app 页面、真实 AT、生产字体/媒体和实现后预览证据。该项属于 C 实现验收未验证，不阻断 B 最小脚手架许可。

### P1-07：disposable preflight 变量与 M4 canonical 变量需要防混用测试

开发预检报告 `:175-204` 使用 `DATABASE_URL`、`SOURCE_PROVIDER`、`REAL_BASE_ENABLED`、`AUTO_PUBLISH` 等探针示例；ADR `:214-246` 将 `SOURCE_CONFIG_PROVIDER`、`ADAPTER_MODE`、`REAL_FEISHU_IO`、`REAL_EXTERNAL_IO`、`REAL_FORM_SUBMIT`、`PUBLISH_MODE` 定为 M4 canonical，并要求拒绝旧组合。实现需有 `verify:env` 负向测试，证明旧探针变量不会改变 provider、真实 IO 或发布行为。
