## 3. 整改实现

### 3.1 启动 argv fail closed

`app/package.json` 的 `dev`/`start` 只把内部 mode 传给 `scripts/serve.ts`。入口只接受 `dev` 或 `start`，并对 `process.argv.slice(3)` 执行长度为零断言。任何附加元素都抛出 allowlist code `CLI_ARGUMENTS_FORBIDDEN`。

校验顺序固定为：

1. 检查内部 mode；
2. 拒绝全部附加 argv；
3. 检查 runtime readiness；
4. 写入固定 Node/Next runtime 环境；
5. 动态导入 Next CLI；
6. 只传入 `127.0.0.1:3000`。

附加 argv 失败发生在 Next 导入及监听之前。原先 runtime-ready 成功行也从 serve 入口移除，避免后续启动失败时混入成功收据。

### 3.2 CLI 稳定 allowlist JSON

统一入口 `runSafeCli` 捕获命令主体的同步与异步失败，并通过 `safeReasonCode` 收敛为静态 `CLI_REASON_CODES`。输出结构固定为：

```json
{"event":"cli_failure","status":"rejected","reasonCode":"<ALLOWLIST_CODE>","externalCalls":0}
```

失败 envelope 不包含 `message`、`stack`、path、URL、payload 或环境变量值。未知错误收敛为 `CLI_INTERNAL_ERROR`；SQLite 原生 code 收敛为 `SQLITE_FAILURE`；已知配置、migration、seed、fixture 和 readiness code 只有命中静态 allowlist 才可输出。

`runtime-bootstrap.ts`、`verify-env.ts`、`db-migrate.ts`、`seed-fixtures.ts` 与 `serve.ts` 均使用同一入口。

### 3.3 自动化验收

新增 `src/tests/p1-cli.test.ts`，通过精确 Node24 下的真实 npm 子进程验证 10 个 P1 场景；新增 `scripts/p1-acceptance.ts`，在 build 后启动真实生产进程、轮询 health、核对 DTO 并清理独立进程组。`npm run check` 在 build 后执行 `npm run test:p1`，使正常 start/health 成为完整 check 的必过出口。
