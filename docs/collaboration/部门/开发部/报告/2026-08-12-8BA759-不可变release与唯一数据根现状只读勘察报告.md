# 不可变 release 与唯一数据根现状只读勘察报告

## 1. 勘察边界

本报告只根据当前仓库静态代码确定路径推导和调用链。未修改 `app/`，未运行测试、build、SSH 或数据库写入。产品部 `TASK-20260812-0196EB` 仍在制定 successor 合同；本报告不代替该系统级定案。

## 2. 已证实的调用链

### 2.1 Admin 运行时私库

1. `app/src/server/runtime-config.ts:16-17` 把每个可执行 release 的 `appRoot` 定义为当前源码模块所在 App 根。
2. `app/scripts/admin-install-macos.ts:84-99` 将该 `appRoot` 传入 `prepareAdminDeployment`。
3. `app/src/server/admin-service/deployment.ts:307-333` 把 `appRoot` 写入 `admin-service-deployment-v2` manifest；`dataRoot` 另外指向 `~/Library/Application Support/F1Plus1/Admin`。
4. `app/src/server/admin-service/deployment.ts:351-358` 生成的 Admin plist 将 `ProgramArguments` 和 `WorkingDirectory` 固定到 manifest 中的 release `appRoot`。
5. `app/scripts/admin-service.ts:13-28` 读 manifest，同时把 `manifest.appRoot` 和 `manifest.dataRoot` 传给 runtime。
6. `app/src/server/admin-service/runtime.ts:135` 打开审核库时只传 `config.appRoot`；`config.dataRoot` 只用于 Passkey/bootstrap 存储（`runtime.ts:149-150`）。
7. `app/src/server/admin-service/runtime.ts:73-92` 的 `openReviewAdminDatabase(appRoot)` 调 `openRssDatabase(root)`，并在同一库原位施加 `0001/0002/0003` migration。
8. `app/src/server/rss/repository.ts:29,118-125` 将库名硬固定为 `.local/f1plus1-rss-real-private.sqlite`；`app/src/server/db/database.ts:293-320` 把相对路径解析到当前 `appRoot/.local`。
9. `app/src/server/db/database.ts:208-240` 在目标不存在时使用 `O_CREAT|O_EXCL`创建库文件，所以新 release 启动 Admin 不会拒绝缺库，它会在新 release 的 `.local` 下创建第二个库。
10. 独立 sender CLI 同样存在该耦合：`app/scripts/projection-sender.ts:16-17` 以 `manifest.appRoot` 调 `openReviewAdminDatabase`。

结论：`AdminDeploymentManifest.dataRoot` 已显式存在，但当前数据库 opener 没有使用它，也没有 `reviewDatabasePath/reviewDataRoot` 字段。版本化 release 直接 load 会把审核链接到 release-local 库，不会继续打开现有 live RSS 唯一私库。

### 2.2 RSS LaunchAgent

1. `app/scripts/rss-scheduled-run.ts:16,26-35` 从该 release 的 runtime `appRoot` 生成 `rssDeploymentPaths`。
2. `app/src/server/rss/deployment.ts:207-230` 将 database、manifest、release manifest、logs 和 temp 全部放在该 `appRoot/.local`。
3. `app/src/server/rss/deployment.ts:268-310` 把 scheduled script、`WorkingDirectory`、TMPDIR 和 log 全部写成该 `appRoot` 下的绝对路径。
4. `app/scripts/rss-collect-once.ts:22-23,62-64` 再从自身 script 反推 `appRoot`，并打开同样的 `.local/f1plus1-rss-real-private.sqlite`。

结论：RSS 调度器和数据库也与 plist 所指的代码 release 绑定。目前旧 live plist 持续写旧 live app 的库；若把 RSS plist 直接切到新 release，它会另用新 release `.local` 下的库。

### 2.3 Public prepare 与 synthetic rollback

1. `app/scripts/install-macos-public-beta.ts:17-23` 把当前 release 的 `appRoot/projectRoot` 传给 `preparePublicMacAgents`。
2. `app/scripts/install-macos-public-beta-core.ts:155-163` 对该 target release 进行 release manifest 验证。
3. `install-macos-public-beta-core.ts:174-179` 同时把同一 `input.appRoot` 当成 rollback root，要求其 `.next/BUILD_ID` 与 `.local/f1plus1-public-multimedia-synthetic.sqlite` 符合外部 rollback release/hash。
4. `install-macos-public-beta-core.ts:204-219` 生成的 public-beta/quick-tunnel plist 的 script、WorkingDirectory 和 logs 同样指向 `input.appRoot`。
5. `install-macos-public-beta-core.ts:221-234` 以该 `input.appRoot` 生成 projection receiver plist；然而 projection 数据根由 home 推导，不在 release 内。

结论：public prepare 的代码根与 synthetic rollback 根现在是同一个参数。已验签的新 release 只保证 content-addressed 运行闭包，它不等于当前 live synthetic 库根。因此，用新 release `appRoot` 执行 prepare 时，rollback DB 校验要么因库不存在早停，要么在 release 中意外有库时校验了错误根。

### 2.4 Public projection 数据根

1. `app/src/server/public/deployment.ts:108-129` 把 public projection root 固定在 `~/Library/Application Support/F1Plus1/Public/projection`，与 release 根物理分离。
2. `public/deployment.ts:204-225` 把该 canonical root 写入 public-only manifest，同时只把 receiver script/WorkingDirectory 指向 target release `appRoot`。
3. `app/scripts/public-projection-runtime.ts:18-27` 读 public-only manifest，用 canonical projection root 创建 receiver。
4. Public Next real reader 从 plist 的 `F1_PUBLIC_PROJECTION_ROOT` 取根（`install-macos-public-beta-core.ts:190-198`），`app/src/server/public/runtime.ts:14-22` 传入 `PublicRealSnapshotReader`，后者每次读取该 root（`snapshot-adapter.ts:75-83`）。

结论：public real projection 根已与不可变 release 解耦，这一部分已具备显式稳定根。

## 3. 已证实的风险

| 编号 | 级别建议 | 已证实事实 | 影响 |
|---|---|---|---|
| R1 | P1 | Admin/runtime 以 release `appRoot` 打开相对 RSS DB，且 safe opener 在缺库时会创建文件。 | 新 Admin release 可形成第二私库；旧 RSS writer 和新 Admin 的审核/发布事实将分叉。 |
| R2 | P1 | projection sender CLI 也以 `manifest.appRoot` 打开库。 | 即使 Admin HTTP 运行时之后单独修复，sender-once 仍可读/写错库。 |
| R3 | P1 | RSS LaunchAgent 的 DB/log/temp/release manifest 都由 release `appRoot` 推导。 | 代码 release 替换时会连带改变 writer 根；无法只替换代码而保留唯一持久根。 |
| R4 | P1 | Public installer 用 target release `appRoot` 验证旧 synthetic rollback BUILD_ID/DB hash。 | 新代码闭包与旧 rollback 资产无法分别锦定，prepare 在正确输入下也可能早停。 |
| R5 | P2 | Admin manifest 存在 `dataRoot`，但其语义只覆盖 auth/session/recovery/log/manifest，字段名容易被误解为已覆盖 review DB。 | 后继只改 manifest 输入却漏改 opener/sender 时，问题仍存在。 |

## 4. Unknown / 不能从静态代码推导

- 产品 successor 最终选 `reviewDatabasePath` 还是 `reviewDataRoot` 尚未冻结；本报告不定案。
- 长期是否把唯一私库原子迁移到 Application Support，及其停采/恢复窗口，属独立产品、数据、安全任务。
- 本勘察没有读取 M1 真实 plist 或 DB 文件，因此不把部署机当前字节身份重复写为本任务已验证事实。
- `openSafeDatabase` 当前只允许 `appRoot/.local` 或测试 root；要安全打开显式外部 production DB，需新的生产路径边界，不能只把绝对路径传给现有 opener。

## 6. 对产品 successor 的事实约束

- 不能只把 `dataRoot` 改名或复用为 review DB root；它已存放 session/recovery/passkey/bootstrap/log/deployment 资产，DB 边界需要独立精确语义。
- 第一版绑定当前唯一 live RSS DB 时，opener 必须要求文件已存在；任何 missing-create 都会重新引入第二库风险。
- 公开候选切换只应改代码/read-mode/release 指针，不应把私库、projection root 或 rollback synthetic 库复制进新 release。
- RSS 长期稳定数据根的迁移属后继系统合同；当前只修 Admin 访问方式时，RSS plist 仍指旧 live app，不应在同一 cutover 中悄然切它。
