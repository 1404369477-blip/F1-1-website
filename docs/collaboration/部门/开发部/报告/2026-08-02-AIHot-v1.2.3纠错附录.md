## 4. E2：installer 的 rename/backup 恢复边界

### 4.1 原句与准确替代

原 5BD745 报告 §4.2 表格将 `install.sh` 的语义概括为包含“原子 mv”；§7.2 第 223–224 行写道：

> “每个文件计算 SHA-256，验证 `SKILL.md` 的 `name/license` frontmatter 和 `agents/openai.yaml` 的 `interface`，全部通过后才用同磁盘临时目录 + `mv` 激活。”
>
> “共享目录发现旧副本时默认停止；`--migrate-legacy` 才允许显式迁移；失败路径尝试恢复 backup。”

准确替代表述为：

> “每个文件在临时 package 目录中完成 SHA-256、frontmatter、agent 元数据和 6 文件数量校验后，installer 先按迁移规则把旧副本移到 backup，再把既有 target 移到 `$INSTALL_PARENT/.aihot-previous.$$`，最后将已校验的 package 目录移动到 target。正常命令失败且 `COMMITTED=0` 时，`EXIT` trap 会在目标缺失的条件下尝试把 backup 移回；该流程存在 target 短暂缺口，不能据此宣称全过程 crash-atomic、SIGKILL/断电安全或目标目录始终可见。”

“原子”一词若保留，只能描述某一次同文件系统目录 rename 在正常执行条件下的操作性质，不能扩展为整个 installer 事务的崩溃原子性。

### 4.2 固定 `install.sh` 行证据

固定 SHA 下 `aihot/install.sh` 的文件 SHA-256 为 `1cb60f33868c2ae670eb5344516d584959504856d5b7b5ab4c7a091977edd768`，Git blob 为 `ec211d4376c4fd2efad9cfd0bfc41f4fb2d7bf6f`。相关行逐字核对如下：

| 行号 | 静态行为 | 证据边界 |
|---:|---|---|
| 116–131 | `restore_on_failure` 只在 `COMMITTED=0` 时检查 backup；仅当 backup 存在且 target 不存在时执行 `mv backup target`；随后清理临时根目录。 | 这是正常 `EXIT` 路径的有条件补救，不是崩溃/断电恢复协议。 |
| 238–242 | 创建临时根和 package 目录，设置 `trap restore_on_failure EXIT`。 | `EXIT` trap 依赖 shell 能够正常退出；强制杀进程和断电不保证触发。 |
| 250–305 | 下载并校验 manifest 的 6 个允许路径、SHA-256、必需文件、frontmatter 和 agent interface；第 305 行拒绝 `README.md` 进入 runtime package。 | stage/package 的完整性检查成立；它不扩大为 9 文件树的全部文件证明。 |
| 307–313 | 迁移旧副本时先 `mv legacy backup`。 | 迁移路径也有 backup 窗口。 |
| 315–319 | 已有 target 时先设置 backup 路径，再执行 `mv "$INSTALL_DIR" "$TARGET_BACKUP"`。 | 此后 target 可能暂时不存在。 |
| 321–324 | 执行 `mv "$PACKAGE_DIR" "$INSTALL_DIR"`，成功后才把 `COMMITTED=1`。 | 在旧 target 已移走、package 尚未移入期间发生 SIGKILL/断电时，代码没有机会恢复 target。 |
| 326–329 | `COMMITTED=1` 后尝试删除旧 backup；删除失败只打印 warning。 | 新 target 激活与旧 backup 清理不是单一持久化事务。 |

静态全文检索未发现 `fsync`、目录 fsync、信号处理或独立崩溃日志机制。该观察只支持“未从代码证明 crash-atomic/断电持久性”，不推断特定操作系统或文件系统在每种异常下的实际行为。

### 4.3 正常失败与异常中断的分离

| 情形 | 代码可证明的结果 | 结论 |
|---|---|---|
| manifest/hash/frontmatter 校验失败 | target 尚未移动，`fail` 退出，既有安装通常保持不变 | 校验前置边界成立。 |
| 已移动旧 target 后，package `mv` 正常返回失败 | `fail` 触发 `EXIT`；若 target 缺失且 backup 可见，会尝试恢复 | 有条件的正常失败恢复，恢复命令自身失败被忽略。 |
| `SIGKILL`、进程崩溃或断电发生在旧 target 移走之后 | shell 不保证执行 `EXIT` trap；可能只剩 `.aihot-previous.$$` 或迁移 backup | 存在短暂缺口和 orphan backup 窗口，crash-atomic 为 Unknown。 |
| 激活后 backup 删除失败 | 新 target 保持可见，旧 backup 留存并打印 warning | cleanup 与激活分离，不能写成单一原子提交。 |

## 5. 对 F1+1 的现行采用结论

1. `manifestAudit` 继续采用 6 个 runtime 文件逐项 hash、allowlist、重复路径和路径安全校验；不把 `README.md`、`install.sh`、`manifest.sha256` 误计入 6/6。
2. 9 文件 tree 只用于完整目录审计。目录存在 README 不改变其未进入 runtime manifest/package 的事实，也不改变 MIT 文件许可证和 API 数据/第三方权利的独立边界。
3. AIHot `install.sh` 在当前路线继续禁止执行。F1+1 不使用它初始化 Agent 目录，也不把其目录替换流程作为 SQLite、worker、发布或恢复合同的证据。
4. 若未来需要本地更新器，应先补独立设计和测试：目标存在性/锁、backup 命名与 orphan 回收、异常终止后的启动恢复、目录项持久化、权限和 symlink 防护、恢复收据以及可重复演练。接受测试前保持 `installer_unknown`，不把正常 `mv` 结果升级为 crash-safety。
