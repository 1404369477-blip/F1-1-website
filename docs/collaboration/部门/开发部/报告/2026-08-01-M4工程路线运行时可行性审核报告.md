### 4.1 运行时版本指纹的额外发现

在同一个本机 Node 25.5.0 进程中观察到：


## 5. Next.js App Router 与 Node 24 兼容性

### 5.1 一手证据与结论

- Next.js 安装文档列出最低 Node.js 20.9；Next.js 16 升级文档再次列出 Node.js 20.9+、TypeScript 5.1+，并说明 App Router、Turbopack 和 `next build`/lint 的脚本变化。Node 24 满足最低版本要求。
- Next.js 支持策略将 16.x 标为 Active LTS，建议使用最新 Active/Maintenance LTS，不建议使用 canary 提供生产流量。
- Next.js 官方博客在 2026-07-20 的安全发布条目列出 `16.2.11 (Active LTS)`；M4 应把该安全补丁作为当前 `next` 精确版本候选，初始化时重新检查官方安全页。
- App Router Route Handlers 位于 `app/**/route.ts`，使用 Web Request/Response API；涉及 `node:sqlite` 的 Handler 必须显式声明 Node runtime，并保持数据库模块只从 `src/server` 引入。

结论：**Node 24 与 Next.js App Router 的最低版本关系为 PASS；实际构建兼容性为 CONDITIONAL PASS。** 本机没有 Next 依赖和 lockfile，无法宣称 `next dev`、`next build` 或 React peer 组合已通过。

### 5.2 A 层精确版本钉住策略（静态候选）

以下内容属于定版前可以审核的候选合同。实际文件和 lockfile 在 B 层生成，C 层再验证运行结果：

1. Node 运行时先以 `24.18.0` 作为可复现候选。Node 官方发布页确认该版本是 LTS，且该发布页列出 SQLite 3.53.1 及 npm 11.16.0 的更新记录；SQLite 3.53.1 高于 3.51.3 的 WAL-reset 修复线。
2. 初始化时若组织要求跟随最新 24.x 安全补丁，先核对官方 Node 24 发布物与 SHASUMS，再把具体 patch 写入 `.nvmrc`/`.node-version`、`package.json.engines.node` 和 `verify:env`。不允许使用 `24.x`、`latest` 或当前机器的 25.x 作为运行时合同。
3. `next` 以 `16.2.11` 作为当前安全补丁候选，使用 `--save-exact`，React/ReactDOM 按 Next 16 peer 要求选定并由 lockfile 固定；初始化时重新检查 Next 官方安全公告，出现新安全补丁要重新走版本核验。
4. 在 `package.json` 中记录项目要求的 npm 版本或 `packageManager`，其值应来自所选 Node 发布物现场的 `npm --version`，不能凭本机 npm 11.8.0 推断。
5. B 层的 manifest 约定所有直接依赖使用精确版本并提交 `package-lock.json`；C 层使用 `npm ci` 作为冻结安装出口，禁止用安装时自动改写 lockfile 的方式掩盖 manifest/lock 不一致。
6. A 层规定项目级 `.npmrc` 使用 `engine-strict=true`，并由 `verify:env` 做精确 Node/npm/SQLite 检查；B 层落盘，C 层执行。npm 官方文档说明 `engines` 在未启用 `engine-strict` 时主要是提示，因此只写 `engines` 不够。

### 5.3 Server-only 边界

`node:sqlite` 只允许出现在 `src/server/db` 及其 server-only 调用链；页面 Client Component、浏览器 bundle、Edge runtime 和共享 DTO 不得直接导入。所有需要 SQLite 的 Route Handler 显式写 `export const runtime = 'nodejs'`，并用 import 结构或 `server-only` 防止误打包。该约束同时降低 Node 原生模块进入浏览器构建的风险。

## 7. `node:sqlite` 隔离与稳定性判断

### 7.1 一手证据

Node 24.18.1 文档把 `node:sqlite` 标为 Stability 1.2（Release candidate），并记录 `DatabaseSync` 的 `timeout` 选项；它仍需隔离在 repository 后方。SQLite 官方文档给出的关键事实是：

- WAL 允许读写并发，但同一数据库文件一次只能有一个 writer；WAL 依赖同机 shared memory，不能放在网络文件系统。
- `BEGIN IMMEDIATE` 立即申请写事务，已有 writer 时可能返回 `SQLITE_BUSY`；COMMIT 也可能因为读事务而暂时失败。
- `busy_timeout` 按连接设置等待上限，每个连接只有一个 busy handler。
- SQLite 3.7.0–3.51.2 存在 WAL-reset bug，影响 WAL 下多个进程/线程同时写入或 checkpoint；3.51.3 起修复。

### 7.2 本轮无持久化探针的现场结果

测试使用本机 `/opt/homebrew/bin/node v25.5.0`、Node `DatabaseSync`、系统临时目录和四个独立子进程；所有临时文件在脚本结束时清理。结果：

| 场景 | 结果 | 对合同的含义 |
|---|---|---|
| 单进程 baseline | SQL 引擎 `3.53.3`，`journal_mode=wal`，`busy_timeout=1000`，提交行 1，COMMIT 后 `isTransaction=false` | API、WAL、显式事务基本可用 |
| 四个独立 writer，各 25 次 `BEGIN IMMEDIATE → INSERT → COMMIT` | 101 行（含 parent 1 行），每个 worker 25 行，`integrity_check=ok`，无子进程失败 | 同机跨进程写入可通过；代码仍需要有限重试 |
| 锁占用 800ms，挑战连接 `timeout/busy_timeout=180ms` | 约 211ms 后返回 `ERR_SQLITE_ERROR: database is locked` | timeout 是有限等待，不是成功保证；锁耗尽必须分类、重试或进入失败队列 |
| `SIGKILL` 终止未提交写事务后重新打开 | 已提交行保留，未提交行消失，`integrity_check=ok`，WAL 可恢复 | 基本 crash recovery 可行 |
| `SIGKILL` 终止未提交 DDL + `user_version=1` | 恢复后 version 仍 0、迁移表不存在；随后完整事务重试后 version 1、表存在、完整性通过 | migration 必须以单事务和 user_version 边界提交 |

这组结果只覆盖 Node 25.5.0；它没有证明 Node 24.18.0、Next 构建、磁盘断电、网络文件系统、长时间 checkpoint 或生产容量。`node:sqlite` 在 Node 24 的 Release Candidate 语义仍需目标运行时复测。

### 7.3 repository 最小实现合同

建议在代码 ADR 中冻结以下最小合同：

1. 每个 `DatabaseSync` 连接打开后设置 `foreign_keys=ON`、`journal_mode=WAL`、明确的 `synchronous`（建议 durable 状态使用 `FULL`，若本地选择 `NORMAL` 必须记录掉电耐久性取舍）、`busy_timeout` 和 defensive 选项。
2. 所有领域写入通过 repository；VS-1 的 observation、inbox、epoch/CAS 和 outbox intent 在同一个 `BEGIN IMMEDIATE` 事务提交，提交前不标记 task 完成。
3. 事务体内不执行网络、文件大读、模型调用或外部 adapter；M4 的 fixture/mock 结果先在事务外准备，事务只写已校验的本地状态。
4. `SQLITE_BUSY`、`database is locked` 和 commit busy 归一为 `lock_contention`，使用有上限的指数退避/抖动；超过次数进入 task failure/dead-letter，不无限循环。
5. M4 默认只允许一个 mock worker 实例；若需要多个同机进程，必须仍然使用同一策略、同一数据库目录和同一 migration 版本，禁止网络文件系统。
6. migration 使用 `PRAGMA user_version` 或等价的迁移表，以“一个迁移一个事务、可重复检查、失败后恢复到旧版本”为边界；启动时执行完整性检查或明确的轻量检查。
7. 记录实际 SQL 引擎版本和 source id；`verify:env` 拒绝低于 3.51.3 的 WAL 多连接运行时。

### 7.4 失败时的最小替代出口

- 仅跨进程竞争无法满足：将 M4 降级为单进程 worker/单租约，Web 只读连接保留，启动时拒绝第二个 worker；保持原 repository 接口和领域合同。
- 事务、恢复或 Node 24 `node:sqlite` API 本身不满足：保持 ADR `proposed`，提交新的替代 spike/ADR。优先比较单进程纯本地 worker、`better-sqlite3` 等本地适配器或 Python 标准库 SQLite；每个替代都要重新做安装、供应链、事务、恢复和中国大陆可达性核验。当前不静默切换。

## 8. Web + 独立 worker + SQLite 闭环判断

**判断：CONDITIONAL PASS，默认形态应收窄为“单 Web 进程 + 0/1 个 mock worker + 单机 SQLite 文件”。**

原因与边界：

- Next Route Handler 与 worker 可以共享 TypeScript 类型、repository、fixture 和错误分类，符合单运行时目标。
- SQLite 的单 writer 语义能支撑 M4 的低并发本地状态；WAL 能让公开读与短写事务并行。
- 四进程写入矩阵在 Node 25 通过，说明候选边界有实现空间；锁耗尽实验同时证明必须保留有限重试和失败出口。
- SQLite 只适合本地同机路径。多实例、网络文件系统、生产备份、容量、跨地域部署和高写入吞吐均留到独立存储 ADR。
- Web 与 worker 的应用级契约仍需在正式代码中测试：inbox lease、CAS、epoch fence、幂等 key、outbox 原子提交、worker 崩溃重启和 stale task 处理。本轮没有 app 代码，因此这些项仍未通过。
