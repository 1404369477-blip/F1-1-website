# 两台 MacBook 配置期同网与运行期跨网联动方案

## 0. 结论

截至 2026-08-09，唯一推荐是 **A：职责隔离的三通道 + Admin server pull**：

1. **协调通道**：iCloud 仅在 M5 工作 Mac/iPhone 侧保存低风险、可重建的研究笔记、任务草稿和人工待办。专用 Admin Mac 不登录个人 Apple Account，也不把 iCloud 设为部署输入或运行依赖；需要进入正式工程的内容必须转成 Git commit、TASK 收据或经批准的 manifest。
2. **版本通道**：代码、无密钥配置模板、migration、runbook 和部署脚本以一个私有 Git 远端的 commit/tag 为唯一版本真值。工作 Mac 只产生并推送待签候选；独立 signer 在审核后生成签名 release tag。Admin Mac 在维护窗口主动 fetch，验证不可变 commit、签名 release tag、lock/hash 和 manifest 后部署。禁止从工作 Mac 直接推送覆盖 Admin 工作目录。
3. **操作通道**：Mac/iPhone 日常通过已获批的私有 overlay 访问 Admin UI。维护时优先使用传统 macOS Remote Login/OpenSSH 叠加在 overlay 上；Screen Sharing 只作为短时、具名、可审计的图形维护通道。Tailscale SSH 在常见 macOS Standalone/App Store 版本上不能作为服务端，不能写成默认能力。
4. **数据通道**：生产 SQLite 只在专用 Admin Mac 上由一个 writer 写入；一致快照直接进入独立异机备份目标。工作 Mac、iCloud、Git 远端和 public-host 都不是主库副本、RPO 恢复点或密钥托管位置。

该方案同时满足“初配可同一局域网”和“运行期经常跨网络”：局域网只缩短首次配置路径，不形成第二套长期真值；跨网后 overlay 改变可达路径，不改变 Git release、应用认证、单写者和备份边界。

中国大陆家庭宽带、蜂窝、跨运营商、CGNAT、Tailscale direct/relay 的真实可用性仍为 `Unknown`，必须在唯一 production manifest 获批后做双端受控实测。本报告没有登录、安装、购买、创建远端、改网络或运行真实探针。

## 2. 三类模式对比

| 维度 | A 三通道 + server pull（推荐） | B 局域网初配 + 按需远程维护 | C 全目录同步/远程桌面/数据库复制 |
|---|---|---|---|
| 核心模型 | 协调、版本、操作、生产数据四类职责隔离 | 工作 Mac 通过 SSH/Screen Sharing 直接维护 Admin | 两机共享项目/运行目录，依赖 iCloud/文件同步或远程桌面长期操作 |
| 代码真值 | 私有 Git commit + 独立 signer 生成的签名 release tag + manifest/hash | 可能仍用 Git，但人工远程修改会产生未提交漂移 | 同步目录或“哪台最新”会形成时序真值 |
| 部署方向 | Admin 主动 fetch/verify/activate；工作 Mac 无生产写权限 | 维护者远程登录后直接操作；需强制只允许受控发布动作 | 双向同步、复制或人工覆盖，难证明原子性 |
| iCloud | 只在工作侧承载低风险协调文档；不进入 Admin | 可不用；若用仍限协调文档 | 承载源码、运行目录、DB 或密钥，判不适用 |
| Remote Login | 按需启用，Only these users、无 full disk access 默认值；overlay 内可达 | 主要维护入口，权限面与漂移风险较高 | 常开且常被用作人工同步补丁 |
| Screen Sharing | 默认关闭；必要时短时开启，具名用户、到期关闭回读 | 可作为 GUI 维护入口；目标离线/睡眠即不可用 | 日常依赖，带宽/延迟和人工操作成为生产关键路径 |
| SQLite | Admin 唯一 writer；只走一致快照到独立备份 | 同样必须维持单写者 | 同步活跃 DB/WAL/SHM 或两机写入，直接淘汰 |
| 密钥 | 生产运行/数据库/备份解密 key 不进入工作 Mac；release signing key 由独立 signer 控制并单独冻结 | 远程 shell 容易扩大读取面，必须再约束 | 同步目录扩大密钥复制与撤权面 |
| public-host | 只收签名只读公开投影 | 同 | 若被当同步/恢复节点则违反合同 |
| 故障隔离 | 工作 Mac 丢失可独立撤权；Admin 与备份仍分离 | 工作 Mac 凭据可能直接触达 shell/GUI | 任一误删/冲突/勒索可跨设备传播 |
| 可审计性 | commit/tag/manifest/deploy receipt 可串联 | shell/GUI 操作须额外捕获完整收据 | 文件最终状态难还原操作顺序 |
| 退出难度 | 低：撤设备/SSH key，切 Git remote，Admin 保持 last-known-good | 中：需清理人工漂移、账号和远程服务 | 高：需判定哪份文件可信、清冲突与重建 |
| 结论 | **唯一推荐** | 只作为 A 的维护子通道，不单独成为运行模型 | **排除** |

## 3. 官方事实核验

### 3.1 iCloud Drive：只能当低风险协调层

- Apple 明确说明，开启 Optimize Mac Storage 后，旧文档可能只保存在 iCloud，需要联网后下载；用户可对文件/目录选择 Keep Downloaded。[Work with folders and files in iCloud Drive](https://support.apple.com/en-gb/guide/mac-help/mchl1a02d711/mac)、[Optimise storage space](https://support.apple.com/en-au/guide/mac-help/sysp4ee93ca4/mac)，访问于 2026-08-09。
- Finder 状态可显示 In iCloud、Waiting to Upload、Out of Space、Downloaded、Keep Downloaded。Waiting to Upload 直接表示文件尚未存入 iCloud；只看到路径或文件名不能证明另一台机器已取得完整 bytes。[Check iCloud Drive status](https://support.apple.com/en-ie/guide/mac-help/mchlc994344b/mac)，访问于 2026-08-09。
- Apple 说明，多台离线设备编辑同一 iCloud Drive 文档可能产生冲突版本；保留多个版本时会加数字后缀，未选择的版本会从启用 iCloud Drive 的设备删除。[If document versions conflict in iCloud Drive](https://support.apple.com/en-gb/guide/mac-help/mh40780/mac)，访问于 2026-08-09。
- Apple 说明，同一 Apple Account 的设备间会传播删除；Desktop & Documents 的同步可在多台 Mac 开启，实际出现时间取决于互联网速度。[Desktop and Documents in iCloud Drive](https://support.apple.com/en-us/109344)，访问于 2026-08-09。

因此，iCloud 的“文件出现”不能充当提交、发布、完整性、原子部署或备份成功收据。`Keep Downloaded` 只能改善本地可用性，不能消除并发冲突、跨设备删除、上传等待或账号故障。

### iCloud 允许与禁区

| 可选允许 | 必须禁止 |
|---|---|
| 工作侧研究笔记、非敏感任务草稿、可重建截图索引、人工待办 | `.git/`、`node_modules/`、构建输出、运行目录、lock 之外的缓存 |
| 不含真实标识符/凭据的模板，且进入正式流程前转成 Git/TASK | 生产 SQLite、`-wal`、`-shm`、journal、backup staging |
| 用户自有普通文档；不得成为 Admin 运行依赖 | `.env`、token、SSH/Tailscale/Git signing key、FileVault/backup recovery material |
| | 审计主账、唯一 manifest、最后成功恢复点、public-host 投影源 |

专用 Admin Mac 现行合同禁止个人 iCloud/个人同步；本报告推荐不在 Admin Mac 登录个人 Apple Account。即使未来考虑专用组织账号，也必须另走产品、安全、用户合同，仍不得承载上述禁区。

### 3.2 Git：版本与发布身份，不是运行数据同步器

- Git 官方说明 `fetch` 下载对象与 refs，并更新 remote-tracking refs；`--atomic` 可让本地多 ref 更新全成或全败。[git-fetch](https://git-scm.com/docs/git-fetch)，访问于 2026-08-09。
- Git annotated tag 面向 release，可携带 tagger、日期、消息和可选密码学签名；`git verify-tag` 验证 tag 对象签名。[git-tag](https://git-scm.com/docs/git-tag.html)、[git-verify-tag](https://git-scm.com/docs/git-verify-tag)，访问于 2026-08-09。
- Git 官方说明托管远端与自建远端都有成本/控制权取舍；具体供应商、账号、地域、价格和中国大陆可达性不由 Git 协议文档保证。[Git on the Server summary](https://git-scm.com/book/en/v2/Git-on-the-Server-Summary)，访问于 2026-08-09。

本项目应采用“工作 Mac 产生候选 commit → 审核 → 独立 signer 新建不可变签名 release tag → Admin fetch → 验签/验 hash → staging 构建/检查 → 原子切换 → deploy receipt”的单向流程。工作 Mac 在推荐方案中不持有 release signing key；若未来改为工作 Mac 使用不可导出的硬件绑定 release key，该设备必须升级为高信任发布端，并在新 manifest 中重做丢机、撤销、轮换和信任根合同。Admin 不跟随可重写的 `latest`、浮动分支或仅凭 tag 名部署；精确 commit、tag object、签名 key version、lock/hash 和 manifest 必须同时冻结。生产运行 key、数据库/备份解密 key、日志和备份不进 Git，也不进入工作 Mac。

### 3.3 macOS Remote Login 与 Screen Sharing

- Apple Remote Login 提供 SSH/SFTP，可选择 All users 或 Only these users，并有“Allow full disk access for remote users”选项。[Allow a remote computer to access your Mac](https://support.apple.com/en-nz/guide/mac-help/mchlp1066/mac)，访问于 2026-08-09。
- Apple Screen Sharing 允许查看/控制桌面、打开文件和应用，甚至重启 Mac；可限制为具名用户。Screen Sharing 与 Remote Management 不能同时开启。[Turn Screen Sharing on or off](https://support.apple.com/guide/mac-help/turn-screen-sharing-on-or-off-mh11848/mac)，访问于 2026-08-09。
- Apple 的 Screen Sharing 排障说明要求目标 Mac 在线、不睡眠且双方网络可达；官方页面没有提供 CGNAT 穿透或中国大陆跨网 SLA。[If you can’t share Mac screens](https://support.apple.com/guide/mac-help/if-you-cant-share-mac-computer-screens-mh14070/mac)，访问于 2026-08-09。

最小使用方式：Remote Login 默认关闭或仅在批准维护窗开启，`Only these users` 精确到维护账号，full disk access 默认关闭，服务账号不可交互登录；Screen Sharing 默认关闭，只在 CLI 无法完成且用户批准的图形维护窗启用，关闭后必须回读。二者都只绑定私有 overlay 地址/接口与主机防火墙 allowlist，不能开放路由器端口、UPnP 或公网入口。传统 SSH over overlay 保留 OpenSSH key/command/账号控制，适合常见 Tailscale macOS 版本。

### 3.4 Tailscale macOS 与 Tailscale SSH 的平台边界

- Tailscale 官方列出 macOS 三种版本：Standalone、Mac App Store、开源 `tailscale + tailscaled`。三者核心联网能力相同，但打包、启动、Keychain、更新、CLI 和服务端能力不同；官方推荐从 Standalone 开始。[Three ways to run Tailscale on macOS](https://tailscale.com/docs/concepts/macos-variants)，访问于 2026-08-09。
- 官方对比表明确：App Store 与 Standalone 可作为 Tailscale SSH 客户端，但**不能作为 Tailscale SSH 服务端**；只有 macOS 开源 `tailscaled` 版本可作为服务端。开源版本无 GUI、不能从 macOS VPN 设置管理，并仅建议由有经验的 macOS 管理员用于无人值守安装。[macOS variants](https://tailscale.com/docs/concepts/macos-variants)、[Tailscale SSH](https://tailscale.com/docs/features/tailscale-ssh)，访问于 2026-08-09。
- Tailscale SSH 服务端只支持 Linux 和 macOS 开源 `tailscale + tailscaled`；启用后在 Tailscale IP 上接管 22 端口，daemon 重启会中断既有 SSH 会话。官方同时指出，可在 Tailscale 网络层之上使用传统 SSH。[Tailscale SSH limitations](https://tailscale.com/docs/features/tailscale-ssh)，访问于 2026-08-09。
- Tailscale 设备可能直连，也可能经 Peer Relay/DERP；hard NAT 组合通常走 relay。官方未承诺中国大陆目标链路质量。[Device connectivity](https://tailscale.com/docs/reference/device-connectivity)、[Connection types](https://tailscale.com/docs/reference/connection-types)，访问于 2026-08-09。

结论：本项目不能把“安装普通 Tailscale macOS App”写成“Admin Mac 已具备 Tailscale SSH 服务端”。默认候选应是 Standalone Tailscale 只提供私有网络，macOS 自带 OpenSSH 提供维护服务；若未来坚持 Tailscale SSH 服务端，就会引入 open-source `tailscaled` 无 GUI变体及额外无人值守运维责任，必须作为新候选单独冻结与验证。

## 4. 配置期拓扑：两机同一局域网

```text
M5 工作 Mac（开发/研究/审核）
  ├─ 产生 commit、测试证据、待签 release 候选
  ├─ 推送到待确认的私有 Git 远端
  └─ 不持有 release signing key、生产 DB、运行密钥或备份解密材料
           │
           ├─► 独立 signer：审核后签 release tag；不运行生产服务
           │
           │ 同网只用于首次受控配置/验收；仍需身份、hash、收据
           ▼
专用 Admin Mac（固定地点）
  ├─ 独立 service account；唯一生产 writer
  ├─ 主动 fetch 精确 release → 验签/hash → staging → 原子切换
  ├─ 私有 Admin origin；Remote Login/Screen Sharing 默认关闭
  └─ SQLite 一致快照 ──────────► 独立异机备份目标

独立 public-host ◄──── 单向签名只读公开投影 ──── Admin Mac
```

配置期角色：

- 工作 Mac：编写、审查和形成待签 release 候选；不得持有 release signing key，也不得直接写 Admin `/service`、`/config`、`/data`、`/logs`、`/backup-staging`。
- 独立 signer：只对已审核的精确 commit/tag payload 签名；其 owner、执行位置、硬件/软件形态、可导出性、签名策略、恢复、撤销与审计由 production manifest 冻结，不承载生产运行数据。
- Admin Mac：只消费已批准 release；每次变更形成旧版本、候选版本、验证结果、切换与回滚 receipt。
- Git 远端：只保存版本化源和无密钥模板；不保存生产值或运行态。
- public-host：只接收签名公开投影；不参与两台 Mac 的管理、代码真值或恢复。
- 备份目标：直接接收 Admin 一致快照，故障域和账号与两台 Mac 分离。

同网期间不得通过 AirDrop、共享文件夹、`scp` 整个项目目录或 Screen Sharing 拖文件替代 release 流程。一次方便的直传会制造无法在后续跨网运行中复现的第二部署协议。

## 5. 运行期拓扑：经常跨网络

```text
外出的工作 Mac / iPhone
   │
   ├─ 私有 overlay ──► Admin UI（Mac/iPhone 全功能 + 应用再认证）
   │
   ├─ 批准维护窗：overlay ──► macOS OpenSSH（优先）
   │                         └─► Screen Sharing（短时例外）
   │
   └─ Git push ──► 私有 Git 远端 ◄── Admin 定时或人工批准后 fetch

固定 Admin Mac ──► 异机备份目标
固定 Admin Mac ──► 独立 public-host（单向签名只读投影）
```

运行期不允许工作 Mac 充当反向代理、临时 relay、备份机、第二 writer 或 Admin 唯一恢复入口。目标 Mac 离线时，代码可以继续在工作 Mac/远端形成候选，但部署、Admin mutation 与发布必须进入可判定失败或排队状态，恢复目标机后先过 freshness、writer=1、DB/backup/readiness，再继续。

## 6. 发布、回滚与收据

### 6.1 正常发布

1. 工作 Mac 从受保护主分支产生精确 commit；CI/本地验收产出绑定 commit 的结果，并提交待签 release 候选。
2. 审核通过后，由独立 signer 创建新 annotated signed release tag；禁止移动/复用旧 tag。工作 Mac 默认无权使用 release signing key。
3. Admin 在维护窗主动 fetch 到 staging，不让远端 hook 直接执行生产脚本。
4. 验证 tag 签名、commit、允许的 signing key/version、lockfile、bundle/manifest hash、Node 版本、migration 前置和 `<15m` 最近恢复点。
5. 停止新高风险 mutation、对账在途 operation，执行 migration/构建/测试；全部通过后原子切换一个 current 指针或等价机制。
6. 启动后验证私有 Admin、writer=1、schema/ledger、RPO freshness、public 投影和公网 Admin=0；写 append-only deploy receipt。

### 6.2 回滚

- 应用失败：切回上一个已验证 release；不能用 `git reset --hard origin/main` 猜测 last-known-good。
- schema 变化：只走该 release manifest 冻结的 forward-fix/restore runbook；未证明可逆时保持停写。
- Git 远端不可达：继续运行本地 last-known-good；禁止从 iCloud、聊天附件或工作 Mac 目录直传补丁。
- 签名/hash/lock 不符：候选隔离，production 不变；轮换/撤销相关发布 key 后再处理。

## 7. Codex / DeepSeek 跨机协作规则

1. 工作 Mac 上的 Agent 可以研究、修改代码和形成候选；Admin Mac 上的 Agent 只承担受控部署检查、诊断和收据生成，不能绕过 release/manifest 直接“顺手修生产”。
2. 聊天记录、模型记忆、提示词和本地工作树都不是跨机真值。跨机交接只认 TASK JSON、Git commit/tag、固定报告路径、manifest/hash 和 append-only receipt。
3. 每个 Agent 开始前读取任务真值并检查工作树；同一文件只能有一个明确 owner。并发修改通过分支/commit 合并，禁止两端编辑同一 iCloud 文件或共享目录。
4. DeepSeek、Codex 或其他模型生成的代码都必须经过同一测试、安全与签名发布门；模型品牌不构成权限或证据等级。
5. Agent 不读取、复制、打印或提交生产 secret；需要验证 secret 时只处理引用、版本、存在性和最小权限收据。
6. Admin 上的任何远程命令/GUI 操作必须绑定 task、operator、release、started/completed time、result/reason 和回滚点；Screen Sharing 人工操作结束后补录同一粒度收据。

## 8. 失败与退出路径

| 失败 | 立即动作 | 恢复/退出 |
|---|---|---|
| iCloud Waiting to Upload、按需文件未下载或冲突副本 | 该文档不进入发布输入；保留各版本人工合并 | 转为 Git commit/TASK 后重新审查；iCloud 故障不影响 Admin last-known-good |
| 工作 Mac 丢失/被盗 | 撤销 overlay 设备、Git credential、SSH key、Admin app session/passkey；冻结新部署并保全审计 | 默认独立 signer 的 key 不在工作 Mac；新工作机从 Git/TASK 恢复后才解冻。若现场事实显示该设备曾可使用 release signing key，立即撤销/轮换该 key，Admin 继续 last-known-good；新 trust root 经 manifest/hash 批准并由 Admin 回读、旧 key 拒绝测试通过后才恢复发布 |
| Admin Mac 离线、睡眠或 overlay 不通 | 远程 mutation=0；public-host 保持 last-known-good；禁止公网旁路 | 现场/带外恢复电源网络，再过 freshness、writer、DB、backup、Admin readiness |
| Git 远端不可达或 tag/hash 验证失败 | 不部署；继续当前 release | 切换经 manifest 批准的远端或修复签名链；不得用聊天附件/iCloud补丁 |
| Remote Login/Screen Sharing 出现未知账号、full disk access 或未关闭 | 关闭远程维护与 Admin mutation，撤权并检查日志 | 恢复精确 allowlist、轮换可能暴露的 key，负例和关闭回读通过后再开 |
| Tailscale 控制面/relay/地区链路失败 | freshness 过期后关闭远程 Admin；不开放路由器端口 | 本地/现场运维，或在独立决策下验证 Headscale/WireGuard候选 |
| 生产 SQLite、WAL/SHM、密钥或备份进入 iCloud/Git/工作 Mac | 视为边界事件：停写、隔离副本、保全证据 | 按范围轮换密钥，从已验证一致恢复点重建；确认跨设备删除/传播范围 |
| 部署后应用/DB 不一致 | 停写、fence 所有候选 writer | 应用回滚或按冻结 runbook 恢复；不能让工作 Mac临时成为写主 |

### 整体退出路线

- 退出 iCloud：低风险协调文档导出到普通本地目录或任务系统；Admin 无依赖，生产无迁移。
- 更换 Git 远端：镜像完整 refs 后比对对象/签名，冻结旧远端只读，Admin 更新经批准的 remote identity；release tag 不重写。
- 更换 overlay：先建并验证新私有通道，保持 Admin 应用认证不变；撤销旧设备/ACL/key并验证不可达。迁移期间公网 Admin 仍为 0。
- 停用 Remote Login/Screen Sharing：关闭服务、回读 Sharing/监听/防火墙，并撤销对应账号/key；日常 Admin UI 不依赖它们。
- 更换工作 Mac：只恢复代码、任务和非敏感文档；生产 DB、密钥与备份继续留在各自故障域。

## 9. 最低下一决策

若用户采纳 A，下一步只需先决定以下最小集合，再由产品/安全形成唯一 production manifest 候选；本报告不替代决策：

1. 私有 Git 远端的供应商/自托管方式、账号 owner、地域、预算、可达性与退出路径；
2. release 签名格式、独立 signer 的 owner、签名执行位置、硬件/软件形态、可导出性、key version/离机恢复、丢机撤销、签名策略、tag 命名、Admin trust-root 更新和旧 key 拒绝测试；若改为工作 Mac 使用不可导出硬件 key，须明确把工作 Mac 列为高信任发布端并重审边界；
3. overlay P0/P1/P2、macOS 精确 variant、身份、设备准入、五分钟 freshness producer 与中国大陆测试窗口；
4. Remote Login 是否保留为按需维护通道；若保留，精确账号、key、允许命令、full disk access、开启/关闭 TTL 与审计；
5. Screen Sharing 是否作为短时例外；默认建议关闭；
6. 工作侧 iCloud 是否启用，以及严格允许目录；Admin Mac 默认不登录个人 Apple Account；
7. 备份目标、故障域、key 托管、保留和隔离恢复方案；工作 Mac 不作为唯一异机备份。

在这些字段、完整现行合同、不可变 manifest hash 和用户批准齐备前，真实 Git 远端、安装、登录、网络、Remote Login、Screen Sharing、Tailscale、生产部署与备份上传全部保持关闭。

## 10. 已验证、未验证与错题自检

### 已验证

- Apple 官方 iCloud Drive 的按需下载、Keep Downloaded、Waiting to Upload、跨设备删除和离线并发冲突语义。
- Git 官方 fetch/atomic refs、annotated/signed release tag 与 verify-tag 语义。
- Apple Remote Login 的 SSH/SFTP、用户 allowlist/full disk access 选项，以及 Screen Sharing 的控制能力、用户限制和与 Remote Management 互斥。
- Tailscale macOS 三变体能力差异；普通 Standalone/App Store 版本不能作为 Tailscale SSH 服务端，开源 `tailscaled` 版本才支持。
- 三类模式、唯一推荐、配置期/运行期拓扑、角色/数据流、发布/回滚、至少三条失败路径和退出路线。

### 未验证 / Unknown

- 目标两台 Mac 的精确 OS、账号、睡眠、Sharing、Firewall、Tailscale/Git 客户端版本与现状。
- 中国大陆实际宽带/蜂窝/跨运营商/CGNAT 下 overlay、Git 远端、SSH 和 Screen Sharing 的可达性、性能与长期稳定性。
- 私有 Git 供应商、账号资格、价格、数据地域、独立 signer/签名方案、Admin trust root 和保护规则；当前未创建远端或签名设施。
- iCloud 目标账号、目录、配额、同步延迟和冲突频率；当前未登录或读取账号状态。
- Remote Login/Screen Sharing 的精确监听接口约束、overlay ACL、防火墙、命令限制和真实关闭收据。
- production manifest、部署脚本、RPO/RTO、异机备份和恢复演练仍未实施。

### 错题自检

- 没有把 iCloud 当成 Git、部署协议、数据库复制、密钥托管或备份成功证明。
- 没有把同一局域网直传便利外推为长期运行模型。
- 没有把 Tailscale macOS 客户端存在外推为 Tailscale SSH 服务端支持。
- 没有把 Screen Sharing/Remote Login 开启写成公网可用或安全；二者仍需 overlay、账号、应用与失败关闭门。
- 没有让工作 Mac、iCloud、Git 或 public-host成为生产 SQLite 第二 writer 或 RPO 恢复点。
- 没有混同生产运行/数据库/备份解密 key 与 release signing key；推荐方案的工作 Mac 只提交待签候选，签名由独立 signer 执行。
- 没有把中国大陆可达性写成已证实。
- 没有登录、安装、购买、改网络、创建 Git 远端、运行真实探针或修改 Spec/ADR/app/data。
