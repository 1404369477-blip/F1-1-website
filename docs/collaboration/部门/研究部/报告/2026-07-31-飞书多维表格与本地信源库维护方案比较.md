# 飞书多维表格与本地信源库维护方案比较

## 一、结论摘要

本报告只提供可选方案、证据和边界，不替用户确定最终路线。

用户已确认的约束只有两项：当前由用户一人维护；刷手机内容时要能随时快速新增。任务验收同时要求混合方案声明唯一业务真值和冲突处理，这是架构完整性边界。

“新增项先进入待验证收件箱”是研究部基于来源身份尚未核验所提出的风险控制建议，尚未获得用户确认。本报告保留该能力分析，但不把它写成用户需求，也不让它主导矩阵排序。基于上述边界，四个可选方案为：

1. **A｜飞书多维表格为单一业务真值**：移动录入最直接；若用户采用候选隔离建议，也可在同一数据表内完成，采集器在线读取飞书。
2. **B｜Git 版本化 JSONL 文件为单一业务真值**：审计、可移植性和采集器读取简单，手机录入摩擦最高。
3. **C｜SQLite 为单一业务真值**：约束、查询和批处理最强，要满足手机录入需额外建设服务与界面。
4. **D｜飞书为单一业务真值，本地为只读版本化副本**：移动端仍写飞书，采集器读本地最后一次成功快照；同步严格单向，禁止本地反写。

按重新校正后的公开权重计算，D 为 90.8/100，A 为 88.6/100，B 为 71.6/100，C 为 67.8/100。待验证建议只占 5 分；完全移除这项并把其余维度归一化后，排序仍为 D 90.3、A 88.0、B 72.2、C 67.2。这个排序不构成最终选择。D 比 A 多出本地同步和凭证维护；A 比 D 更省维护，但飞书/API 故障会直接影响采集器读取。

当前资料 `F1+1信源.md` 实际是 RTF 文件，扩展名虽为 `.md`。本地检查提取到 59 个 `x.com/<handle>` 链接核心；去掉查询参数后有 59 个唯一项。账号身份、来源可信度与是否应启用均未验证。研究部建议迁移时先隔离为候选并复核，是否采用该门禁需用户确认。

## 二、范围、证据等级与术语

### 2.1 本次范围

- 比较信源的快速新增、批量删改、身份复核、证据溯源、变更历史、自动采集系统读取、备份恢复、权限、直接费用和维护成本。
- 核验飞书官方产品能力、开放平台能力与本机 `/opt/homebrew/bin/lark-cli` 的只读可行性。
- 不创建、修改、删除或提交任何真实飞书资源。
- 不验证 59 个 X 账号的真实身份与质量。

### 2.2 证据等级

- **官方事实**：飞书帮助中心、飞书开放平台、Git 或 SQLite 官方文档可直接支持。
- **本机实测**：本机文件与 CLI 的只读命令输出。
- **工程推断/方案设计**：根据已确认能力设计的使用方式，仍需原型或真实账号复测。
- **unknown**：当前官方公开材料或本机只读环境不足以确认。

### 2.3 单一业务真值

单一业务真值指：某条信源是否存在、是否通过身份验证、是否启用、证据是什么，只能在一个权威位置修改和裁决。缓存、导出、快照可以存在，但必须满足：

- 有明确生成方向；
- 禁止人工修改后反向覆盖权威数据；
- 冲突时无条件由权威位置胜出；
- 可丢弃并从权威位置全量重建。

## 三、从第一性原理拆解业务流

信源库需要完成五个动作。以下第 2、3 步的验证门禁是研究部建议，是否采用仍待用户确认：

1. **捕获**：手机上只要求记录原始 URL，备注可选，减少录入摩擦。
2. **验证**：若用户确认采用验证门禁，核对规范 URL、平台账号 ID、显示名、身份/官方关系和证据链接。
3. **发布**：由用户确认的 `publish_predicate` 决定哪些记录可供采集器读取。
4. **退役**：优先停用或标记拒绝，保留原因；确认无需审计后再硬删除。
5. **恢复**：误删、云端不可用、同步失败时，能恢复最后一份满足 `publish_predicate` 的正确采集集合。

研究部建议把验证状态与启停状态拆成两个正交字段；它仍是待用户确认的设计项：

```text
verification_status: 待验证 -> 已确认 | 已拒绝
enabled: false <-> true
已停用 = verification_status=已确认 且 enabled=false
```

`已拒绝`记录建议暂时保留规范 URL 与理由，用于阻止重复录入。若有隐私或数据最小化要求，再按保留期硬删除。

本报告用 `publish_predicate` 统一指代“进入采集集合的生效条件”：

- 若用户确认研究部的验证门禁建议，`publish_predicate = verification_status=已确认 AND enabled=true`。
- 若用户不采用该建议，必须先由用户另行确认手机新增是否立即生效及 `enabled` 的含义；实施前不预设另一套条件。
- A、B、C、D 的采集读取、快照发布、故障阻断和迁移切换都应引用 `publish_predicate`，禁止在各组件内分别硬编码。

## 八、权重与决策矩阵

### 8.1 评分方法

- 1 分：当前形态严重不满足，需要额外系统才能补齐。
- 3 分：可满足，但有明显人工步骤、凭证或维护成本。
- 5 分：直接满足，边界清楚且日常摩擦低。
- 加权分 = `该项权重 × 得分 / 5`，总分 100。

全部权重和 1–5 分均为研究部工程判断，用于显式比较，不属于用户陈述或真实产品实测结果。关键评分依据是：A/D 的移动端 5 分来自官方表单链接直接入表能力；B/C 的 1 分反映它们在不另建入口时无法自然满足手机快增；C 的候选隔离 4 分来自数据库查询/约束能力，但仍缺管理界面；D 的自动读取 5 分是“完成只读同步后”的条件分，当前尚未实现。

矩阵只把“单人维护 + 手机随时快速新增”当作用户事实。单一业务真值是任务要求的架构边界。候选隔离/待验证流程是研究建议，只占 5 分；未来若用户接受、拒绝或调整该流程，应重新评分。

| 维度 | 权重 | A 飞书真值 | B Git 文件真值 | C SQLite 真值 | D 飞书真值 + 本地只读副本 |
|---|---:|---:|---:|---:|---:|
| 手机快速录入（用户已确认） | 25 | 5 | 1 | 1 | 5 |
| 单一业务真值清晰度（任务边界） | 20 | 5 | 5 | 5 | 5 |
| 候选隔离/待验证流程（研究建议） | 5 | 5 | 3 | 4 | 5 |
| 自动采集读取与可用性 | 12 | 4 | 5 | 5 | 5 |
| 溯源与长期审计 | 10 | 4 | 5 | 3 | 4 |
| 批量删改、查重与校验 | 8 | 4 | 3 | 5 | 4 |
| 备份、恢复与退出路径 | 7 | 3 | 5 | 4 | 4 |
| 单人维护负担（用户已确认） | 8 | 4 | 3 | 2 | 3 |
| 直接费用、权限与凭证门禁 | 5 | 4 | 5 | 4 | 4 |
| **加权总分** | **100** | **88.6** | **71.6** | **67.8** | **90.8** |

### 8.2 敏感性

- 若手机录入权重从 25 显著下降，B 会快速接近 A/D。
- 若用户不采用候选隔离/待验证流程，删除该 5 分维度并将其余维度归一化后，D/A/B/C 分别为 90.3/88.0/72.2/67.2；排序没有依赖这项未确认建议。
- 若要求采集器在飞书临时不可用时继续工作，D 的优势扩大。
- 若拒绝维护任何 API 凭证，A/D 的自动化分应下降，B 的相对位置上升。
- 若来源规模达到数万、需要复杂约束和高频查询，C 的批处理与完整性优势会扩大。
- 若当前账号无法低成本取得 Base API 授权，A 只能先做人工作台，D 暂时无法落地同步。

## 九、四个方案详解

### A｜飞书多维表格为单一业务真值

**真值位置**

一张 Base 数据表保存所有业务字段。表单和不同视图只是同一数据源的入口与展示。若用户确认候选隔离建议，再增加待验证与已确认视图。

**日常流程**

1. 手机打开表单链接，粘贴原始 URL 并提交。
2. 若用户确认候选隔离建议，新记录进入 `待验证` 视图；状态空值也可按待验证处理，避免依赖自动化额度。
3. 在桌面端补规范 URL、账号 ID、证据、验证时间。
4. 若启用验证门禁，通过后设置 `已确认 + enabled=true`；拒绝时记录理由。若不启用，需另行确认手机新增是否立即生效。
5. 采集器按用户确认的生效条件查询记录。

**增删改与批处理**

- 人工：在筛选视图内批量停用、改状态或删除。
- 程序：CLI/API 可查、增、改、删；同表写请求需串行。CLI 当前批量创建限制为 200 行/次。
- 去重：以 `canonical_url` 为业务查重键，写前先查询；Base 未在本次核验中确认数据库式唯一约束，不能只依赖人工目测。

**溯源与审计**

- 使用自动创建人/修改人/时间字段和记录历史。
- 记录历史保留期与导出缺口要求把证据 URL、判断、时间写进业务字段。
- 批量删除前先导出或改为停用；硬删除会削弱长期拒绝/退役审计。

**自动化与冲突**

- Collector 每次从 Base 读取，Base 为唯一裁决点。
- 任何 API 写入都携带 `source_id` 和规范 URL，按表串行。
- 读取端遇到 API 或鉴权失败时，不得用空结果覆盖有效配置；A 方案应停止本轮采集并报警。

**恢复**

- 利用 Base 历史版本整体还原。
- 定期人工导出 `.base` 加 CSV；导出文件不包含历史与评论。
- 恢复演练需验证字段、视图、启用状态与采集器查询，而不只检查文件能导入。

**费用与维护**

- 当前 59 条规模低于相互冲突的两种官方公开容量口径；精确权益仍需在目标账号核验。
- 主要隐性成本是租户/自建应用/用户授权、token 更新、导出纪律和平台依赖。

**适用条件**

- 追求最快落地和最低手机摩擦；
- 接受采集器实时依赖飞书 API；
- 能取得并维护所需权限；
- 以人工导出补足灾备。

### B｜Git 版本化 JSONL 文件为单一业务真值

**真值位置**

项目仓库中的 UTF-8 `sources.jsonl` 与 JSON Schema。每行一条信源，提交历史保存变更。当前 RTF 文件只保留为迁移原件。

**日常流程**

- 桌面：编辑结构化文件，运行 schema/唯一性校验，提交 Git。
- 手机：纯文件方案需要移动 Git 客户端、仓库网页编辑或额外捕获入口；均增加登录、定位文件、提交等步骤。
- 若另设飞书表单作为手机临时收件箱，它只充当只追加传输队列，不能裁决某条信源是否存在或生效；Git 仍是唯一业务真值。手机网关若能直接创建 Git 提交/PR，也可不持久化第二份队列。

**临时收件箱的单向交接协议（仅在用户选择该入口时启用）**

1. 每次投递生成 `candidate_id`；以 `platform + canonical_url` 的规范化哈希作为业务幂等键。
2. 导入器只执行 `收件箱 -> Git`，禁止 Git 业务状态反向覆盖收件箱字段。
3. 校验通过后创建或更新同一 Git 记录，并把 commit SHA 作为交付确认；重复投递命中同一幂等键，不生成第二条业务记录。
4. 失败项保留错误和重试次数，可安全重放；成功项标记已确认交付，不静默删除。
5. 定期全量对账“未确认交付记录、Git 中的幂等键和 commit SHA”；Git 对存在、验证、启用和拒绝状态拥有最终裁决权。
6. 队列只对“投递是否已交付”负责；在写入 Git 前，它不构成信源业务记录，也不可供采集器读取。

**增删改与批处理**

- 单条编辑可直接改 JSONL；批量规范化、停用与查重用脚本完成。
- CI 或本地校验应检查 schema、`source_id`/`canonical_url` 唯一、状态枚举、已确认记录的证据完整性。
- CSV 对嵌套证据与历史字段表达较弱；YAML 人工可读性高但解析细节更多。当前规模下 JSONL 更易流式处理和逐行 diff。

**溯源与审计**

- Git 记录文件变化、作者和提交信息，可比较版本并恢复。
- Git 提交不能证明账号身份，证据仍要保存在记录字段中。
- 手机临时收件箱的传输历史与 Git 历史分离，交付确认需记录 `candidate_id`、幂等键和 commit SHA。

**自动化与冲突**

- 采集器直接读取固定 commit 或部署产物，无云 API 凭证。
- 当前单人维护时冲突少；未来多写者会出现文本合并冲突。
- 发布前以原子文件替换，避免采集器读到半写状态。
- 使用临时收件箱时，导入器按幂等键串行提交并周期性全量对账；失败重试不能改变 Git 的最终裁决。

**恢复**

- Git 可比较和恢复历史；应配置至少一个异地私有远端或离线备份。
- 单一本地仓库仍是单点，Git 历史不能替代异地备份。

**费用与维护**

- 本地软件直接费用低；远端私有仓库、移动端工具和捕获网关可能产生服务或时间成本。
- 最大日常成本是手机录入和把候选同步进真值。

**适用条件**

- 可移植、可审查文本和无运行期云凭证优先；
- 手机录入频率不高，或愿意接受候选收件箱到 Git 的人工导入；
- 采集器与仓库部署流程已成熟。

Git 官方说明版本控制可记录文件变化并恢复特定版本，分布式克隆包含完整历史；这仍要求正确的远端和备份策略。来源：[关于版本控制](https://git-scm.com/book/zh/v2/%E8%B5%B7%E6%AD%A5-%E5%85%B3%E4%BA%8E%E7%89%88%E6%9C%AC%E6%8E%A7%E5%88%B6.html)、[git diff](https://git-scm.com/docs/git-diff.html)。

### C｜SQLite 为单一业务真值

**真值位置**

受控 SQLite 数据库；schema/migration 放进 Git。`sources` 表存当前状态，`source_events` 以追加方式保存业务事件。

**日常流程**

- 桌面或采集器经受控 CLI/管理界面写入。
- 手机随时录入需要额外 Web 表单/API、TLS、鉴权和可访问的运行环境；纯本地 SQLite 无法满足该约束。
- 若用户确认候选隔离建议，可由 SQL 查询形成待验证列表，但还需要可用的人机界面完成复核。

**增删改与批处理**

- 可通过唯一索引强制 `source_id` 和 `canonical_url` 唯一。
- 事务内完成状态修改、事件追加与批量停用，数据完整性强。
- 删除策略可用外键与事件表约束；高风险硬删除可要求二次确认。

**溯源与审计**

- SQLite 本身保存当前数据；长期业务审计要显式设计 `source_events`，不能依赖数据库文件修改时间。
- 数据库文件为二进制，直接放进 Git 的 diff 审核价值低；Git 应保存 schema、迁移与确定性导出快照。

**自动化与冲突**

- 同机采集器可直接只读查询，性能与过滤稳定。
- SQLite 支持多个并行读取和单一写事务；写者需序列化，处理 `SQLITE_BUSY`。
- 不应让多个设备通过普通网盘同步一个正在使用的数据库文件。

**恢复**

- 使用 SQLite Online Backup API、`VACUUM INTO` 或静止状态复制，生成一致快照。
- 直接在活跃事务期间复制单个数据库文件可能产生损坏备份；WAL/日志文件也必须按官方规则处理。
- 定期运行完整性检查和恢复演练，并保存异地快照。

**费用与维护**

- SQLite 本身无需单独服务；手机入口带来托管、证书、鉴权、监控和安全更新成本。
- 对 59 条记录而言，完整自建管理服务的复杂度较高。

**适用条件**

- 唯一约束、事务、复杂查询与批处理的重要性高；
- 已有可复用的安全 Web 服务和移动入口；
- 愿意承担服务运维与备份演练。

SQLite 官方说明事务具备 ACID 特性、多个读取与单一写事务；活库备份应使用一致性方法。来源：[SQLite 事务](https://sqlite.org/lang_transaction.html)、[Online Backup API](https://www.sqlite.org/backup.html)、[损坏与安全备份](https://www.sqlite.org/howtocorrupt.html)。

### D｜飞书为单一业务真值，本地为只读版本化副本

**真值位置**

业务状态只在 Base 修改。同步程序按用户确认的生效条件生成本地 `sources.snapshot.json`；若采用验证门禁，条件为 `已确认 + enabled=true`。当前 59 条规模无需先引入 SQLite。若未来查询需求扩大，可将同一快照构建为 SQLite 只读模型。

**日常流程**

1. 手机通过 Base 表单提交候选。
2. 若用户确认候选隔离建议，在 Base 待验证视图完成身份复核和启停裁决；若不采用，按另行确认的生效条件维护。
3. 单向同步读取符合生效条件的记录，校验 schema/唯一性后生成临时快照。
4. 只有全量校验通过才原子替换 `last-known-good` 快照并记录同步时间、Base 记录 ID、校验和与记录数。
5. 采集器只读本地快照；快照过期时报警并标记数据新鲜度。

**增删改与批处理**

- 所有业务写入只在 Base 完成。
- 本地副本设置只读或在 CI 中检查“只允许生成器修改”。
- 手工改本地文件的内容在下次同步被覆盖，且禁止反向上传。

**溯源与审计**

- Base 字段与历史保存业务判断；Git 快照显示“已发布给采集器的集合如何变化”。
- Git 快照是发布记录，不能代替 Base 的业务证据。

**自动化与冲突**

- 简化起步：按采集周期前置拉取，或每日/按需拉取；无需消耗 Base 内部自动化额度。
- 低延迟阶段可订阅记录变更事件，但事件只触发同步；每次仍从 Base 读取当前值。
- 定期全量对账修复漏事件、token 失效或局部同步错误。
- 冲突规则固定为 `Base wins`，本地永远不参加业务裁决。

**故障策略**

| 故障 | 行为 |
|---|---|
| Base/API 暂时不可用 | 保留上一份通过校验的快照；采集器继续读，并暴露 `snapshot_age` 告警。 |
| token 失效/权限不足 | 同步失败，不覆盖快照；要求重新授权后全量对账。 |
| 返回缺页/记录数异常 | 视为校验失败，不发布新快照。 |
| 准备写入发布快照的结果出现重复规范 URL、schema 失败，或混入不满足 `publish_predicate` 的记录 | 阻断整版发布并输出冲突记录 ID，回 Base/同步查询处理。正常不满足条件的记录只应在查询阶段被排除；缺证据只在用户采用验证门禁时属于阻断条件。 |
| 本地快照被手改 | 校验和失败；从 Base 全量重建，不反写。 |
| Base 误删 | 先用 Base 历史还原；必要时用最近 `.base` 或覆盖全部业务记录的独立备份受控重建。运行发布快照只含采集集合，不能恢复候选、拒绝、停用记录或完整审计字段。 |

**恢复**

- 日常读取依赖 last-known-good 发布快照；它只负责恢复采集器运行白名单。
- 完整业务恢复依赖定期 `.base` 导出，以及按需覆盖全部记录的 CSV/JSON 独立备份；版本化发布快照不能替代这类备份。
- 全量同步必须具备临时文件、schema 校验、计数/唯一性检查、原子替换和回退。

**费用与维护**

- 继承 A 的账号/权限成本；额外增加一个只读同步作业与凭证轮换。
- 相比 C，无需建设手机 Web 服务；相比 A，增加同步代码与监控。

**适用条件**

- 手机快速捕获优先；候选隔离流程是否采用由用户另行确认；
- 采集器需要在飞书短暂不可用时继续使用已发布集合；
- 能维护最小权限的只读凭证和一个单向同步作业；
- 接受 Base 是唯一业务写入口。

## 十、手机录入摩擦专项比较

| 方案 | 手机最短路径 | 候选隔离落点（研究建议） | 主要摩擦 | 需实测 |
|---|---|---|---|---|
| A | 复制链接 -> 打开表单 -> 粘贴 -> 提交 | 若采用：同一 Base 的待验证视图 | 首次定位表单；网络/登录/分享范围 | iOS/Android 实际点击数、X 分享菜单、弱网、重复提交 |
| B | 打开移动 Git/仓库网页 -> 找文件 -> 编辑 -> 提交；或先投递临时表单 | 若采用：Git 候选记录；临时表单只算候选 | Git 登录、结构化编辑、提交；临时收件箱还需导入 | 可用的移动 Git 工具、私有仓库权限、导入耗时 |
| C | 打开自建 Web 表单 -> 提交 | 若采用：SQLite `pending` 查询 | 需先建安全可访问服务 | TLS、鉴权、离线重试、手机兼容、安全测试 |
| D | 与 A 相同 | 若采用：同一 Base 的待验证视图 | 同步延迟只影响采集器发布，不影响录入 | A 的手机项 + 快照发布时间与过期提示 |

表单的产品能力已有官方证据；“收藏到飞书常用/手机桌面后能达到多少秒”属于工程体验假设，必须由真实设备测试。

| 日常人工 | 验证、导出 | 验证、提交、移动候选导入 | 验证、服务运维 | 验证、导出、监控同步 |
| 平台锁定 | 中 | 低 | 低 | 中，因有可移植快照而降低退出成本 |
| 中国大陆个人非商业项目门禁 | 租户、自建应用、审批与授权需实测 | 私有远端与移动客户端可达性需选择 | 公网托管、域名/证书与安全责任 | 同 A，并增加 runner 可达性 |

公开材料能确认功能额度，无法据此确认当前个人账号的全部成本、租户/管理员流程与未来价格。任何付费或企业主体要求应在真实账号内确认后再进入实施。

## 十二、迁移路径与回滚

以下步骤只描述方案，不在本任务中执行：

1. **冻结原件**：保留当前 RTF 原文件及哈希，禁止直接覆盖。
2. **确定字段合同**：先确认第七节最小字段和状态枚举。
3. **机械提取**：提取 59 个 URL，保留 `raw_url`，生成去参数的 `canonical_url`；记录解析异常。
4. **用户门禁**：用户确认是否采用候选隔离/待验证流程。研究部建议新导入项先不启用，并写入 `migration_batch_id`；若用户不采用，切换前仍需显式批量复核。
5. **身份复核**：逐条核对账号身份、稳定账号 ID与证据；拒绝项保留理由。
6. **影子读取**：新读取路径只生成影子快照，与原有列表比对数量、规范 URL 和启用集合，不切换采集器。
7. **切换**：用户确认 `publish_predicate` 后，采集器只读取满足该条件的记录；保留旧路径作为短期回滚输入。
8. **恢复演练**：模拟误停用、误删、权限失效、缺页、重复 URL 和快照损坏。
9. **退出路径**：A/D 至少保留 `.base` 与 CSV；B 保留异地 Git；C 保留一致 SQLite 快照与确定性导出。

### 12.1 各方案的最小迁移差异

- A：RTF -> CSV -> Base；用户确认候选隔离建议后才配置待验证视图，表单始终保持薄录入。
- B：RTF -> JSONL；先通过 JSON Schema 和唯一性检查，再提交 Git。
- C：RTF -> staging CSV -> 单事务导入 SQLite；建立唯一索引和事件记录。
- D：先完成 A；随后只读同步生成首个 last-known-good 快照，确认校验和后再让采集器读取。

## 十三、选择条件，不代替用户拍板

- **选择 A 的条件**：最短上线时间优先；可接受飞书在线依赖；愿意定期人工导出；已确认账号与 API 权限。
- **选择 B 的条件**：Git 可审查性、可迁移性和无运行期飞书凭证优先；可接受手机候选到真值之间的额外步骤。
- **选择 C 的条件**：唯一约束、复杂查询、批处理和事务成为主要需求；已有安全的移动 Web 服务或愿意建设。
- **选择 D 的条件**：手机入口保持飞书优势，同时要求采集器在短时 API 故障下继续使用最后正确集合；愿意维护单向同步。候选隔离体验是可选设计项。

当前矩阵只将 A/D 识别为高分短名单。这个结果在删除待验证建议的权重后保持不变。用户仍需在“更少维护”与“采集读取韧性”之间选择，并另行确认是否采用候选隔离/待验证流程；选择前应先完成真实账号只读授权与手机表单体验复测。

## 十四、已验证、未验证与错题自检

### 14.1 已验证

- 本机原始信源文件类型、59 个唯一 X 链接和当前字段缺口。
- 飞书官方表单、移动填写入口、视图筛选、CRUD API、记录历史、导出、自动化额度和事件订阅；同时确认官方容量口径存在冲突。
- 本机 `lark-cli 1.0.68`、`lark-base 1.2.2`、相关命令面、风险标记和 CLI 批量上限。
- 本机离线诊断能找到配置，但当前沙箱无法读取钥匙串。
- Git 版本记录/恢复的官方说明；SQLite 事务与一致备份的官方说明。
- 四方案均声明了唯一业务真值，D 的同步方向为 Base -> 本地只读副本。
- 已按统筹纠正把待验证收件箱降级为研究建议/待用户确认，并重算矩阵；删除该维度后排序不变。

### 14.2 未验证 / unknown

- 用户是否采用候选隔离/待验证收件箱，以及手机新增是否可以立即进入采集集合；当前仅有研究建议。
- 当前飞书账号、租户、自建应用、用户身份 scope 与目标 Base 的真实授权状态。
- 中国大陆个人非商业项目在当前账号下的全部免费权益、管理员审批要求和后续价格。
- 真实 iOS/Android 手机上从 X 内容到表单提交的点击数、耗时、弱网与重复提交行为。
- 当前账号能否调用记录历史、表单、workflow 与事件订阅 API；本次未连接真实资源。
- Base 历史记录公开 API 的当前细节：[官方权限列表](https://open.feishu.cn/document/server-docs/application-scope/scope-list)可见 `base:history:read`，本机 CLI 暴露单记录历史命令，但未做账号级调用。
- 59 个 X 来源的身份、可信度、证据、当前有效性与启用决策。
- 去除跟踪参数后的平台重定向、handle 改名、账号 ID 取得和重复判定规则。
- D 的同步程序、缺页保护、凭证轮换、原子替换、全量对账和采集器回退尚未实现或测试。
- A/D 的 `.base` 导出与恢复尚未用真实资源演练；导出任务只能在用户授权后进行。

### 14.3 错题自检

项目错题集当前没有可匹配的既有错题条目。本任务按失败路径额外检查：

- 没有把 CLI 安装等同于账号或资源已授权。
- 没有创建、修改、提交或删除真实飞书资源。
- 没有使用第三方营销文章替代飞书官方能力证据。
- 没有把 Base 历史、Git 提交或数据库时间戳当作账号身份真实性证据。
- 混合方案只有 Base 一个业务写入口，本地副本不参与冲突裁决。
- 对具体个人账号费用、企业主体/租户门禁、手机体验和历史 API 保持 unknown。
- 报告给出四个方案和适用条件，保留用户最终选择权；待验证流程没有写成用户已确认事实。
