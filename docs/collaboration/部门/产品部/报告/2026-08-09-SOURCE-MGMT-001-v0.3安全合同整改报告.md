## 3. P1-1整改：raw authority、session、CSRF

v0.3 已冻结以下 MUST：

1. **Raw HTTP gate**：HTTP/1.1-only；framework规范化前保存raw request-target和header multiplicity；只允许origin-form、单一exact Host和单canonical loopback authority。
2. **拒绝矩阵**：duplicate/comma/missing Host、Host+`:authority`、absolute-form、raw/normalized不一致、HTTP/2/h2c、proxy headers和非loopback peer均在session/nonce/业务写前拒绝。
3. **Origin**：mutation、session create/refresh/destroy及CSRF issue必须有唯一exact Origin；Admin GET无Origin可只读，存在Origin仍须exact match；CORS allow header=0、OPTIONS=405。
4. **Session**：进程启动由系统CSPRNG生成32-byte、43字符base64url无paddingID；单ACTIVE、仅内存、host-only HttpOnly SameSite=Strict、absolute 30m、idle 10m、refresh轮换、重启失效。
5. **CSRF**：服务端CSPRNG生成32-byte token；绑定session+uppercase method+exact path+canonical body SHA；TTL 300秒、capacity 32；issued→consumed原子单向转换，并发仅一请求成功，失败/rollback不恢复。
6. **Zero delta**：任何raw/session/CSRF/no-egress拒绝前后，Source、receipt、Outbox、TaskEnvelope、Inbox、Attempt、DeadLetter、domain AuditEvent和provider调用增量均为0；最多一条脱敏security audit。

对应mandatory：`SRC-V3-RAW-01` 至 `SRC-V3-SEC-ZERO-05`。

## 4. P1-2整改：identity生成、编码、碰撞与复用

唯一identity合同：

| 域 | Owner | 随机输入 | Canonical格式 | 长度 |
|---|---|---:|---|---:|
| command operation | 可信UI Web Crypto | 32 bytes | `op-cmd-` + 64小写hex | 71 |
| command key | 可信UI独立Web Crypto调用 | 32 bytes | `cmd-key:` + 64小写hex | 72 |
| business operation | 首次/新activation事务内Node crypto | 32 bytes | `op-srcact-` + 64小写hex | 74 |
| business key | 同事务独立Node crypto调用 | 32 bytes | `srcact-key:` + 64小写hex | 75 |
| job id | 同事务独立Node crypto调用 | 32 bytes | `job-srcact-` + 64小写hex | 75 |
| task id | 同事务独立Node crypto调用 | 32 bytes | `task-srcact-` + 64小写hex | 76 |
| live lease | 每次acquire/retry事务内Node crypto | 16 bytes | `synthetic:lease:` + 32小写hex | 48 |

规则已经闭合：

- command请求顺序唯一为：冻结不含command的业务/expected输入→独立生成command pair→组装完整DTO→canonical-json-v1得到最终bytes/body hash→申请绑定method/path/hash的CSRF→提交逐字相同bytes；任何输入、identity或serialization变化都丢弃未消费nonce并重走全链。
- 每个域独立CSPRNG调用；禁止Math.random、时间、计数器、跨域复用与identity派生。
- 服务端只验证codec/prefix/length/binding/UNIQUE，不宣称可以验证客户端熵。
- 客户端不得提交business/job/task/lease字段；unknown字段在业务事务前拒绝。
- command receipt是command与business域的唯一桥；Source/Outbox/TaskEnvelope只使用business identity，command事务与worker AuditEvent分别使用command operation和business operation/task，禁止跨列复用。
- command同scope/body响应丢失时逐字复用；operation/key的交叉绑定冲突固定409并零业务写。
- business/job/task整组碰撞最多重新生成3组；耗尽或CSPRNG失败返回固定500并整笔rollback。
- live lease碰撞最多重生3次；耗尽时acquisition rollback，attempt不增加、adapter不运行。
- stopped/queue_failed/dead-letter使用新command pair并复用business/job/task，取得新lease；cancelled后新activation生成全新server-owned整组。
- 原business identity缺失、重复、codec错误或绑定不一致固定409并零写，不自动生成替代identity。

v0.3 还给出七组逐字fixture vector与全部codec/owner负例；对应mandatory为 `SRC-V3-ID-CODEC-06` 至 `SRC-V3-ID-CONCURRENCY-10`。

## 5. P2整改：source_id碰撞

v0.3 保留96-bit source_id公式，同时增加完整SHA-256判别：

- prefix和full hash均相同：`ADMIN_SOURCE_ALREADY_PROPOSED`，返回只读current ref，零业务增量；
- 96-bit prefix相同但full hash不同：`ADMIN_SOURCE_ID_COLLISION`，整笔零写；
- canonical URL与其他Source冲突：独立 `ADMIN_SOURCE_CANONICAL_CONFLICT`；
- 禁止自动salt、后缀、扩位、覆盖或第二Source；
- 用户只能核对现有Source，修改synthetic canonical path或platform，重新生成command pair/CSRF后明确提交。

对应mandatory：`SRC-V3-SOURCE-ID-11`。未来若扩展到真实、不可信或高规模输入，必须另建successor重新评估位数。
