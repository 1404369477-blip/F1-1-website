## 2. 已落实的用户出口

### 2.1 身份与会话

- 无有效会话时显示通行密钥登录；首次配置入口要求 43 字符一次性 bootstrap token。
- WebAuthn 创建/获取凭据使用浏览器原生能力；不支持或用户取消时保持关闭并给出明确状态。
- 登录、首次注册、发布前 fresh re-auth 均只调用同源 Admin 服务。
- `401` 返回登录出口；服务未确认会话、CSRF 或 fresh receipt 时不开放写入。

### 2.2 审核与编辑

- 队列支持搜索、刷新、候选状态、来源与时间；详情显示来源快照、原文链接、证据、来源版本、Bundle 与投递状态。
- 中文标题、中文摘要、私有备注可编辑并保存为新 revision；来源或 Bundle CAS 变化交由服务端以 `409` 拒绝覆盖。
- revision 只发送 `detail.integrity.versionTag` 对应的 12 位 `expected.sourceVersionTag`；UI 不接收、不显示、不推断 64 位 `sourcePayloadHash`。
- 完整性阻断、来源更新、未知状态均 fail closed。

### 2.3 决定、发布与对账

- `approve`、`reject` 使用独立确认；拒绝原因必填。
- 批准只记录当前 Bundle 决定与预留 Publication；批准完成后才出现独立 `manual publish`。
- 发布顺序固定为：fresh options 携带完整 `PublishRequest` → WebAuthn → fresh verify 携带同一 mutation → 接收旋转 cookie 与 fresh receipt → 用同一 mutation 申请 CSRF → publish 同时携带 `x-csrf-token`、`x-f1-fresh-reauth`。
- mutation 网络结果未知时保留同一 `operationId`，提供读取同一 operation 的对账出口；投递未确认时只读取同一候选/delivery 状态，不创建第二次发布。
- `409` 提供加载最新状态；`503` 保留当前输入并阻止写入；无 synthetic 自动回退。

## 3. 真实默认与 fixture 边界

无查询参数的正式入口始终实例化 `RealAdminAdapter`。验收 fixture 只有同时满足以下条件才启用：

1. URL 显式携带 `fixture=review-ui-v1`；
2. 页面来源为 `file:` 或 `127.0.0.1`、`localhost`、`::1`；
3. 页面持续显示“验收 Fixture / 当前页面没有连接真实 API”警告。

截图里的标题、摘要、来源、Bundle、Publication、状态与投递均为 synthetic 浏览器内存样本。它们只用于验证正式 HTML/CSS/JS 的渲染和用户出口，不构成真实 RSS、真实会话、真实写入或已发布内容证据。
