# F1资讯聚合产品体验与信息架构基准研究

## 0. 结论先行

本轮以桌面 1280×900 与手机 390×844 的公开视图为主，比较了 9 个产品／项目：Formula 1 官方、Motorsport.com、Autosport、RacingNews365、The Race、ESPN F1、BBC Sport F1、AI Hot、Google News。页面内容和组件会随时间变化，以下结论是 2026-08-02 的可见快照，不代表各站完整产品合同或后台实现。

对 F1+1 最有价值的输入有五项：

1. 把“少量精选”和“完整时间流”分成两个阅读速度层，避免首屏既要追热点又要查全量。
2. 把来源、作者、原发布时间、系统发现时间、摘要状态和原始链接放进同一条证据链，来源可信度可被快速判断。
3. 在赛事期间提供轻量事件上下文（下一场、时间、结果／积分入口），上下文服务阅读，不抢占信息流主任务。
4. 详情页采用“中文提炼 → 相关来源／事件 → 原始信源”的阶梯；这与 F1+1 当前详情合同一致。
5. 手机端优先保留标题、来源、时间、摘要和操作，首图可选；筛选、长表格、外部媒体和第三方嵌入必须有降级出口。

本报告只形成研究证据，不修改 [F1+1 Spec](../../../../spec.md) 或 [全站设计规范 v0.1](../../../../../design/ui/F1+1-全站设计规范-v0.1.md)。精选／全量双层信息流、赛事数据模块、评分、已读／收藏、社交嵌入等若要进入产品，需要统筹部另行确认，不因参考站存在而自动扩大 MVP。

## 1. 研究方法、证据等级与使用边界

### 1.1 方法

- 通过 Codex 内置浏览器，只读打开公开 URL；没有登录、搜索历史读取、提交、关注、评论、反馈、收藏写入或其他外部副作用。
- 每个样本先看桌面公开视图，再看手机公开视图；视图覆盖 1280×900 与 390×844。站点动态加载或隐私弹窗遮挡时，只记录已可见区域。
- 证据以 DOM 可访问名称、导航、标题、时间、筛选器和页面模块为主；视觉观察只用于判断层级、密度和重排，不复制页面截图、文案、图片、商标或代码。
- 内容、版式、数据、评分和性能会变化；观察日期、公开 URL 和“直接证据／合理推断／无法确认”标签是本报告的一部分。

### 1.2 证据等级

| 标签 | 含义 |
| --- | --- |
| 直接证据 | 在取证日期的公开 DOM、可见页面或公开 URL 上直接看到；例如导航、标题、时间、筛选器、主题按钮。 |
| 结构推断 | 从多个直接证据归纳出的可复用模式；不等于站方确认，也不等于其后台数据结构。 |
| Unknown | 页面未公开、需登录、动态内容未稳定加载，或当前样本不足以判断；按任务要求保留未知。 |

### 1.3 使用与版权边界

参考站只作为内部设计研究证据。F1+1 不复制其商标、字体文件、摄影、图标、原文、摘要、评分、接口、图片 URL、布局组合或受保护的页面资产；只提炼信息层级、密度、状态和响应式原则。页面证据链接可供团队复核，不作为产品素材或数据源授权。

### 2.1 观察结论

- **赛事媒体共同点**：新闻入口几乎都与赛历、结果、积分、车手／车队目录并列；它们把“阅读新闻”和“确认赛事状态”视为相邻任务。
- **编辑媒体共同点**：The Race、BBC 和部分 ESPN 卡片保留摘要、作者／归属和时间，帮助用户在打开详情前判断阅读价值。
- **聚合产品共同点**：AI Hot 和 Google News 都把多来源内容再组织成精选、热点或主题簇；前者强调中文提炼和评分，后者强调来源并列。
- **商业干扰共同点**：Motorsport.com、Autosport、RacingNews365 和 The Race 的公开页面可见广告、订阅、会员、Podcast 或隐私弹窗。它们说明商业模块常与阅读流竞争注意力，不能直接作为 F1+1 的首屏模板。

## 4. 3–5 条高价值借鉴模式

### P1：精选／全量双速信息流

**模式**：用一个较短的“精选／热点”入口完成快速决策，再提供可检索、按时间连续的“全部动态”。AI Hot 的精选／全部、Google News 的 Top news／主题簇以及赛事媒体的 Latest／News in depth 都证明用户有两种不同阅读速度。

**F1+1 映射**：当前公开信息流可以先保持一个主路由，首屏使用精选区或轻量“重点”分组；是否正式新增 `/all`、评分、TOP 5 或单独精选页必须先由产品合同确认。审核只允许 approved bundle 进入任一公开层。

**边界**：不复制 AI Hot 的评分、文案、事件聚类或数据；不把未审核内容放进“热点”。

### P2：来源证据行 + 双时间轴

**模式**：标题旁同时放来源／作者、来源发布或 Posted 时间；聚合站再加系统发现时间、重复来源数或推荐理由。用户可以在展开前判断“谁说的、何时发生、系统何时看到”。

**F1+1 映射**：复用现有 source evidence、original URL 和审核状态，视觉上把 `source_published_at` 与 `discovered_at` 分开；审核和公开层再显示 reviewed／published 时间。该模式可直接增强卡片与详情的信息层级，不要求复制外站字段名。

**边界**：发现时间不能伪装成来源发布时间；来源名、作者和原链需要以实际采集记录为准，Unknown 不渲染为已确认。

### P3：赛事上下文作为轻量“伴随层”

**模式**：F1 官方、ESPN、BBC、RacingNews365 把赛历、结果、积分、车手／车队入口放在新闻附近。它能减少用户在赛事新闻与赛历工具之间来回跳转。

**F1+1 映射**：先做不阻断主任务的上下文条（如当前回合／下一场／查看赛历），置于公开流头部或详情相关模块；详细赛历、实时积分和成绩需要数据合同、更新 SLA 和版权／来源确认。

**边界**：没有稳定、可信的数据就显示 Unknown 或隐藏模块；不能用静态时间或旧积分制造“实时”错觉。

### P4：详情页的证据阶梯

**模式**：The Race、BBC 和 AI Hot 通过标题、中文或编辑摘要、相关内容／事件，再到原始信源，逐层增加上下文。

**F1+1 映射**：与当前详情页合同直接兼容：摘要先回答“发生了什么”，来源证据说明“依据是什么”，相关报道补充“是否同一事件”，原始链接完成阅读闭环。审核页可复用同一证据组件，但增加版本 hash 与审计状态。

**边界**：摘要是站内整理，不是原文重发布；原始链接、权利和媒体状态必须显示清楚。

### P5：响应式密度与无图优先降级

**模式**：媒体站的图文卡在桌面形成视觉入口，手机则压缩为单列；AI Hot 的文字时间线在无图时仍可读；移动筛选普遍收进按钮／抽屉。

**F1+1 映射**：复用 v0.1 的单列／双列／三列重排、图片 optional、筛选面板、44px 控件和 skeleton／error／no-more 状态。首图失败时保留标题、来源、时间、摘要和原链，不能留下大面积空白或失去可读性。

**边界**：不能把“响应式”理解为缩小桌面卡片；手机要重新安排证据顺序，平板要保留足够行宽和可扫读密度。

## 5. 反模式与规避规则

1. **商业模块抢占首屏**：广告占位、订阅 strip、会员 CTA、Podcast 或隐私弹窗在部分公开站点位于主阅读流之前。F1+1 首屏优先信息流；合规提示必须可访问、可关闭或不遮挡主要内容。
2. **赛事工具压过新闻任务**：完整赛历、倒计时、成绩和积分 widget 同时展开会把用户注意力从新内容带走。上下文先做一条轻量入口，详细工具进入独立页面或折叠区。
3. **黑箱评分取代证据**：分数、热度、TOP 排名若没有口径、时间窗和人工纠偏说明，会把编辑判断伪装成事实。F1+1 先展示来源与审核状态，评分需另行确认用途、阈值、版本和解释。
4. **第三方社交嵌入成为硬依赖**：嵌入可能触发 Cookie、登录、跨域脚本、性能和读屏问题。首版使用来源卡和原链；未来嵌入必须支持失败占位、隐私同意、键盘访问和关闭。
5. **图片优先、证据缺失**：大图和标题在视觉上很强，但没有来源、原发布时间、作者或摘要时，用户无法判断可信度。F1+1 让证据行与标题同级，图片只作为可选媒体。
6. **只优化桌面导航**：桌面多级导航在手机会变成“只剩汉堡菜单”，筛选条件和当前上下文消失。移动端必须保留当前频道、已选条件、返回路径和可见状态；复杂表格才允许局部滚动。

## 6. 与 F1+1 当前 Spec／设计规范的差距

### 6.1 已经对齐、可以直接复用

- Spec 已固定“白名单信源 → 采集 → 去重／初筛 → 人工审核 → 公开信息流 → 详情 → 原始链接”的阅读与治理链路；研究中的来源证据、摘要、原链和详情阶梯与它一致。
- [全站设计规范 v0.1](../../../../../design/ui/F1+1-全站设计规范-v0.1.md) 已有公开信息流、内容详情、审核队列、信源管理四类布局模式；研究验证了卡片、筛选、来源证据、状态、移动重排的必要性。
- v0.1 已规定深色默认／浅色可选、图片可无图、语义结构、键盘焦点、44px 触控目标、320px 不产生页面级横向滚动；这些是对竞品反模式的直接防护。
- Spec 已定义审核、发布 hash、unknown／阻断／失败状态；公开竞品无法提供更强的后台证据，因此不作放宽。

### 6.2 研究暴露、但尚未写入产品合同的决策

| 主题 | 现状 | 是否可直接进入设计 |
| --- | --- | --- |
| 精选／全量双层流 | AI Hot 和 Google News 有清晰样本；当前 Spec 只固定公开信息流 `/`。 | 视觉上可用现有分组组件做候选；正式新增入口、排名和数据字段需产品确认。 |
| 赛事上下文 | Spec 尚未定义赛历、结果、积分、下一场和回合字段。 | 可先预留轻量模块位；不得在页面合同中宣称实时数据。 |

| 评分／推荐理由／热榜 | AI Hot 公开展示，但 F1+1 当前没有口径和阈值。 | 先不纳入 MVP；若启用，要有版本、证据、解释、人工覆盖和失败态。 |

| 赛事媒体、视频、播客 | 竞品普遍有，但与资讯聚合核心价值不同。 | 后置；引入前确认媒体权利、成本、性能和可访问性。 |

### 6.3 本轮不改变的设计决定

本轮没有新建 token、颜色、字体、组件或页面；没有修改 `docs/spec.md`、accepted ADR 或 `app`。研究只为后续页面级设计提供证据，风格仍以已确认的 Apple OS 清爽材质、BMW M 硬朗编辑节奏、深色默认／浅色可选和中英文兼容为准。

## 7. 必须等本地 F1+1 预览再验证的结论

公开参考页不能替代本地页面验收，以下事项必须在本地 app 真实路由和真实 fixture 上复核：

1. `/`、`/stories/[publicId]`、`/admin/reviews`、`/admin/sources` 在 320、390、768、1200、1440px 下的最终行宽、列数、筛选展开方式和返回上下文。
2. 中文摘要与英文来源、车手／车队名、数字、时间和 URL 混排时的字体回退、断行、截断和 200% 放大重排。
3. 深色／浅色主题在玻璃材质、图片、无图占位、警示／阻断／Unknown 状态和审核证据面板中的对比度与可读性。
4. 首图加载慢、失败、超宽、无 alt、版权不可用时的降级；真实图片尺寸、WebP／AVIF、懒加载、LCP、CLS 和长列表滚动成本。
5. 键盘顺序、焦点可见性、跳过链接、筛选抽屉、对话框、表格局部滚动和实机 VoiceOver／NVDA 读屏；本轮只检查了公开语义信号，没有宣称实机读屏通过。
6. 公开流在 Loading、Empty、Error、Partial、No more、Unknown、受限、阻断和停用状态下，是否仍能看见来源证据和下一步动作。
7. 事件上下文、代表信源、重复数和“精选／全量”若落地，必须用真实数据检查新鲜度、排序、去重和审核 hash 是否一致；参考站的可见排名不能代替 F1+1 的数据合同。
8. 真实部署的网络、缓存、CSP、外链跳转、图片代理、Origin／CSRF、后台 session 和跨设备状态；竞品公开页面无法证明这些安全与稳定性条件。
