# M3 写后 OAuth 过宽 Scope 安全残余风险补充报告

## 1. 审核范围与结论口径

- 本报告只审查 OAuth `--recommend` 产生的用户授权范围、M3 任务级白名单的缓解能力和后续权限收敛确认点。
- 本轮不访问飞书、不执行鉴权命令、不重授权、不撤权、不写资源、不修改表单或记录，也不把 token、open_id、appId 或认证原始 JSON 写入仓库。
- 统筹部本轮提供的脱敏事实为：`identity=user`、`verified=true`、用户 scope 总数 `142`；Base 域包含 app、field、form、record、role、table、dashboard、workflow 等广泛的 create/read/update/delete 能力；本轮实际业务动作仍按精确白名单执行，没有使用额外 scope 执行业务动作。
- 本报告的 `decision=pass` 表示安全部完成了本项只读风险审查并形成可执行的风险登记。过宽 scope 的风险等级仍为高，不能把任务级 PASS理解成 OAuth 权限已经达到最小权限。

## 2. 历史时态与当前 M3 导入状态边界

### 2.1 旧 PATCH 报告的取证时点

[旧版 M3 表单官方 PATCH 最小白名单报告](2026-08-01-M3表单官方PATCH最小白名单-审核报告.md)中的“真实导入尚未执行”“首次 59 条仍待继续”等描述，属于该报告取证时点的历史事实。安全部不对该报告做回写，也不把当时的状态延伸为当前状态。

### 2.2 后续导入状态的权威来源

- `TASK-20260801-57E98D` 的任务详情记录了统筹部关于 typed `+record-batch-create` 已执行并回读 59×33 全等的执行陈述。
- 同一任务的测试部独立验收报告 `docs/collaboration/部门/测试部/报告/2026-08-01-M3飞书Base影子资源与59条导入-独立验收报告.md` 为 `decision=fail`，原因是受限环境的用户 CLI 读取在 Keychain 阶段失败，测试部无法独立现场确认真实 Base、记录、ACL 和表单状态。
- 因此，本权限风险报告不替代统筹部执行收据，也不把测试部的证据阻断解释成资源不存在或记录必然缺失。当前真实导入状态应继续由统筹部执行收据和测试任务的后续核收证明；本报告只记录其证据边界。

## 3. 风险等级与事实基础

### 3.1 风险等级

**高等级残余风险（P1，预防性授权风险；当前无脱敏证据显示已发生越权）。**

判断依据：

1. 用户授权总量为 142 项，明显超过 M3 本轮所需的资源创建、固定表单字段收敛、记录创建和只读回读范围。
2. Base 域同时覆盖资源创建、读取、更新、删除，以及 role、dashboard、workflow 等高影响对象。按 scope 能力分类，潜在影响包括记录/字段/表删除、权限角色变更、自动化流程修改、仪表盘配置改变和大范围数据读写。
3. OAuth scope 代表租户级 API 能力集合；它不能单独证明某一具体 Base 的资源 ACL，也不能证明任何具体资源已经被访问。资源级权限和 scope 是两条独立证据链。
4. 本轮脱敏事实说明实际业务动作仍受精确白名单限制，且没有使用额外 scope 执行业务动作。这降低了本轮误用概率，但没有从令牌能力层移除多余权限。

### 3.2 未发现的事件

在当前提供的脱敏证据范围内，没有看到以下已发生事实：

- 使用 bot 身份代替用户身份；
- 使用白名单外 API 完成 M3 业务动作；
- 记录删除、表/字段删除、角色或 workflow 变更、公开分享或权限扩张；
- `enabled=true`、Base 真值/provider/Collector/采集/发布切换；
- 将真实 token、open_id、appId 或认证原始 JSON写入仓库。

这些结论只覆盖已提供的脱敏执行事实，不能替代平台审计日志或资源级现场核验。

## 4. M3 任务级白名单能缓解什么

现行 M3 安全报告和补充 PATCH 报告将执行动作锁定为：

- 身份固定为 `user`，禁止切换 bot；
- Base、表、表单、字段、视图和批次使用固定真实 ID 或受控解析结果；
- 表单字段 PATCH 只允许此前报告定义的一个官方字段端点、七个字段 ID 和三类精确请求体；
- 记录写入只使用 typed `+record-batch-create`，固定主信源表和 `migration_batch_id + source_id` 对账键；
- 写前 dry-run/结构检查，写后立即回读，超时和部分成功先读回，禁止盲重放；
- 禁止 `--yes`、删除、公开分享、权限扩张、真实表单提交、workflow、Collector、采集、启用和发布动作；
- 任务报告、日志和仓库不保存认证原文或真实 Base token。

在操作层，这组白名单可以：

1. 减少本轮命令的目标、方法、字段和请求体集合；
2. 降低误把 generic `api` 当通用写入口的概率；
3. 在异常响应后用批次键和只读回查限制重复写入；
4. 把 M3 影子导入与真值、provider、Collector、采集和发布链路隔离；
5. 为本轮执行提供可审计的命令边界和停止条件。

## 5. M3 任务级白名单不能缓解什么

任务级白名单只约束本轮已知执行者和已知命令，不能替代 OAuth 权限收敛。它不能：

- 从当前用户 token 中撤掉 142 项 scope，不能阻止同一 token 被其他进程、其他脚本或被盗凭证调用；
- 防止执行者绕过本项目 wrapper，直接使用 `lark-cli api` 或其他客户端访问 scope 覆盖的对象；
- 保证资源级 ACL、租户高级权限、角色配置或外部协作者边界符合最小权限；
- 防止 role、dashboard、workflow、表/字段/记录 delete 等高影响动作在 M3 以外被执行；
- 证明当前 Base 的资源、记录或表单状态，亦不能替代统筹部执行收据和测试部现场验收；
- 降低 token 在日志、shell 历史、环境变量、备份或终端进程中泄露后的爆炸半径；
- 防止未来 OAuth 重新授权、scope 漂移或推荐授权再次扩大权限。

因此，“当前实际只按白名单执行”应被记录为本轮控制证据；“令牌已经最小权限”不能由此推出。

## 6. 建议的最小权限模型（待用户确认）

### 6.1 保留的业务操作类别

后续如需继续 M3 读回、重放受控执行或维护影子资源，建议只保留以下操作类别，具体 OAuth scope 名称应由官方授权页/CLI 当前版本列出后再由用户确认：

| 类别 | 允许的最小用途 | 备注 |
|---|---|---|
| Base 资源读取/解析 | 精确标题解析、资源目录与结构回读 | 只读；不推导资源 ACL |
| M3 资源创建 | 仅 1 个固定影子 Base、两张表、必要视图/表单的创建 | 若资源已经存在，优先只读复用；不重复创建 |
| 字段/表单读取 | 33/9 字段、表单问题、分享状态回读 | 只读核验 |
| 固定表单字段配置 | 已审的七字段官方 PATCH 窄例外 | 仅固定路径、方法、字段和 body |
| 影子记录写入 | 主信源表固定批次的 record create | `enabled=false`，以批次键对账 |
| 记录读取 | 写前/写后逐页回读和异常恢复判断 | 不含 record update/delete |

### 6.2 明确排除的能力类别

以下类别不属于 M3 最小权限目标，后续重授权时应默认排除，任何保留都需用户单独确认：

- app/table/field/record 的 update 或 delete；
- role 管理、dashboard 写入、workflow 创建或修改；
- 公开权限、链接分享、外部协作者扩张和表单公开提交；
- Base 真值、provider、Collector、采集、同步、启用、自动化或发布切换；
- bot 身份、租户级全局管理能力和与 M3 无关的其他业务域；
- 任何未列入固定路径的 generic raw API。

本节只提出概念级最小权限边界，没有猜测当前租户实际 scope 名称。授权页给出的具体 scope 名称、隐含依赖和是否可单独勾选，必须由用户在重授权前看到并确认。

## 7. 最小 scope 重授权/撤权的用户确认点

权限收敛会改变外部系统授权状态，不能由安全部自动执行。用户至少需要确认以下事项：

1. **当前 token 的保留窗口：** 在统筹部执行收据、M3 记录状态和测试任务完成收口前，是否暂时保留现有 token 供只读回查；是否要求立即停止所有后续外部动作并先撤权。
2. **目标操作集合：** 后续是否仍需要影子 Base 资源创建、字段/表单配置、记录 create 和记录 read；若 M3 已完成，是否只保留 read-only 证据回查。
3. **具体 scope 清单：** 官方 OAuth 页面/CLI 给出最小可选 scope 后，用户确认保留哪些条目；安全部不依据 `--recommend` 自动接受额外 app/field/form/record/role/table/dashboard/workflow 能力。
4. **新旧 token 轮换顺序：** 是否采用“新 token 最小 scope 重授权 → 用户身份/有效性只读验证 → 受控回读 → 用户确认后撤销旧 token”的顺序。新 token 验证失败时是否停止 M3 后续动作，由用户决定。
5. **撤权后的恢复策略：** 撤权是否意味着永久停止当前 M3 读回、暂停未完成的测试验收，还是仅关闭旧 token 并保留资源状态。撤权不应触发自动删除资源或记录。
6. **临时例外：** 若用户需要保留任何 update/delete、role、dashboard、workflow 或权限分享 scope，必须明确用途、对象、时间窗口、调用者和回退方式，并重新经过安全审查；默认为拒绝。

在上述确认完成前，安全部只维持风险登记，不发起 OAuth 重授权、撤销、scope 修改或任何外部写入。

## 8. 停止条件

出现任一情况，立即停止当前 M3 后续动作并回统筹部：

- scope 总数、Base 域能力或身份状态与本轮脱敏事实不一致，且无法获得新的脱敏证据；
- 使用 bot、未列入白名单的 generic API、表/字段/记录 update/delete、role/dashboard/workflow 或分享/权限接口；
- 任务执行者无法证明命令只作用于固定 M3 资源，或无法留存用户身份、命令类别和脱敏回读摘要；
- 发现 token、open_id、appId、认证原始 JSON或私密资源标识进入仓库、日志、shell 历史或报告；
- 发生记录删除、字段/表删除、角色/workflow 变更、公开分享、`enabled=true`、真值/provider/Collector/采集/发布切换；
- 统筹部执行收据与测试任务在导入状态上出现冲突，无法区分取证时点、执行声明和独立验收结果；
- 用户尚未确认最小 scope 清单，却要求安全部执行重授权、撤权或扩大白名单。

## 10. 已验证 / 未验证

### 已验证

- 当前任务已领取，任务要求与用户“不改授权、不访问飞书、不写敏感认证数据”的边界一致。
- 统筹部提供的当前脱敏事实已被完整转述为风险输入：`identity=user`、`verified=true`、总 scope 142、Base 域广泛 create/read/update/delete 能力、实际动作按精确白名单执行。
- 现行 M3 白名单覆盖身份、固定资源、表单 PATCH、typed 记录写入、读后回查、批次对账和禁止业务切换的操作边界。
- 旧 PATCH 报告的“领取态/尚未导入”已被明确标记为历史取证时点，没有修改历史文件。
- `TASK-20260801-57E98D` 的统筹部执行陈述与测试部 `decision=fail` 报告的证据边界已分开记录。

### 未验证

- 当前 142 项 scope 的完整去标识名称、OAuth 颁发时间、过期时间、刷新策略和实际撤权状态；本轮不重新运行鉴权。
- 当前用户 token 是否仍可调用每个具体 scope、每个资源的 ACL、角色继承、租户高级权限和平台审计日志。
- M3 当前真实记录数、59/59 对账、表单/分享状态以及导入后的最终平台状态；这些由统筹部执行收据和测试任务决定。
- 最小 scope 的具体官方名称、可拆分粒度和 OAuth UI 的隐含依赖；在用户确认前不猜测或提交。

## 11. 错题自检与结论

- 没有把租户级 scope 摘要写成具体 Base ACL，也没有把 `verified=true` 写成资源读写成功。
- 没有把任务级白名单写成 token 层最小权限，明确列出 token 泄露、旁路客户端和 scope 外部滥用无法被白名单消除。
- 没有把旧 PATCH 报告的“尚未导入”改写为当前导入状态；后续状态继续交由统筹部执行收据和测试任务证明。
- 没有把测试部因 Keychain 阻断的 `FAIL`解释成资源缺陷，也没有把统筹部执行陈述当作安全部现场独立验证。
- 没有执行重授权、撤权、权限扩张、记录写入、删除、分享或业务链路切换。
- 没有把当前风险登记扩展成真值、provider、Collector、采集、启用、同步或发布授权。

**结论：条件式 PASS，风险等级为高。** 本轮脱敏证据未显示白名单外业务动作，M3 任务级白名单继续作为操作层控制；OAuth `--recommend` 造成的 142 项过宽用户 scope 仍需登记为高等级残余风险。最小 scope 重授权或撤权属于用户决策，在获得明确确认前，安全部不执行任何授权变更，也不据此改写 M3 真实导入状态。
