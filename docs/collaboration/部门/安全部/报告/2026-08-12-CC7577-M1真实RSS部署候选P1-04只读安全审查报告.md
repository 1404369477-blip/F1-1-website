## 3. P1

### P1-01：release commit/hash 只是受信输入，manifest 没有核验实际 release

**状态：OPEN。**

`assertReleaseIdentity` 只验证环境变量是 40/64 位小写十六进制（`app/src/server/rss/deployment.ts` 第 295–305 行）。installer 将这两个输入直接传入 manifest（`app/scripts/rss-install-macos.ts` 第 70–82 行）。回读时又从 manifest 取出相同字符串，通过同一格式检查后重建 expected manifest（`deployment.ts` 第 360–382 行）。代码没有读取实际 release archive、内容根或当前 checkout commit，也没有把输入 hash 与任何本地字节比较。

因此任意格式合法的假 commit/hash 都可形成并通过自校验 manifest，无法证明部署目录来自统筹固定的 release。

最小修复：把统筹提供的 expected release SHA 当作期望值，对目标机上实际 release archive或冻结内容清单计算 SHA；再验证 archive内不可变 release manifest中的 commit和完整文件root。回读时重新计算当前安装树root并与该固定值比较，禁止从待验证 manifest 本身取得唯一信任锚。

### P1-02：manifest 未形成 collector/control/installer 的完整运行时字节闭包

**状态：OPEN。**

manifest 只记录 collector、installer、control、deployment module、plist、migration和package-lock（`deployment.ts` 第 53–80、308–350 行）。collector实际传递依赖的 `transport.ts`、`parser.ts`、`repository.ts`、`types.ts`、DB/config/runtime/security模块均未绑定；`node_modules/fast-xml-parser`实际安装字节也未校验。`package.json`虽然被读取并检查一个依赖版本，文件hash被计算后直接丢弃，没有进入manifest（第 312–337 行）。Node只记录路径/版本，未记录或核验可执行文件hash（第 214–230、332 行）。

未绑定模块或运行时安装树漂移时，`readVerifiedRssDeploymentManifest`仍可能重建完全相同的 expected manifest。这个缺口覆盖RSS输入安全、SQLite围栏、CLI脱敏和控制工具自身，属于部署身份P1。

最小修复：由可信release清单绑定全部生产传递闭包、package.json/lock、实际依赖安装树root和固定Node二进制hash；manifest回读对当前字节逐项或按确定性Merkle/content root复算。至少包含已冻结的RSS types/transport/parser/repository/collector、DB安全入口、runtime-config、safe CLI、installer/control/deployment及其生产依赖。

### P1-03：resume 没有验证当前 DB schema fingerprint

**状态：OPEN。**

manifest只保存常量 `RSS_SCHEMA_SHA256`（`deployment.ts` 第 68–73、338–343 行）。`readVerifiedRssDeploymentManifest`检查DB是0600单链接普通文件及manifest/plist一致性，但没有打开DB、调用 `assertRssSchema` 或重新计算fingerprint（第 360–387 行）。control在resume分支回读manifest后直接 `setSourceEnabled(true)`，该函数只UPDATE source，没有schema断言，随后bootstrap（`app/scripts/rss-control.ts` 第 60–77、101、117–123 行）。`assertRssSchema`只出现在status的只读辅助函数（第 46–58、103–114 行）。

这与“resume先验证schema再启用”的合同不一致。主表仍能UPDATE、其他约束/索引/trigger已漂移的数据库可被启用和加载。

最小修复：resume在启用source前，以只读连接执行完整 `assertRssSchema`、integrity/foreign-key检查和冻结schema fingerprint；结果必须与manifest值相等。随后在启用事务中再次确认同一DB身份或建立可防替换的文件/连接绑定。

### P1-04：launchctl异常时，resume重围栏与stop/unloaded后置条件未能保证

**状态：OPEN。**

`isLoaded`把`launchctl print`所有非零退出统一解释为“未加载”，无法区分确实不存在、权限错误和launchctl自身故障（`app/scripts/rss-control.ts` 第 36–44 行）。stop在bootout失败后依赖该布尔值；print再次异常时仍可输出`loaded=false/status=stopped`（第 85–98 行）。

resume先提交`enabled=1`再bootstrap。bootstrap非零时，代码先调用第二次DB事务重围栏；若该事务因busy/I/O等原因抛错，后续bootout不会执行，第一次enable已经提交。重围栏成功后，bootout结果也被忽略，且没有验证source disabled、epoch已增加和job确实unloaded（第 117–134 行）。这不能满足resume失败后的fail-closed后置条件。

最小修复：launchctl调用返回结构化的固定状态，只有明确“service not found”可判unloaded；其他错误一律Unknown/FAIL。bootstrap失败清理用独立的best-effort两阶段：无论DB refence是否失败都尝试bootout，并分别记录结果；最终必须回读确认`enabled=false`、epoch已增加、job明确unloaded，否则输出固定失败且禁止宣称stopped。stop采用相同后置条件确认。

## 4. P2

### P2-01：日志叶子文件权限未固定

`logsRoot`会被收紧为0700，能提供目录级隔离（`deployment.ts` 第 232–237 行）。plist只声明`StandardOutPath`/`StandardErrorPath`，没有`Umask`，installer也没有预创建和断言两个日志文件为0600（第 247–281 行；`rss-install-macos.ts` 第 70–82 行）。最终叶子mode由M1 launchd创建行为决定，当前为Unknown。父目录0700限制其他用户遍历，故定P2。

最小修复：prepare阶段原子预创建两个0600单链接普通日志文件并纳入权限检查；plist显式设置0077 umask；status/resume复核日志文件owner、link count和0600。

### P2-02：`installed-not-loaded`没有证明目标机原先未加载同名job

installer确实没有`launchctl`调用，prepare-only动作本身成立（`rss-install-macos.ts` 第 52–93 行）。它仍无条件输出`status=installed-not-loaded`，未读取既有launchd状态。runbook只在prepare之后要求`launchctl print`（runbook第 24–42行）。若M1已残留同label job，收据措辞与事实不符，并可能在prepare期间继续运行。

最小修复：SSH实施在prepare前先取得明确unloaded收据；若无法确认则先走stop并核对后置条件。installer输出改为只承诺`prepared-no-bootstrap-called`，避免声称全局未加载状态。
