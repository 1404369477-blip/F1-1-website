# OAuth 142 scopes 最小化与无损轮换执行包审核报告

## 1. 审核范围与安全边界

- 本报告只使用仓库中的脱敏鉴权收据、任务 JSON、现有安全/统筹/产品证据，以及本机 `/opt/homebrew/bin/lark-cli` 的 help、schema 与 embedded `lark-shared` skill。
- 本轮没有执行 login、device-code、logout、revoke、重新授权、token 刷新、scope 修改、飞书资源读取或任何飞书资源写入。
- 本轮没有使用浏览器，没有访问完整 Base URL，没有记录 token、refresh token、open_id、appId、用户名称、租户标识或认证原始 JSON。
- 本报告是可执行包和用户确认材料，不构成授权变更。任何会改变认证状态的命令都必须在用户看到精确 scope diff、风险、保存方式和回退条件后另行确认。
- “最小 scope”只描述租户级 OAuth 能力候选；它不能替代 Base 资源 ACL、角色继承、租户策略或平台审计证据。

`2026-08-01T13:47:45+08:00` 是 15 个精确 `base:*` 名称收据的取证时间；`142` 总量来自当前任务/统筹部的脱敏事实，报告不假设两者来自同一次鉴权读取，也不以 13:47 收据单独证明 142 总量。

### 2.2 本轮 CLI 只读取证尝试

## 3. 脱敏 scope 分类与精确名称证据

### 3.1 收据明确列出的 15 个精确名称

以下名称逐字来自脱敏收据，属于已验证的租户级 scope 名称。它们仍然不能证明某个资源 ACL 或 API 实读成功。

| 能力分类 | 精确 scope 名称 | 默认风险处理 |
|---|---|---|
| Base 读取 | `base:app:read`、`base:field:read`、`base:record:read`、`base:table:read`、`base:view:read` | M3/A 只读候选；仅按固定资源和只读命令使用 |
| Base 创建 | `base:app:create`、`base:field:create`、`base:record:create`、`base:table:create` | 不进入运行时只读档；仅作一次性建库/迁移例外 |
| Base 更新 | `base:app:update`、`base:field:update`、`base:record:update`、`base:table:update` | 不默认保留；按维护性写入例外单独授权 |
| Base 删除 | `base:table:delete` | 默认排除；任何临时保留都要单独用户确认 |
| View 写入 | `base:view:write_only` | 语义细粒度和包含的对象范围需继续核实；默认不进入运行时档 |

### 3.2 142 总量和未列名称

- 142 是当前用户 scope 总量的脱敏事实，不能从该数字推导每个 scope 的官方名称或依赖关系。
- 脱敏收据只保存了 15 个 `base:*` 名称；其余 127 个位置没有精确原文。它们可能属于其他业务域，也可能包含收据未保留的 Base/表单/权限名称，当前统一为 `Unknown`。
- `base:form:*`、`base:role:*`、`base:dashboard:*`、`base:workflow:*` 以及公共权限、协作者、表单分享和外部访问相关名称，在当前收据中没有精确 scope 原文；不得用 SDK 字段名、HTTP 路径或经验拼造 scope。
- “app/field/form/record/role/table/dashboard/workflow 的 CRUD 能力存在”是高层脱敏分类，适用于风险分级和排除项，不能替代精确授权清单。

## 4. M3 只读审计档（运行时最小候选）

### 4.1 已有精确名称候选

M3 只读审计档只覆盖固定影子 Base 的结构、字段、视图和记录回读。基于现有精确名称证据，候选 allowlist 为：

```text
base:app:read
base:table:read
base:field:read
base:view:read
base:record:read
```

用途映射：

| 只读动作 | 候选 scope | 约束 |
|---|---|---|
| 精确资源/应用解析和结构读取 | `base:app:read` | 仅使用已确认标题/受控资源上下文，不把 scope 当作资源存在证明 |
| 表与表级结构回读 | `base:table:read` | 只读，不创建、更新或删除表 |
| 字段定义回读 | `base:field:read` | 只读，不执行字段 PATCH |
| 视图读取 | `base:view:read` | 只读，不写视图 |
| 记录分页、批次和状态回读 | `base:record:read` | 只读，不创建、更新或删除记录 |

### 4.2 仍需证据补齐的只读能力

- 手机表单元数据和问题列表读取所需 scope：`Unknown`。当前不能写成 `base:form:read`，也不能因为表单属于 Base 就假定继承 `base:app:read`。
- 公共 ACL、`manage_public`、协作者列表和分享状态读取所需 scope：`Unknown`。已有 typed CLI schema 的 scope 元数据不能替代用户实际 grant 的精确名称。
- 若只读审计命令需要云盘/文档路由 scope，具体名称和依赖：`Unknown`；未经官方证据补齐，不纳入 M3 allowlist。
- M3 只读档不包含任何 create/update/delete、role、dashboard、workflow、权限管理、外部分享、表单公开提交或 bot scope。

### 4.3 M3 只读档的验收条件

1. 用户看到并确认精确五项已知候选，以及所有 Unknown 项的处理方式。
2. 新授权结果应只出现已确认的 read scope；出现任意未列 scope、write/delete、role/dashboard/workflow 或公共权限 scope 时停止。
3. `identity=user`、`verified=true`、token 状态有效的结果只能作为身份/令牌证据，不能替代固定 Base 的资源级读回。
4. 未来固定资源读回必须保持 M3 影子边界：不创建、不修改、不删除、不公开、不切换真值/provider/Collector/采集/发布。

## 5. A/base_direct 档（运行时最小候选）

### 5.1 运行时读取档

已接受的 A 路线规定，Base 成为唯一业务真值后，`base_direct` 作为采集器的在线读取 provider。运行时采集器只需读取完整、有效且满足生效谓词的 Base 配置，因此候选仍为 M3 的五个已知 read scope：

```text
base:app:read
base:table:read
base:field:read
base:view:read
base:record:read
```

表单、公共 ACL、角色继承或租户策略读取若被运行时需要，必须先由官方证据补齐精确名称；在此之前保持 `Unknown`，不得把维护 scope 默认放入 `base_direct` 运行时 token。

`base_direct` 运行时档明确禁止：record create/update/delete、field/table/app update/delete、视图写入、表单配置、权限管理、分享、workflow、dashboard、role 变更以及任何业务真值以外的第二写入口。

### 5.2 建库与维护例外档

维护性写入、权限管理和 delete 不属于 `base_direct` 运行时默认 scope。若未来确有必要，应使用单独的短时授权上下文、固定对象、最小调用者和用户确认，完成后立即关闭使用窗口。

| 例外目的 | 已知精确 scope 候选 | 默认状态 | 额外门禁 |
|---|---|---|---|
| 一次性创建影子/真实 Base 资源 | `base:app:create`、`base:table:create`、`base:field:create`、`base:view:write_only` | 排除 | 固定资源计划、dry-run、用户确认；完成后不得留在运行时 token |
| 一次性导入受控记录 | `base:record:create` | 排除 | 固定批次、`enabled=false`、先读回/后读回、唯一键对账、用户确认 |
| 维护信源状态或字段配置 | `base:app:update`、`base:field:update`、`base:record:update`、`base:table:update` | 排除 | 逐字段/逐记录白名单、变更前后差异、短时间窗；不得作为 collector 默认能力 |
| 视图维护 | `base:view:write_only` | 排除且语义待核实 | 先补齐官方语义，禁止据名称推导其覆盖范围 |
| 公共 ACL/协作者/表单分享管理 | 精确名称 `Unknown` | 排除 | 另立安全任务、用户确认、写前/写后 fresh read；不可用经验 scope 顶替 |
| delete | 已知 `base:table:delete`；记录/字段/应用/视图 delete 名称 `Unknown` | 默认拒绝 | 只有资源所有者明确确认的单次处置任务可讨论；本执行包不授权 |

即使后续用户确认某个维护例外，也不得将其与 `base_direct` 运行时 token 合并。A 的业务真值切换、`base_direct` provider 切换和任何 ACL 改动继续是相互独立的用户门禁。

## 6. 默认排除项

以下能力不进入 M3 只读档或 A/base_direct 运行时档：

- `--recommend`、`--domain all`、未经拆分的 `--domain base`，以及任何自动扩展 scope 的授权方式；
- 所有 app/field/record/table update/delete，除非作为单次维护例外明确批准；
- `base:table:delete` 及所有未取得精确名称的 delete；
- form、role、dashboard、workflow 的 create/read/update/delete 未确认项；
- 公共 ACL、协作者增删、外部分享、表单公开、评论/下载/复制控制等权限管理能力；
- bot 身份、租户级管理、与 M3/A 无关的其他业务域；
- generic raw API、浏览器自动化、未经固定资源解析的命令；
- 真值切换、`base_direct` provider 切换、`base_snapshot` 切换、Collector、采集、同步、启用和发布切换；
- login、device-code、logout、revoke、token 刷新、scope 追加或任何认证状态变更，除非完成下述用户门禁。

### 7.1 只读命令

| 命令 | help 风险 | 本包用途 | 本轮状态 |
|---|---|---|---|
| `lark-cli auth status --json --verify` | `read` | 未来验证身份、token 状态和用户 scope | 只读 help；未执行，沿用脱敏收据 |
| `lark-cli auth check --json --scope <list>` | `read` | 未来检查新 token 是否具备已确认 scope | 只读 help；未执行 |

| `lark-cli auth scopes --format json` | `read` | 读取 app 已开通 scope | 尝试一次，因 keychain 未初始化失败；未改变认证状态 |
| `lark-cli config show` | `read` | 未来确认 CLI 配置来源，不读取或输出凭证 | 只读 help；未执行 |

### 7.2 会改变认证状态的命令

| 命令 | help 事实 | 当前处理 |
|---|---|---|
| `lark-cli auth login --scope ... --no-wait --json` | `Risk: write`；支持 `--scope`、`--exclude`、`--domain`、`--recommend` | 仅列入未来计划，当前不执行 |
| `lark-cli auth login --device-code ...` | 完成前一授权流程，属于认证写入路径 | 当前不执行 |
| `lark-cli auth logout --json` | `Risk: write`，清除本机 token | 当前不执行；不能当作服务端撤权 |
| `lark-cli auth revoke` | CLI 无独立命令 | 不据此推导不存在平台撤权；服务端撤权语义保持 Unknown，需用户在授权管理处处理 |
| `lark-cli config bind` / `config remove` | `Risk: write`，可能覆盖凭证或配置 | 当前不执行 |

`lark-shared` embedded skill 明确指出：`auth login --scope` 是按指定 scope 授权，scope 可与 domain/recommend 组合；多次 login 的 scope 会累积，CLI 不支持单独撤销一个已授予 scope；`auth logout` 只清本机登录态，服务端授权需要用户在飞书授权管理页取消。基于这些规则，不能把一次增量 login 或本机 logout 描述为“已完成最小化”或“已完成服务端撤权”。

## 8. 无损轮换执行包（只定义步骤，不执行）

### 阶段 0：冻结旧授权和输入

1. 保留旧 token 原状，不执行 logout、revoke、login、refresh 或 scope 追加。
2. 以本报告的 scope manifest 为候选输入：15 个精确已知名称、M3/A read 档、维护例外和 Unknown 清单分开保存；manifest 不含 token、URL、用户标识或认证原文。
3. 用户确认当前 M3 仍需哪些只读回查、A/base_direct 是否已到 provider 门禁、旧 token 的保留窗口和是否允许任何后续外部读回。

### 阶段 1：形成新旧 scope diff

1. 以旧总量 `142` 作为风险基线，不把 142 个完整名称伪造或补全。
2. 将候选新集分为 `M3_READ`、`A_BASE_DIRECT_READ`、`MAINTENANCE_EXCEPTION`、`PERMISSION_UNKNOWN`、`DELETE_EXCLUDED` 五类。
3. 用户逐项确认新集、排除集、Unknown 处理和临时例外的时间窗口。任何 form/role/dashboard/workflow/ACL scope 仍未知时，不能自动进入新集。
4. 输出仅含 scope 名称、用途、风险级别、来源日期、证据状态和 manifest 哈希的审计材料；禁止保存 token 或完整 Base URL。

### 阶段 2：建立新授权（未来用户门禁后）

计划命令形状如下，当前不执行，且 `<精确已确认scope列表>` 不能由本报告的 Unknown 项替换：

```bash
lark-cli auth login \
  --scope '<精确已确认scope列表>' \
  --exclude '<经官方证据确认应排除的scope列表>' \
  --no-wait --json
```

注意：

- `--scope` 与 `--exclude` 的最终请求语义必须由用户在当前 CLI 版本上看到并确认；不能凭参数名断言它会从既有 grant 中删除 scope。
- `--recommend`、`--domain all` 和未经拆分的 broad domain 禁止使用。
- CLI help/skill 没有证明“同一凭证存储可安全并行保留新旧 token”或“login 会替换而非累积 grant”。因此，若无法提供独立、可审计且不覆盖旧 token 的凭证上下文，阶段 2 立即停止。
- `--no-wait` 只用于在用户看到授权链接后交还控制权；后续 `--device-code` 仍是认证状态变更，需用户明确确认，当前不执行。

### 阶段 3：只读验证新授权

只有阶段 2 完成且用户明确要求后，才可在独立凭证上下文中做以下验证：

1. 读取 `identity=user`、`verified=true`、token 状态和 scope manifest；出现额外 scope、缺少必需 scope、身份不符或输出未脱敏即停止。
2. 使用 `auth check --json --scope` 检查已确认的 read scope；响应必须 `ok=true` 或进程退出码为 0。
3. 如需固定 M3 资源读回，只能经单独资源门禁读取结构/记录，不能把读回结果写入飞书，不能执行表单提交、ACL 写入或业务切换。
4. A/base_direct 只读验证要覆盖完整分页、schema、唯一性、生效谓词、权限失败、缺页、空响应和在途 epoch；任一失败都停留在已批准阶段，不能切 provider。
5. 保留新 token 的 scope 摘要和验证收据；不保存 token、refresh token、open_id、appId 或完整 URL。

### 阶段 4：受控切换与旧 token 保留

- 当前仓库没有 app/Collector 运行实现，安全部不执行任何消费者切换。
- 将 `base_direct` provider 切换与 OAuth 轮换分开处理；新 token 验证通过不自动授权 Base 真值切换、A provider 切换或 D snapshot 切换。
- 新 token 验证和受控读回均通过后，用户再决定是否让受控执行者使用新 token；在用户确认前继续保留旧 token，不执行 logout/revoke。
- 切换窗口、调用者、资源范围、最大时间和停止条件必须形成单独收据。

### 阶段 5：旧 token 撤销门禁

1. 用户看到新旧 scope diff、身份验证、受控读回、失败探针和回退方案后，明确决定是否撤销旧 token。
2. CLI `auth logout --json` 只清本机登录态，不能代替服务端授权管理页撤权；服务端撤权入口、撤权后 refresh token 是否立即失效、已发 access token 的剩余寿命和恢复语义，在本地资料中均为 `Unknown`。
3. 未得到用户明确确认前，不执行 logout、平台撤权、旧 token 删除或 token 文件清理。
4. 撤权操作不触发资源删除、记录删除、ACL 变更、真值/provider/Collector/采集/发布切换。

## 9. 验证矩阵与回退

| 阶段 | 验证项 | 通过条件 | 失败处理 |
|---|---|---|---|
| scope manifest | 精确名称、用途、来源日期、差异 | 已知项逐字匹配；Unknown 未被补猜 | 停止授权，交研究部/统筹部补证据 |
| 应用 grant | app 已开通 scope 与用户 grant 分开 | 两份清单独立、无额外高危项 | 停止，不把 app scope 当 user grant |
| 身份状态 | `identity=user`、`verified=true`、token 有效 | `ok=true` 或退出码 0，输出已脱敏 | 保持旧 token，不切换，不撤旧 |
| M3 read | Base/app/table/field/view/record 只读 | 固定资源读回成功，无写入副作用 | 先停止；不重试 create/update/delete |
| A/base_direct read | 完整分页、schema、唯一性、生效谓词和权限失败安全 | 全量通过，失败时保持停止 | 不切 provider；保留旧运行路径或停机待用户决定 |
| 认证存储 | 新旧 token 并存/选择语义 | 有可审计、无覆盖的独立上下文证据 | 不运行 login；将轮换标为 Unknown |
| 旧 token 撤权 | 用户确认、服务端入口、撤权后语义 | 先完成新 token 收口与回退窗口 | 不 logout/revoke；旧 token 保留 |

### 回退原则

- 阶段 2 失败：旧 token 不变，终止新授权流程；不盲目重试。
- 阶段 3 失败：旧 token 继续保留，停止任何 provider/业务切换；由用户决定是否恢复授权流程。
- 阶段 4 发现新 token 读回不完整、scope 漂移、缺页、权限错误或超时：不撤旧 token，不把残缺结果写入业务真值，保持当前已批准阶段。
- 阶段 5 后发现平台撤权语义与预期不符：不得自动重新授权或恢复第二真值；交用户和平台管理员处理。
- 当前任务没有运行时消费者，因此不执行自动回切、资源修复、ACL 回滚或记录修复。

## 10. 必须停止的失败路径

1. **认证状态风险或凭证输出风险：** 任意命令显示可能刷新 token、触发 login/logout/revoke、覆盖凭证、输出未脱敏认证原文，立即停止；保留已有收据并将相关项标为 Unknown。
2. **scope 精确性或存储语义不足：** 官方/CLI 证据无法证明 scope 精确名称、粒度、依赖、`--exclude` 语义或新旧 token 并存能力时，不构造请求、不发起授权、不声称已最小化。
3. **新 token 验证或业务边界失败：** 新身份、scope、固定资源只读回、分页、schema、唯一性或状态不符合预期，或要求使用 raw API、bot、delete、ACL、真值/provider/Collector/采集/发布切换时，停止并保留旧 token，不进行撤权或盲重试。
