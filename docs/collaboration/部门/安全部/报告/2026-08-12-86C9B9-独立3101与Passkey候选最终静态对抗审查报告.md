# TASK-20260812-86C9B9 独立 3101 与 Passkey 候选最终静态对抗审查报告

## 1. 最终结论

**FAIL：P0=0，P1=1，P2=1。**

十三份任务冻结文件的 SHA-256 全部逐字匹配。审查严格保持候选修改 `0`、测试 `0`、typecheck `0`、网络/SSH `0`、数据库写入 `0`。本轮只读取候选源码、既有固定依赖源码/类型、开发部持久化收据和现行安全合同。

首个必须停止的问题位于 WebAuthn 认证状态提交边界：登录与 fresh re-auth 都在异步验证前读取一份 credential counter 快照；验证完成后，`PasskeyCredentialStore.updateCounter()` 没有携带或核对 `expectedCounter`，也没有执行单调更新。两个有效 assertion 因而可以同时基于 `counter=N` 通过 SimpleWebAuthn 验证；若携带 `N+2` 的调用先完成、携带 `N+1` 的旧调用后完成，持久化 counter 会从 `N+2` 回退到 `N+1`。同时，SimpleWebAuthn 在认证结果中提供的 `credentialDeviceType` 与 `credentialBackedUp` 被 adapter 丢弃，存储层不能验证 backup eligibility/device type 的一致性，也不能按明确策略持久化 backup state。

这会回退 WebAuthn clone-detection 的服务端状态，并使任务明确要求审查的 counter/backup 状态缺少可靠提交门，判定为 P1。发现后已立即向统筹部发出精确修正，并停止扩展。当前候选不得进入 Admin UI 业务接线或固定 M1 prepare；修正应保持在 auth/webauthn/storage 及一组聚焦并发负例内。

## 4. P1-01：认证状态可逆序回退，device/backup 状态被丢弃

### 4.1 静态证据

1. `auth.ts:269-278` 的登录路径先从 store 取得 `credential`，随后 `await verifyAuthentication(...)`，最后只调用 `updateCounter(id, newCounter, now)`；fresh 路径在 `auth.ts:335-345` 采用同一顺序。
2. `storage.ts:199-215` 的 `updateCounter()` 重新读取当前 credential file 后直接覆盖传入 counter。它没有接收验证时的 `expectedCounter`，没有要求当前值仍等于验证快照，也没有拒绝非单调回写。
3. `webauthn.ts:33-37` 将认证结果类型缩减为 `credentialId + newCounter`；`webauthn.ts:180-184` 同样只返回这两个字段。固定依赖实际返回的 `credentialDeviceType` 与 `credentialBackedUp` 没有传回 auth/store。
4. challenge 绑定和单次消费不能关闭该交错。第一个调用消费 challenge 后会在异步签名验证处让出；同一 identity 可以取得第二个 challenge，另一已批准 identity 也有独立 challenge key。两次验证均可能在读取相同 `counter=N` 后并发进行。

### 4.2 可复现的静态交错

```text
credential file counter = N
A: 读取 credential(N) → 消费 challenge-A → await verify(assertion N+1)
B: 读取 credential(N) → 消费 challenge-B → await verify(assertion N+2)
B: verifier 相对 N 接受 N+2 → updateCounter(N+2)
A: verifier 相对旧快照 N 接受 N+1 → updateCounter(N+1)
最终持久化 counter = N+1
```

每个 assertion 都可以独立满足 RP ID、origin、challenge、presence、UV 与签名验证。问题只发生在验证后的共享状态提交，不需要伪造 assertion。

### 4.3 影响

- 服务端保存的 authenticator counter 可以从更高值回退，缩小或绕过后续用于发现 cloned credential 的计数窗口。
- 登记时保存的 `deviceType/backedUp` 成为不会在认证时核对或更新的静态字段。服务端无法发现 backup eligibility/device type 与登记状态不一致，也没有可审计的 backup-state 变化规则。
- session/fresh receipt 只依赖当前调用是否验证通过；状态提交没有证明它基于最新 credential state。该缺口同时影响日常登录和高风险 publish fresh re-auth。

### 4.4 精确最小修正

1. 将 `AuthenticationVerification` 扩展为返回 `credentialDeviceType` 与 `credentialBackedUp`，逐字转发 SimpleWebAuthn 的认证结果；不手写解析 authenticatorData。
2. 以单一同步方法替换 `updateCounter`，建议形状为 `commitAuthenticationState(id, expectedCounter, newCounter, deviceType, backedUp, now)`。
3. 在一次 store 临界区内重新读取当前 credential，并强制 `current.counter === expectedCounter`；不等时失败关闭，调用方重新开始一轮 challenge，不盲重试旧 assertion。
4. 当 `current.counter > 0 || newCounter > 0` 时只接受 `newCounter > current.counter`；两者都为 `0` 时允许 passkey 的零计数语义。禁止任何 counter 回退或相等的非零提交。
5. `credentialDeviceType` 必须与登记时的 backup eligibility/device type 一致；不一致时拒绝。`credentialBackedUp` 按明确且有审计含义的状态策略验证并原子保存，不能继续静默丢弃。
6. 只有认证状态提交成功后，登录才签发 session，fresh 才轮换 session/签发 fresh receipt。
7. 只增加一组聚焦负例：两个 verifier 都基于 N 成功但以 N+2→N+1 逆序提交，第二次提交必须失败且最终 counter 保持 N+2；再覆盖 device type 不一致与允许的 backup-state 策略。无需重跑无关套件。
