## 3. CC7577 六项复核

### P1-01：外部 release-manifest SHA 与实际 release 身份

**CLOSED（静态）。**

- builder 从真实 Git HEAD 取 40 位 commit，要求列明的运行文件均 tracked，并拒绝限定闭包的 dirty/untracked 漂移（`app/src/server/rss/release-manifest.ts` 第 210–231 行）；随后把 commit、运行文件、生产依赖和 Node 纳入两个确定性 root（第 193–207、234–248 行）。
- installer 读取外部 `RSS_EXPECTED_RELEASE_MANIFEST_SHA256`，先比较 manifest 实际文件字节，再根据当前安装树、当前依赖目录和当前 Node 重新生成 expected manifest，并要求 canonical bytes 完全一致（第 251–305 行；`app/scripts/rss-install-macos.ts` 第 70–75 行）。
- deployment manifest 继续保存已核验的外部 manifest SHA、Git commit、content root 和 release root（`app/src/server/rss/deployment.ts` 第 315–369 行），回读会重新生成并逐字比较（第 377–408 行）。

上述路径关闭了 CC7577 所述“格式合法的受信字符串可自证”的原缺口。

### P1-02：完整运行文件、递归生产依赖与 Node 字节闭包

**原问题 CLOSED（静态）；定时执行绑定缺口另记 P1-N01。**

- release 清单显式列出 18 个运行文件，覆盖 collector、RSS 模块、DB/config/runtime/security、部署/控制/安装/builder、migration、package 与 lock（`release-manifest.ts` 第 16–35 行），并逐文件绑定 mode、size 与 SHA（第 96–110 行）。
- `fast-xml-parser` 从 lock 递归遍历生产依赖图；每个包目录拒绝 symlink/特殊文件和非 owner 控制目录，并递归绑定文件列表及 content root（第 113–180 行）。
- 固定 M1 Node 绝对路径、版本和实际二进制 SHA 进入 content/release root（第 184–207、234–248 行）；installer 回读对当前运行文件、依赖目录与当前 Node 字节重算（第 251–305 行）。

因此 CC7577 原报告列出的缺失文件、实际 `node_modules` 与 Node 字节三类问题已经关闭。执行时点的重新绑定缺口见第 4 节。

### P1-03：resume 同一 DB 连接 schema 门

**CLOSED（静态）。**

`setSourceEnabled` 打开将要写入的同一 DB 连接，在该连接上先执行 `assertRssSchema`，随后才进入 `BEGIN IMMEDIATE` 更新 source（`app/scripts/rss-control.ts` 第 80–98 行）。resume 在启用前读取并校验当前 schema，并调用 `setSourceEnabled(true, false, true)` 后才 bootstrap（第 170–180 行）。这关闭了只信 manifest 常量或在另一连接上检查的原缺口。

### P1-04：launchctl 状态、stop/resume 次序与失败后置

**CLOSED（静态）。**

- `launchctl print` 成功才判 loaded；仅固定 service-not-found 文本判 unloaded，其余失败为 unknown（`rss-control.ts` 第 40–56 行）。
- `bestEffortStop` 独立尝试 DB refence 与 bootout，并最终回读 source 与 launch state；只有 source disabled、epoch 严格增加且 job 明确 unloaded 才确认停止（第 100–118 行）。
- stop 仅在三项后置同时满足时输出 `stopped-confirmed`（第 127–141 行）。resume 要求先明确 unloaded，成功回读 enabled+loaded；异常路径再次执行独立 best-effort stop，后置无法确认时固定 fail closed（第 170–199 行）。

### P2-01：日志叶子 0600 与 plist Umask

**CLOSED（静态）。**

installer 在 prepare 中原子创建两个私有日志叶子或核验既有叶子（`app/scripts/rss-install-macos.ts` 第 76–80 行）；deployment 回读要求 stdout/stderr 及 SQLite sidecar 均为私有单链接普通文件（`app/src/server/rss/deployment.ts` 第 377–390 行）；plist 固定 `Umask=63`，即 `0077`（第 265–300 行）。

### P2-02：prepare-only 措辞与 prepare 前 unloaded preflight

**CLOSED（静态/文档）。**

installer 成功收据只声明 `prepared-no-bootstrap-called`（`rss-install-macos.ts` 第 94–102 行），没有宣称 M1 全局未加载。runbook 在 prepare 前要求 `launchctl print`，仅明确 service-not-found 可继续，loaded 或 Unknown 均停止（runbook 第 40–59 行）。

## 4. 直接同级问题

### P1-N01：定时与单次入口执行前不重验已绑定运行时字节

**OPEN，P1。**

证据链：

1. `resume` 在 bootstrap 前确实核验 release/deployment manifest（`app/scripts/rss-control.ts` 第 145–152、170–180 行），该核验只证明核验时点的安装树。
2. plist 的 `ProgramArguments` 只设置隔离环境、`RSS_REAL_IO=true`、固定 Node 参数，并直接把 `scripts/rss-collect-once.ts` 作为入口；其中没有外部 expected manifest SHA，也没有 verified launcher（`app/src/server/rss/deployment.ts` 第 265–275 行）。
3. collector 顶层直接静态导入 parser、repository、transport 与 types（`app/scripts/rss-collect-once.ts` 第 1–20 行），进入 `main` 后直接打开 DB、claim run 并请求 RSS（第 46–72 行）；该入口没有调用 `readVerifiedRssReleaseManifest` 或 `readVerifiedRssDeploymentManifest`。
4. runbook 的受控单次命令同样直接执行 collector，且没有传入外部 manifest SHA（runbook 第 67–80 行）。

因此，owner-writable 的运行文件、递归依赖或 Node 在 resume/prepare 后漂移时，下一次 RunAtLoad/900 秒进程与文档规定的单次进程会直接执行漂移后的字节。manifest 文件仍可保存原内容，执行入口不会在发请求前发现不一致。现有机制形成“门点核验”，没有形成“每次真实执行前核验”。该缺口直接属于 release/runtime 字节绑定，能够让未复审代码进入真实 RSS 与私有 DB 路径，定为 P1。

最小修复：将 plist 与 runbook 的直接 collector 入口统一替换为一个 fail-closed verified launcher；通过已固定的外部 release-manifest SHA 启动，先对 manifest 文件、当前 18 文件、递归生产依赖和目标 Node 字节重算并核对，成功后再动态导入 collector。launcher 自身必须进入外部锚定的 release 闭包。核验失败时应在打开 RSS DB、claim run 或发出网络请求前退出。修复后冻结新 SHA，并只复审该入口及其 manifest/plist 绑定。

## 5. 四层放行结论

| 层级 | 结论 | 依据 |
|---|---|---|
| 1. 提交 deployable release | **不放行** | 当前候选仍含 P1-N01；不得把本组字节标记为可部署 release。修复可形成新的精确提交候选。 |
| 2. M1 prepare | **不放行** | prepare 会固化仍带直接 collector 入口的 plist/runbook 候选；应先修复并重新冻结 SHA，避免在 M1 建立待废弃部署身份。 |
| 3. 单次真实运行 | **不放行** | runbook 直接执行 collector，运行前没有重新核验外部锚与当前闭包。 |
| 4. 900 秒 load | **不放行** | launchd 每次直接执行 collector，resume 后的运行树漂移不会在真实 I/O 前被拦截。 |

当前用户授权与任务中的实施意图不替代 P0/P1 清零门。自动发布与公网 Admin 保持关闭。
