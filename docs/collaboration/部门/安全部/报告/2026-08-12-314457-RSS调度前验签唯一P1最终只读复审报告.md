## 3. P1-N01 关闭证据

### 3.1 wrapper 进入完整闭包

- release manifest 的显式运行文件清单加入 `scripts/rss-scheduled-run.ts`（`app/src/server/rss/release-manifest.ts` 第 16–36 行）；运行文件逐项绑定 mode、size 与 SHA（第 97–112 行）。
- release 回读以外部 expected SHA 核对 manifest 原始字节，并重算当前运行文件、递归依赖、Node 与确定性 root（第 252–306 行）。因此 wrapper 与 collector、验证器、依赖和 Node 共用一个外部锚定闭包。
- deployment manifest 单独记录 scheduled wrapper artifact（`app/src/server/rss/deployment.ts` 第 88–95、372–379 行）；回读重新生成 manifest、plist 与 artifacts 并逐字比较（第 389–420 行）。

### 3.2 外部锚传递成立

- installer 先从 `RSS_EXPECTED_RELEASE_MANIFEST_SHA256` 取得统筹外部锚，调用 release verifier 核对实际 manifest；通过后才计算该文件的实际 SHA（`app/scripts/rss-install-macos.ts` 第 73–80 行）。
- 同一个已核验实际 SHA 被用于生成 plist、deployment manifest 及回读（第 92–95 行），没有从待验证 deployment manifest 中取得信任锚。
- plist 以 `/usr/bin/env -i` 建立闭合环境，注入 `RSS_RELEASE_MANIFEST_SHA256=<已核验SHA>`，固定 Node，最终入口为 `scripts/rss-scheduled-run.ts`（`app/src/server/rss/deployment.ts` 第 268–287 行）。LaunchAgent 不再直接执行 collector。

### 3.3 验证先于 collector、业务 DB 写与外联

wrapper 的静态调用顺序为：

1. 拒绝附加参数，并要求外部锚是一个 64 位小写 SHA-256（`app/scripts/rss-scheduled-run.ts` 第 18–24 行）。
2. 校验固定主机/app root/Node 门（第 26–27 行）。
3. 以同一个外部锚重验 release manifest 与当前完整闭包（第 28–32 行）。
4. 重验 deployment manifest、plist、wrapper/collector artifacts、DB/日志权限（第 33 行；`deployment.ts` 第 389–420 行）。
5. 以 `readOnly: true` 打开固定私有 DB，在该连接执行完整 `assertRssSchema` 后关闭（`rss-scheduled-run.ts` 第 35–40 行）。
6. 上述步骤全部成功后才动态导入 collector（第 42 行）。wrapper 顶层没有导入 parser、transport 或 collector。

collector 的业务写连接、run claim、DNS 与 HTTP 路径均位于其模块执行阶段；动态 import 之前不可达。前置校验抛错时，`runSafeCli` 的默认 external-call 计数器返回 0，并输出脱敏失败收据及非零退出状态（`app/src/server/security/cli.ts` 第 45–57 行）。因此 P1-N01 所要求的“每次真实执行前验签、失败时 `externalCalls=0`”在静态调用图上闭合。

### 3.4 单次与 900 秒入口一致

- runbook 的单次命令传入 `RSS_RELEASE_MANIFEST_SHA256` 并执行 wrapper（runbook 第 68–84 行）。
- 900 秒路径说明 resume 先执行原有完整身份/schema/状态门，LaunchAgent 的 RunAtLoad 与每次 900 秒触发均进入带同一锚的 wrapper（runbook 第 107–115 行）。
