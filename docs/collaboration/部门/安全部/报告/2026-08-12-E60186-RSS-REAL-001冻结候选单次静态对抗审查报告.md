## 3. P1

### P1-01：`stop_epoch` 没有绑定 claim/finalize，停采后在途成功响应仍可提交

accepted ADR 要求 source 带 `stop_epoch`，回退时先递增 epoch、卸载采集器，并确认停止后无新增 run（ADR 第 42、46、72–73 行）。实现虽然从 source 读出 `stopEpoch`（`repository.ts` 第 173–185 行），`ClaimedRssRun` 却只含 run/slot/时间，不含已领取 epoch（`types.ts` 第 133–138 行）；`claimRun` 返回值也没有 epoch（`repository.ts` 第 188–227 行）。三个 finalize 入口只校验 run 仍为 `running`（`repository.ts` 第 85–91、241、329、358 行），成功路径未重新检查 `source.enabled` 或 `source.stop_epoch`，随后直接写候选、validator 与成功游标（第 245–318、330–335 行）。

静态可达序列为：run 在 epoch N 领取 → 运维递增 epoch 并停源 → 在途 200/304 返回 → finalize 仍提交。该行为破坏紧急停采和回退边界，属于错误停采 P1。

最小修复：claim 时捕获并绑定 `claimed_stop_epoch`；所有成功 finalize 在同一 `BEGIN IMMEDIATE` 事务内先执行 `enabled=1 AND stop_epoch=claimed_stop_epoch` 的条件校验/CAS。条件失配时保持候选与 validator 零写入，把该 run 收口为固定 `SOURCE_STOPPED` 失败收据。补一条“claim 后递增 epoch、随后收到 200”负例，断言候选、validator、success cursor 均不变。

### P1-02：IPv6 分类器把合同要求拒绝的特殊/文档地址判为 public

accepted ADR 要求 DNS 任一结果属于保留/文档地址或 IPv4-mapped IPv6 时整体拒绝（ADR 第 33 行）。`isPublicIpv6` 只按首个 hextet 接受整个 `2000::/3`，随后仅用字符串前缀排除少量地址（`transport.ts` 第 57–72 行）。因此代码会把 `2002::/16` 6to4、`3fff::/20` 文档地址，以及 `/28` 实际覆盖范围内但不以字面量 `2001:10:`/`2001:20:` 开头的地址判为 public。通过该函数的首个 DNS 地址会直接进入 pinned lookup（`transport.ts` 第 234–275 行），TLS 校验发生在发起目标连接之后，无法消除对特殊地址 443 端口的越界连接。

最小修复：改为对解析后的 16-byte 地址执行 CIDR 判定，使用冻结的完整非全球可达/特殊用途拒绝表；至少覆盖 6to4 `2002::/16`、文档 `2001:db8::/32` 与 `3fff::/20`、ORCHID 的完整 `/28`、mapped/translated、loopback、unspecified、ULA、link-local 与 multicast。所有 DNS 结果逐个校验，任一命中即整体拒绝；新增每个边界首尾地址的静态向量。

### P1-03：拒绝响应的 drain 无大小和总时限，单次 CLI 可长期不退出

accepted ADR 要求总计 10 秒超时和超过 1 MiB 立即中止（ADR 第 34–35 行）。实现收到 redirect、429、stop status、5xx、其他非 200 或 200 头部校验错误后进入 catch，调用 `response.resume()` 再 `fail(error)`（`transport.ts` 第 293–327、357–360 行）。`fail` 会立即清除全部 timer（第 243–261 行），其中包括 10 秒 total timer（第 363–377 行）；非 200 响应也没有字节计数。远端可持续发送 chunked 错误响应或保持连接不结束，Promise 已失败但 socket 仍在无界 drain，Node 进程可能长期不退出，阻断 M1 单次运行和后续调度。

最小修复：由于 `agent:false` 且无需复用连接，所有拒绝状态/头部失败路径应立即 destroy response/request 后再结算；若选择 drain，必须保留同一个绝对 10 秒 deadline、应用 1 MiB 总字节上限，并等到 bounded end/close 后才返回。补 redirect/429/5xx 持续 chunked 与不结束连接的负例。

### P1-04：部署与 LaunchAgent 硬门尚未形成可审核产物

accepted ADR 要求同一 manifest 绑定 migration/schema/profile/DB path，并要求精确 commit、release、LaunchAgent plist hash；安全与测试 `P0=0/P1=0` 后才能初始化、单次受控真实运行，核对后才能启用 900 秒调度（ADR 第 50、70–73 行）。开发报告明确记录：没有 LaunchAgent、M1 私有目录、部署 manifest、release/commit/plist hash、单次运行或停机回退证据（开发报告第 52–58 行）。本次冻结候选也未包含这些对象。

最小修复：先关闭前三项 P1，再提交精确部署候选，至少绑定 commit/release/migration/schema/profile/DB path/plist hash、0700/0600 与 link 拒绝、独立进程、900 秒节奏、stop epoch 操作、受控单次运行及 synthetic 零漂移收据。取得测试和安全独立 `P0=0/P1=0` 前保持 LaunchAgent 未加载。

## 4. P2

### P2-01：I/O 门前失败的 `externalCalls` 被过报为 1

CLI 在调用 transport 前先把 `networkAttempted=true`（`rss-collect-once.ts` 第 65、72–73 行）；transport 随后才检查 `RSS_REAL_IO === "true"`（`transport.ts` 第 203–208 行）。因此 `RSS_IO_DISABLED`、代理环境拒绝或请求 validator 前置拒绝会在 CLI catch 中被记为 `externalCalls=1`（`rss-collect-once.ts` 第 82–95 行）。这与开发报告“显式 I/O 门前失败保持 0”的陈述冲突（开发报告第 64 行）。该偏差是保守过报，没有形成越界外联或虚假 no-egress，定为 P2。

最小修复：把“transport 已真实进入 DNS/连接”作为显式阶段结果，或在 catch 中优先使用 transport 返回的 `RssError.externalCalls`；收到 HTTP 响应后再用独立 `responseReceived=true` 保证后续 parser/finalize 错误记 1。
