## 3. 官方规范与 CLI 能力核对

### 3.1 官方字段 PATCH 合同

飞书官方[更新表单问题接口](https://open.feishu.cn/document/server-docs/docs/bitable-v1/form/patch)定义了唯一必要的 HTTP 形状：

```text
PATCH https://open.feishu.cn/open-apis/bitable/v1/apps/:app_token/tables/:table_id/forms/:form_id/fields/:field_id
```

官方文档列出 `pre_field_id`、`title`、`description`、`required`、`visible` 和 `rich_description` 请求字段；其中 `visible=false` 时不允许同时更新其他字段。字段 ID 代表表单问题所绑定的底层表字段。该约束解释了隐藏字段必须使用只有 `visible` 的请求体，也解释了仅使用 typed `+form-questions-update` 无法完成本合同的隐藏动作。

### 3.2 官方表单读回与分享状态

官方[获取表单元数据接口](https://open.feishu.cn/document/server-docs/docs/bitable-v1/form/get)可读取表单名称、描述和分享状态。官方[更新表单元数据接口](https://open.feishu.cn/document/server-docs/docs/bitable-v1/form/patch-2?lang=zh-CN)说明了 `shared`、`shared_limit` 和 `submit_limit_once` 的语义：`off` 仅限受邀者，`tenant_editable` 允许组织内链接持有者，`anyone_editable` 允许互联网链接持有者。此任务只读确认 `shared=false`，禁止借字段 PATCH 例外修改这些元数据。

### 3.3 本机官方 CLI 证据

- `/opt/homebrew/lib/node_modules/@larksuite/cli/package.json` 标记包名 `@larksuite/cli`、版本 `1.0.68`、官方仓库 `larksuite/cli`；本机帮助将 `api` 明确描述为任意 Lark API 请求的 raw HTTP escape hatch，带 `--data`、`--as user|bot`、`--dry-run` 等参数，并标注写风险。
- 本机 `base +form-questions-create --help` 只接受题目 `title/type` 等创建参数，没有既有底层 `field_id` 绑定参数；将其用于本表会有重复底层字段风险。
- 本机 `base +form-questions-update --help` 要求问题 ID，但支持字段只有 `title`、`description`、`required` 和选择项显示方式，没有 `visible`。
- 本机 `base +form-questions-delete --help` 将删除标为 `high-risk-write` 并要求 `--yes`；该命令禁止使用，因为它会破坏表单题目与底层字段的绑定。
- 以上命令语义可在官方 [larksuite/cli 源码仓库](https://github.com/larksuite/cli)及其 [Base shortcut 源码索引](https://pkg.go.dev/github.com/larksuite/cli/shortcuts/base)交叉核对。本报告只引用本机帮助和官方源，不把 CLI 安装当成远程授权。

## 4. 唯一 raw API 例外：精确路径、方法、字段和请求体

### 4.1 路径白名单

运行时由受控执行器完成如下等值约束：


### 4.5 CLI 执行形状与顺序

后续若发生重复配置或只针对已读回字段进行修复，唯一允许的命令形状为 `lark-cli api PATCH <上节固定路径> --data <上节固定 JSON> --as user --dry-run` 预览后，再由受控执行器去掉 `--dry-run` 执行同一请求。命令必须串行，每一个请求完成后立即只读回查；不允许 `--as bot`、`--yes`、批量拼接多个 PATCH、并发调用或把 JSON 写进未经审核的文件。

## 7. 必测失败路径与停止条件

### 必测失败路径

1. **错误 field ID 或表单 ID：** 返回 `FormFieldNotFound`、资源不唯一或读回 ID 不一致时停止；不得改用题目创建、删除或其他 Base。
2. **隐藏请求体越界：** `visible=false` 之外出现任何键、目标字段不在五项隐藏集合，或 raw_url/capture_note body 值有一处不符时停止。
3. **写冲突/未知结果：** 遇到 `1254291 Write conflict`、超时或未知响应时，先只读回；只在目标状态尚未生效时串行重试同一白名单请求，不能并发或换命令。
4. **表单边界漂移：** 可见题目多于两项、底层字段少于 9 个、`shared` 不是 `false` 或出现分享链接时停止，禁止导入和真实提交。
5. **批量记录不确定：** 现存子集字段不完全正确、批次重复/越批、分页不完整或状态不明时停止，不补缺、不覆盖、不删除。

### 总停止条件

- Base token 哈希、标题、手机捕获表、表单或七个字段任一不精确；出现 open_id/appId/认证原始 JSON进入仓库；身份不是 `user`。
- 任何 raw API 请求越出固定 PATCH 路径、方法、七字段或请求体；出现 bot、`--yes`、delete、权限/分享修改或并发写。
- 官方文档约束、CLI 版本或本地回读互相矛盾，无法证明底层九字段仍保留。
- `shared=false` 无法读回，或发生真实表单提交、workflow、自动入主表、真值/provider/Collector/采集/发布切换。
- 首次导入前后 payload、批次键、默认值、字段数量或对账结果任一不一致。

## 10. 错题自检与结论

- **raw API 边界：** 没有把 generic API 的存在写成通用授权；例外只覆盖一个固定官方字段端点，其他 raw API 继续禁止。
- **字段保留：** 没有把隐藏题目误写成删除字段；`capture_id`、`captured_at` 保持底层字段且不新增表单题目。
- **数据敏感性：** 没有把 Base token、open_id、appId 或认证原始 JSON写入仓库；报告只保留 token SHA-256 和必要的非凭证资源 ID。
- **业务边界：** 没有把用户对 M3 资源和影子记录的授权扩展成真值、provider、Collector、采集、启用、同步或发布授权。
- **导入门禁：** 没有把 dry-run 当成真实写入；首次 59 条只在读回、ACL、字段、payload 和停止条件全部通过后允许继续。

**结论：条件式 PASS。** 既有“禁 raw API”门禁仅在上述固定 Base（以标题和 token SHA-256 绑定）、固定手机捕获表、固定表单、七个字段、`PATCH` 方法和三类精确 JSON body 上增加窄例外；其余 raw API 和高风险操作继续禁止。首次 59 条 `enabled=false` `record-batch-create` 可以继续，但必须遵守第 6 节的写前核验、串行执行、先读回恢复、批次对账和停止条件。
