## 5. P1-1：npm 附加参数可覆盖固定 loopback 命令配置

当前命令为：

```json
{
  "dev": "node --experimental-strip-types scripts/runtime-bootstrap.ts && next dev --hostname 127.0.0.1 --port 3000",
  "start": "node --experimental-strip-types scripts/runtime-bootstrap.ts && next start --hostname 127.0.0.1 --port 3000"
}
```

`npm run <script> -- <args>` 会把附加参数放到 script 末尾，形成：

```text
next dev --hostname 127.0.0.1 --port 3000 --hostname 0.0.0.0 --port 61234
next start --hostname 127.0.0.1 --port 3000 --hostname 0.0.0.0 --port 61234
```

使用项目本地 Next 16.2.11 内置 Commander 做无监听解析，结果为：

```json
{
  "parser": "next/dist/compiled/commander",
  "devProfile": { "hostname": "0.0.0.0", "port": "8080" },
  "startProfile": { "hostname": "::", "port": "8081" }
}
```

本地 Next CLI 源码随后把 `options.hostname`、`options.port` 传给 `nextDev()`/`nextStart()` 和服务器启动链。bootstrap 只校验 canonical env；它没有读取或拒绝 npm 附加 argv。由此可得：

```bash
npm run dev -- --hostname 0.0.0.0 --port 61234
npm run start -- --hostname 0.0.0.0 --port 61234
```

可让实际服务配置偏离已校验的 `127.0.0.1:3000`，违反 accepted R2 的实际 bind 与 canonical origin 必须一致要求。该问题需要本地命令执行前置，本轮没有证明无前置的远程利用，故判 P1。

### 最短修复出口

1. 用单一 Node wrapper 拥有完整启动生命周期，并在任何 readiness/Next import 前拒绝 `process.argv.slice(2)` 中的附加参数。
2. wrapper 自己生成固定 host/port；避免让 npm `--` 参数落到最终 Next CLI。
3. `dev`、`start` 都覆盖长参数、短参数、重复参数、positionals、`--` 与未知参数负例。
4. 每个负例须非零退出、无端口监听、无 `.next`/DB 副作用、无 stack/路径泄漏。
5. 正常命令仍按 Node24 → env/profile → DB/fixture readiness → 固定 loopback 的顺序执行。

## 7. P0：accepted R5 同 UID 强 TOCTOU 保持独立用户门禁

修订实现已经加入以下防护：

- app root、DB root、parent 与 final 的 owner/type/mode/identity 检查；
- DB 文件 `O_NOFOLLOW` guard 与 SQLite 打开后的 inode/location/descriptor 交叉核对；
- DB 及 sidecar 的 single-link、owner-only mode 检查；
- 异常 sidecar 在 SQLite 打开前拒绝；
- health 公开 `filesystemIsolation=local_trusted_user`、`toctouProof=false`。

这些措施显著缩小普通误配、symlink、hardlink 与弱权限攻击面。Node `DatabaseSync` 仍要求 SQLite 按 pathname 独立打开 DB，并自行创建/打开 WAL 与 SHM。恶意同 UID 进程可与受审进程共享文件系统权限，当前纯 TypeScript 代码没有提供 dirfd/openat/VFS、受控 broker、sandbox 或等价不可替换证明。

本轮遵守统筹任务边界，没有运行恶意同 UID 竞争式替换。accepted R5 当前仍要求强 TOCTOU 拒绝，因此报告保留 P0=1。可选后继路径：

- **方案 A：保留 accepted R5。** 引入能把 DB、parent 和全部 sidecar 绑定到稳定文件系统能力的实现，并完成 Darwin 竞争复验。
- **方案 B：用户确认收窄威胁模型。** 明确 owner-only `0700/0600`、本地受信任单用户环境，不把同 UID 恶意进程纳入 VS-0；建立 successor ADR，并保留 `toctouProof=false` 的公开声明。

在用户确认和 successor ADR 生效前，安全报告不能自行采用方案 B。

## 8. P2 与后置边界

### P2-1：bootstrap 子进程设置的 umask 不会传给 Next 进程

`openSafeDatabase()` 调用 `process.umask(0o077)`，能保护该 Node 进程创建的 DB 文件族。package scripts 使用：

```text
node scripts/runtime-bootstrap.ts && next ...
```

shell 会依次创建两个同级子进程。前一个 Node 进程修改自身 umask 后退出，后一个 Next 进程仍继承 shell 原始 umask。机械收据：

```text
bootstrap_umask=77
next_process_inherited_umask=22
```

因此 accepted R5 的“启动入口设置 `umask(077)`”尚未覆盖 Web/Next 整个生命周期。建议在统一启动 wrapper 的第一条可执行逻辑设置 077，并由同一进程启动 Next。

### P2-2：lowercase proxy 仍保留在进程环境

uppercase `HTTP_PROXY/HTTPS_PROXY/ALL_PROXY/NO_PROXY` 已被拒绝。`BLOCKED_NAMES` 大小写敏感；`http_proxy/https_proxy/no_proxy` 不属于应用前缀，因此 runtime config 会接受并保留。无网络探针结果：

```json
{"status":"accepted","bind":"127.0.0.1","port":3000,"lowercaseProxyPresent":true,"externalIo":false}
```

当前业务源码没有真实外联能力，该项在 VS-0 记 P2；它应随 R12 的最小进程环境和 OS/进程 no-egress 一并收口。

### P2-3：统一基础安全响应头仍未配置

health route 当前设置 `cache-control=no-store`、JSON content type 和 local scope；`next.config.ts` 没有统一 CSP、`X-Content-Type-Options: nosniff`、frame 限制、Referrer-Policy 与 Permissions-Policy。当前 VS-0 没有不可信公开内容，故保持 P2；首个真实 UI/API 和 VS-3 公开投影验收前必须收口。
