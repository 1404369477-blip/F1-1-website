## 4. Serve app-cap 代码合同裁定

### 4.1 raw header 与闭集 JSON

`server.ts:49-74,101-147` 直接使用 `IncomingMessage.rawHeaders`：

- 名称按 ASCII 大小写不敏感收集，每个 raw field 单独计数；目标头缺失或重复时 `single()` 返回 null，不能依赖 Node 的 normalized merge。
- legacy `x-f1-approved-device-ref` 先按 raw 名称扫描；出现一次或多次即通用 `401 ADMIN_SESSION_REQUIRED`。扫描没有读取对应 value。
- login 要求单 field、UTF-8 `3..320 bytes`、可见 ASCII；app-cap 要求单 field、UTF-8 `1..4096 bytes`。
- `JSON.parse` 后顶层和参数对象均要求 `Object.getPrototypeOf(...)===Object.prototype`，array/null/非普通对象失败。
- 顶层唯一 key、唯一 array item、参数唯一 `sourceRef`、43 字符 base64url 闭合；额外/未知 key、未知字段、0/多 item失败。
- 原始 JSON 中的对象 key 计数必须精确为 2，阻止重复 JSON key被 `JSON.parse` last-wins 折叠后冒充闭集对象；`__proto__`/`constructor` 等未知 key也无法通过精确 capability key与参数字段检查。
- login 与 sourceRef 在同一 trusted row 中逐字匹配，错 login/ref 组合不回退到 login-only。

成功输出只含 `operatorRef` 及 login/sourceRef 的 SHA-256 前 16 hex 脱敏引用；原始值未进入 challenge/session/API响应。

### 4.2 challenge、session 与 fresh 三元绑定

- `auth.ts:164-186` 的 bootstrap/login/fresh challenge key固定为 purpose + `(operatorRef,deviceRef,tailnetUserRef)`；另一 source 无法 consume 原 challenge。
- `security.ts:220-271` 会话记录持久绑定同一三元组，每个受保护业务请求均经 `authorizeBoundIdentity()` 与当前请求重算三元组做常量时间比较。
- `auth.ts:293-367` 的 fresh options/verify 先做 bound-session 检查，fresh challenge也绑定三元组。
- `security.ts:306-390` fresh re-auth 轮换旧 session，并让 fresh receipt绑定新 session digest、operation、action与resource hash；跨 source复制 cookie/fresh receipt时，会先在当前身份的 bound-session门失败。
- Mac/iPhone的两个唯一 sourceRef派生两个不同 deviceRef；同一login仍产生相同tailnetUserRef，operatorRef由同一manifest行给出。

app-cap 本地代码合同在上述范围内 CLOSED。

### P2-01：legacy 头拒绝缺少合同指定的内部脱敏 reason

accepted ADR 要求 legacy 头存在时，对外通用401，内部只记录脱敏 reason `ADMIN_UNTRUSTED_DEVICE_HEADER_PRESENT`，且头值不入日志。当前实现完成了401与不读值，但 `server.ts` 没有发出该内部 reason，也没有接入相应的脱敏安全日志接口。

该缺口降低目标机排障与拒绝原因可观测性，不改变身份、session或授权决定，未暴露头值，因此定级 P2。后继可在 parser 抛出通用外部错误前，仅向既有 owner-only redacted logger发送固定枚举 reason；不得记录 raw header/value/login/sourceRef。
