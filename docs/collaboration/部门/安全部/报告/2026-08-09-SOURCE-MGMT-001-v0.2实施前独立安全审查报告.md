## 3. 分级发现

### P1-1：local Admin 安全合同未被唯一、不可漂移地吸收

产品 v0.2 仅写明：继承 local session 合同、只接受一个 canonical loopback origin、拒绝 forwarded headers/authority 歧义、mutation 使用 TTL 5 分钟的一次性 CSRF。冻结输入表没有列出既有安全候选的任务、路径或 SHA，也没有逐项复述其关键 predicates。

这不足以为开发提供唯一机械输入，至少留下以下实现分歧：

- 框架规范化前的 raw HTTP/1.1 request-target、Host multiplicity 与 authority 如何校验；
- duplicate/comma Host、Host 与 `:authority` 同时出现、absolute-form、HTTP/2/h2c、normalized/raw authority 不一致时的拒绝顺序；
- IPv4 与 IPv6 canonical origin 二选一、peer loopback 与 proxy-header 拒绝；
- session 的 32-byte CSPRNG、单活动会话、仅进程内存、单调时钟 TTL、刷新轮换及重启失效；
- CSRF 的 32-byte CSPRNG、session/method/exact-path/canonical-body-hash 绑定、issued→consumed 原子转换、并发重放、失败或业务回滚后不恢复、tombstone 与多进程拒绝；
- 所有安全拒绝前后 Source、Outbox、TaskEnvelope、receipt 与 AuditEvent 的业务增量必须为 0。

同一份 v0.2 同时声称自己是开发唯一输入，因此“继承”一个未 pin 的候选会产生实际安全歧义。此项阻断实施。

**最小整改：** v0.3 successor 必须把 `TASK-20260802-6F7563` 的安全候选以精确路径和 SHA `e043705915c4c2489cdf3cb178677b4d5dc753781c98e8c10e7886d2a5462218` 写入冻结输入表，并明确上述 predicates 为规范性 MUST；`SRC-V2-SECURITY-13` 应逐项覆盖 raw authority、session、nonce 原子消费、并发重放和零业务增量。

### P1-2：command/business identity 的生成与校验合同未完全闭合

产品 v0.2 对 `command_operation_id` 只规定可接受字符和长度，对 `command_idempotency_key` 写明“≥128 bits entropy”；对首次 activation 新建的 `business_operation_id` / `business_idempotency_key` 及复用路径，没有固定生成方、编码、字节数、域分离、碰撞处理和可机械校验规则。数据合同提供 UNIQUE 约束与复用关系，这能拒绝已发生的重复，不能证明调用方提交的字符串具有承诺的熵，也不能消除不同 identity 域之间的生成歧义。

风险包括低熵 command key 导致可预测/碰撞的幂等域、command 与 business identity 被错误复用、并发 activation 产生冲突后出现不一致恢复逻辑。数据库唯一键使其倾向 fail-closed，但实施合同仍可能把有效用户操作错误结算或错误关联，因此按 P1 阻断。

**最小整改：** successor 应为 command、business、task、lease 各 identity 固定生成责任、域分离前缀、CSPRNG/确定性生成方式、最小原始随机字节数、base64url/hex canonical 编码、最大长度、服务端语法检查、唯一键冲突行为与重试规则。客户端生成的 command key 若继续保留，必须说明服务端无法验证“熵”，安全保证应落到可信生成器及其固定测试向量；business identity 只能由服务端在首次 activation 事务内生成，恢复/requeue 必须逐字复用。

### P2-1：截断 source_id 具有低概率可用性碰撞面

local `source_id` 使用 SHA-256 前 24 个 hex 字符，即 96 bit。合同已要求对 effective baseline/local identity 与 canonical URL 查重并整笔拒绝，因此没有证据表明碰撞可形成第二业务真值；剩余风险主要是极低概率或刻意构造输入导致新增操作被拒绝。建议 successor 明确碰撞 reason code、零写与用户改用不同 canonical input 的恢复出口；若未来输入从 synthetic 扩至不可信高规模来源，应重新评估位数。此项不单独阻断当前本地 synthetic 合同。

## 4. 已验证的闭合项

以下结论只针对合同文字与 ACK 数据拓扑：

1. **候选完整性：** 两个任务固定 hash 均精确匹配，无候选漂移。
2. **单真值边界：** 唯一 `source-management-synthetic` profile、单 writer、单 handle；禁止 ATTACH、跨 profile 查询、public DB mutation credential 与共享挂载。
3. **baseline：** 冻结 59×39、全部 disabled；baseline 不 seed 到 local DB，任何 baseline source mutation 在事务前固定 403，文件/root/count/local DB 零变化。
4. **请求体：** mutation 使用 canonical-json-v1 exact UTF-8 bytes、`additionalProperties=false`、上限 16 KiB；URL 只允许 `https://synthetic.invalid/...` 且只做字符串验证。
5. **command/业务分域：** 六条明确 mutation lane；Add/Validate/Stop/Retire 不创建 Outbox/TaskEnvelope，首次 Activate 创建唯一业务事实，dead-letter requeue 复用原业务 operation/key/job。
6. **CAS 与 five-fence：** Source version/hash、两个 Source epoch、三个 runtime epoch、canonical state 与 enabled 共同参与 CAS；影响行数不等于 1 时全回滚。
7. **stop/retire/recovery：** stop 同事务提高 config/safety epoch 并使旧 lease 失效；retire 保留历史；dead-letter requeue 递增 generation、重新验三门/stop/fence，失败零业务增量。
8. **response loss：** commit 后响应丢失只允许 GET 原 command operation 再刷新 Source，禁止盲换 operation/key 重发。
9. **公开面：** public 只读投影不拥有 Admin route、主库路径或写凭据；SOURCE-MGMT 不得写 public DB。
10. **no-egress 与脱敏：** 每入口要求 runtime no-egress ready；DNS/HTTP/TLS/raw socket/proxy/外部 subprocess/provider 尝试均失败关闭；日志/AuditEvent 禁止 Cookie、CSRF、body、完整 URL、真实 ID、stack、SQL、路径和 secret。

## 6. 真实用户失败与恢复出口

| 场景 | 用户可见结果 | 唯一恢复动作 |
|---|---|---|
| session/Host/Origin/CSRF 拒绝 | 固定 401/403 reason；不回显输入；零业务写 | 返回 guard shell；重新建立合法 session，重新签发并确认新 CSRF |
| body/canonical/size 错误 | 400/413/415/422；保留非敏感表单 | 用户修正后重新确认；使用新 command identity 与 CSRF |
| stale/CAS/fence 冲突 | 409；不覆盖当前值 | 重新 GET Source 与 operation，展示差异后由用户再次确认 |
| response unknown | 显示“结果待确认” | GET 同 `command_operation_id`，再刷新 Source；禁止自动重发 |
| storage busy/profile not ready/no-egress | 503；功能关闭 | 先读回 operation；待唯一 profile/no-egress/存储恢复并验证后再由用户操作 |
| baseline mutation | 403 `ADMIN_M3_SHADOW_DENIED` | baseline 保持只读；不得复制到 local 或提供绕过入口 |
| dead-letter | 保留原业务 identity 与完整历史 | 用户在三门/stop/fence 恢复后显式 requeue；新 command、原 business identity |
| identity/source_id collision | 固定 conflict；整笔零写 | 读回既有 receipt/Source；确认是不同输入后按闭合的碰撞规则处理，不盲重试 |
