## 5. P0-1：DB、父目录与 sidecar 稳定打开仍不满足 R5

### 5.1 代码事实

`app/src/server/db/database.ts` 当前分成两个不同打开对象：

1. `openStableDatabasePath()` 使用 `O_NOFOLLOW` 打开 `guardFd`，并比较 guard fd 与当时最终路径的 `dev/ino/nlink`。
2. `openSafeDatabase()` 随后调用 `new DatabaseSync(absolutePath)`，由 SQLite 再次按字符串路径解析并独立打开。
3. `DatabaseSync` 构造完成后，代码才重新检查 parent 和最终 DB 身份。
4. WAL 模式启用之后，代码才对 `-wal`、`-shm`、journal 和 backup 名称执行 `lstat`/权限检查。

最终文件 guard 能发现一部分 symlink/hardlink/regular-file 替换。它无法把 SQLite 实际打开的对象与 guard fd 绑定，也无法证明后验拒绝发生前没有边界外读取、创建或写入。嵌套 `.local/...` 路径没有用稳定目录句柄绑定 `.local` 根与每一级祖先；WAL/SHM/journal 也由 SQLite 独立按派生路径打开。

因此，accepted R5 所要求的以下安全性质尚未形成完整实现证据：

- `F1_DB_PATH` 实际打开对象始终位于允许根；
- root、parent、final 和 sidecar 在检查到使用之间不可被换位；
- `O_NOFOLLOW` 和原子创建覆盖 SQLite 的实际打开，而不只覆盖旁路 guard；
- 任何拒绝发生前都没有对边界外对象产生副作用。

### 5.2 判级与防御性修复

该问题直接命中 accepted R5，是本轮唯一 P0，阻断 VS-0 安全放行。

完整修复需要使用能够把 SQLite 打开绑定到稳定目录句柄/文件身份的方案，例如受控 broker、SQLite VFS、原生 `openat/O_NOFOLLOW` 边界或等价 OS 隔离；DB、WAL、SHM、journal 和 backup 必须处于同一受控文件族。

短期缓解至少包括：

- 启动时设置 `umask(077)`；
- 对 `.local` 根和每一级祖先记录并复核 `dev/ino/mode/nlink`；
- 打开前拒绝既有异常 sidecar；
- SQLite 构造前后复核 root、全父链和最终文件；
- 写事务后、checkpoint/close 前重新复核 sidecar 权限与身份；
- 检查失败时安全关闭，并只清理能够证明属于本次创建的临时文件。

这些措施能缩小窗口，仍不足以单独证明强 TOCTOU 已消失。如果项目选择依赖 owner-only `0700` 目录并排除同 UID 文件系统竞争，需要通过新 ADR 明确缩小威胁模型，并把当前强 R5 标为未满足；在此之前不能把该 P0 降为通过。

## 6. P1-1：migration 可将预占伪 schema 登记为成功

`0001_local_foundation.sql` 和 `0002_source_fixture.sql` 对 application-owned table/index 使用 `CREATE ... IF NOT EXISTS`。`migrateDatabase()` 会校验 migration 文件顺序、ledger 记录、文件 hash 和 `user_version`，没有核对迁移后实际存在的 table/index/constraint 是否由相应 SQL 创建。

固定 Node24 的独立临时负例结果为：

```json
{
  "result": {
    "applied": ["0001_local_foundation.sql", "0002_source_fixture.sql"],
    "userVersion": 2,
    "sqliteVersion": "3.53.1"
  },
  "columnCount": 40,
  "hasAttackerExtra": true,
  "ddlHasChecks": false
}
```

这证明 ledger/hash 目前只证明 SQL 文件被登记，不能证明实际物理 schema 符合合同。相同缺口也会影响预占 index、seed ledger 约束和 migration 后 schema 漂移。

最小修复：

1. 首次应用前拒绝所有预存在的本 migration-owned table/index，或移除关键对象的 `IF NOT EXISTS` 让预占对象直接使事务失败。
2. 为每一 migration 记录并验证实际 schema fingerprint。
3. fingerprint 至少覆盖 `sqlite_master.sql`、列名/顺序/类型、`NOT NULL`、PK、唯一与普通索引、partial-index predicate、`CHECK`、ledger 表结构。
4. 每次启动及 seed 前复核 fingerprint；不能只在首次创建后检查。

该项为 VS-0 必修。

## 7. P1-2：Web 启动安全门禁和 readiness 没有接入实际运行

`app/package.json` 的 `dev`、`start` 直接执行 Next。`verify:env`、`db:migrate` 和 `seed:fixtures` 是分离命令，没有成为 Web 进程启动的强制前置。

`app/src/server/health.ts` 无条件返回：

- `status=ready`
- `dataGate=accepted-local-fixture`
- `migration=source-fixture-0002`
- `seed=59-source-disabled`
- `network=disabled`

`/api/health` 与首页没有加载 runtime config，也没有打开数据库检查 `user_version`、ledger、schema、seed 或 projection hash。因此错误 Node、数据库缺失、未迁移、未 seed 或数据库已漂移时仍可能显示 ready；Next CLI 的绑定参数也没有与 canonical loopback profile形成同一个启动门。

最小修复：

1. 建立唯一的 `dev/start` wrapper，强制执行精确 Node、canonical env、profile、实际 loopback bind 和数据库 readiness。
2. health 使用只读检查服务，验证 exact `user_version`、migration ledger、schema fingerprint、seed ledger、59 行、59 disabled 与 projection hash。
3. 任一检查失败返回 `503` 和 `not_ready/degraded`；响应禁止包含绝对路径、SQL、堆栈和原始错误。
4. 首页和 API 必须复用同一个 readiness 服务。

该项为 VS-0 必修。

## 8. P1-3：fixture 安全校验和解析没有绑定同一份字节

`validateFixturePath()` 会执行 `lstat/realpath/stat/read/stat` 并返回路径、hash 和 size。后续 `readSourceFixture()` 又根据返回路径重新读取 schema、mapping 和 bridge；旧 M3 provider 也存在多次按路径读取。

硬编码 artifact hash 与最终 projection hash 为 bridge 提供了重要完整性保护，明显降低了持久数据注入风险。这组保护仍不能证明“被校验的文件字节”与“被 JSON 解析的文件字节”是同一个对象，也没有在重读前设置统一字节上限。

最小修复：

- 使用 `O_NOFOLLOW` 打开一次；
- 对同一个 fd 执行 `fstat`、字节上限检查、读取和 SHA-256；
- consumer 直接解析该 buffer；
- schema、mapping、bridge、M3 fixture 复用同一安全读取器；
- 读取完成后不再凭 `realPath` 二次打开。

该项命中 accepted R1 的 fixture TOCTOU 条件，为 VS-0 必修。

## 9. P1-4：日志边界未完全满足 R4

当前 logger 采用安全 key allowlist，能够删除明显的 Authorization、payload、body、header、stack 等字段，并限制字符串长度。仍存在以下合同缺口：

1. 未知或疑似 secret 字段被静默丢弃，没有产生 R4 要求的固定 redacted incident。
2. allowed key 的字符串值只检查 secret 关键词，没有拒绝 private URL、平台 ID 或藏在 `operationId`、`traceRef`、`reasonCode` 中的 opaque secret。
3. `externalCalls` 的任意有限 number 会被通用 number 分支先接纳，因此 runtime 输入可以记录非零值。

最小修复：

- 每类日志事件使用严格 runtime schema，`additionalProperties=false`；
- 未知/疑似敏感字段转为固定且不含原值的 `redacted_incident`；
- 为 trace、operation/task ID、reason code、hash 分别固定格式、长度和字符集；
- 拒绝 URL、平台身份与未识别 opaque 值；
- `externalCalls` 只接受数值 `0`。

该项为 VS-0 必修。

## 10. P1-5：R12 no-egress 尚无运行强制

`CAPABILITY_REGISTRY` 将 network 和 external write 标为 disabled；当前业务源码静态扫描没有发现主动外联调用。代码与 package scripts 没有 OS/进程 deny-all wrapper，也没有覆盖 DNS、HTTP、raw socket、`child_process` 和 proxy bypass 的负例及 redacted security event。

因此当前证据只能说明“审查到的业务源码没有显式外联调用”，不能证明“运行时无法外联”。Next、测试依赖、未来 worker 或新增代码仍具有系统网络与子进程能力。

范围边界：

- 完整 OS/进程 no-egress 可以按 Spec 明确留到完整 R12。
- 在完整 R12 收口前，health、页面和报告必须写 `network_enforcement=pending`，不得宣称运行隔离已验证。
- 最迟在 VS-1 mock worker 开工前完成，因为 worker 合同明确要求无 DNS、socket、subprocess 和外部工具。
- 如果 VS-0 继续保留 `network=disabled` 或以 R12 通过为验收陈述，本项继续阻断 VS-0。

## 11. P2

### P2-1：启动入口未设置 `umask(077)`

代码在显式创建目录和 DB 时传入 `0700/0600`，没有在进程最早入口设置 accepted R5 要求的 `umask(077)`。SQLite 临时文件及未来 worker 临时产物仍需要统一默认权限边界。建议随唯一启动 wrapper 一并修复，并在加载任何数据库或 worker 模块前执行。

### P2-2：环境变量拒绝覆盖仍不完整

精确 blocked-name 集合大小写敏感；常见 lowercase proxy 变量和部分云凭证命名不会被当前规则识别。该问题与缺少 no-egress 强制组合时风险增大。建议在 R12 中规范化环境变量名、对子进程使用最小环境 allowlist，并覆盖 lowercase proxy、CA 注入、云凭证和子进程环境继承负例。

### P2-3：导出 seed 边界不独立验证完整 migration 真实性

`seedSourceFixture()` 只要求 `user_version >= 2` 和两张表存在。当前 CLI 脚本会先执行 `migrateDatabase()`，因此正常脚本路径受到一定保护；其他 repository/测试调用方可以绕过 exact known version、ledger/hash 和 schema fingerprint。

建议建立统一 `assertDatabaseReady()`，由 Web、repository、seed 和 worker 共用，拒绝版本 ahead、ledger 缺失/重复、migration hash 漂移、schema fingerprint 漂移及受管对象增删。

### P2-4：基础响应缺少 R7 安全头

`/api/health` 当前只有 no-store、content-type 和 local scope；`next.config.ts` 没有统一 CSP、`nosniff`、`frame-ancestors` 和 `Referrer-Policy`。当前 VS-0 页面没有不可信内容，该项可留到 VS-3 首个真实公开页面/API 前完成。
