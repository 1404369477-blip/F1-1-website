## 3. P1

### P1-01：post-enable 异常没有统一、可审计的停采后置

**状态：OPEN。**

具体可达路径：

1. enable 在 `COMMIT` 后把 `committed=true`，随后才写 enable receipt并输出（第 512–528 行）。这两步任一异常会调用 `stopAfterEnableFailure()`，但返回值被丢弃，未解析 stop receipt、未核对exit/status，也未最终回读source/job（第 529–540 行）。stop timeout、进程错误或非零退出均可能留下enabled=1/epoch3。
2. `run-stop` 开始时 source 已enabled。job状态、private DB/schema、running状态或slot-count检查的异常路径会直接抛错且没有stop；只有“slot已前进”分支尝试stop，该分支同样丢弃stop结果（第 546–571 行）。
3. wrapper与stop正常调用顺序正确，但两个进程返回后先检查wrapper error/signal，再检查stop（第 596–606 行）。wrapper 20秒timeout、signal或spawn错误会在第605行直接失败，跳过stop receipt解析、写盘、验证及最终source/job回读（第 607–625 行）。
4. wrapper stdout不是唯一JSON、stop stdout异常、任一receipt写盘失败时，也没有统一finally后置。真实请求可能已经发生，source是否disabled、epoch是否为4及job是否unloaded将失去执行器内的持久化审计。

影响：当前脚本不能满足“enable后任何异常均停采”和“真实请求后始终有可审计stop后置”。RSS job虽然按前置应为unloaded，source仍可能保留enabled；后续误执行wrapper即可继续真实I/O。定为P1。

最小机械修正：把 enable commit 到 stop确认之间收敛为一个不可分割的受控阶段，或在所有post-enable代码外包一层单一 `try/finally`。一旦enable commit成功，`finally`必须确保 `rss-control stop`恰调用一次；无论wrapper timeout、无stdout、解析或写盘失败，都先解析/持久化stop结果并独立回读source/job。只有disabled、epoch4、明确unloaded三项同时成立才离开临界区。stop超时/异常时必须走预先定义的紧急DB refence+bootout+最终回读机械分支；仍无法确认则输出固定 `STOP_UNCONFIRMED`、保存已有进程结果hash并阻断，禁止声称完成。wrapper错误应在stop证据持久化之后再上抛。

### P1-02：slot边界存在检查到执行的竞态，scheduler-gap合同可在真实请求后失配

**状态：OPEN。**

baseline记录current slot；enable仅要求当前slot仍相等（第 414–436、475–490 行）。`run-stop`再次比较slot后，继续执行schema/slot-count检查，再启动wrapper（第 560–599 行）。代码没有检查距15分钟slot结束的剩余时间，也没有限制enable receipt到wrapper的最大间隔。

若检查发生在slot末端，wrapper内的collector可在下一slot取`scheduledAt`并发出唯一真实请求。repository会根据新slot只补`newSlot-1`的scheduler gap（repository第 223–236 行）；执行器仍按旧baseline期待旧current run与旧`current-1` gap。stop会被调用，但执行器随后才因wrapper slot mismatch或run/gap数量不符失败（执行器第 626、645–687 行）。这会造成已发生真实请求却无法形成合同要求的最终四阶段审计收据。

最小机械修正：baseline、enable和wrapper前统一计算固定slot结束时间；只允许在剩余时间大于明确安全预算时enable并启动wrapper。预算至少覆盖wrapper启动裕量，建议直接覆盖 `wrapper timeout 20s + stop timeout 15s + 固定审计裕量`，例如要求剩余≥60秒。enable receipt另加短TTL并在run-stop验证 `0 <= now-enabledAt <= TTL`。任何时间/slot门在enable后失败必须进入P1-01的统一stop finally。修复后重新冻结执行器SHA，再做一次精确静态复审。

机械后继至少必须满足：

- 新脚本保持固定app/DB/Node/manifest/source/label与clean env；

- 加入slot-end≥60秒与enable短TTL；
- stop证据先于wrapper错误上抛，且最终独立回读disabled epoch4/unloaded；
- wrapper一次、stop一次、RSS最多一次、无业务重试；
- 继续保留scheduler-gap、run/candidate、人工字段、20秒零新增和public零漂移检查；
- 冻结新SHA并重新只读复审。无需修改产品collector核心。
