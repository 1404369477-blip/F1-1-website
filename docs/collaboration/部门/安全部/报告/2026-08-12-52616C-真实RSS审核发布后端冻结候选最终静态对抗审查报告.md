# TASK-20260812-52616C 真实 RSS 审核发布后端冻结候选最终静态对抗审查报告

## 1. 最终结论

**FAIL：P0=0，P1=1，P2=0。**

按任务失败路径，发现该 P1 后已立即通知统筹部与 `admin_backend`，并停止扩展剩余静态层。本结论不会被开发部的 Vitest/typecheck 结果覆盖；这两项动态收据不能证明一个已缺 trigger 的现成 v2 库会在写前被拒绝。

## 5. P1 问题与精确最小修正

### P1-01：现成 `user_version=2` 库没有完整 schema fingerprint 门

**静态证据**

- `app/src/server/review-real/migration.ts:23-45` 只要求 version 精确为 2、`REVIEW_TABLES` 七名均存在、FK/recursive=1、foreign-key check 为空且 integrity 为 `ok`。
- 表名检查使用 `includes`，既不拒绝未授权的额外业务对象，也不读列、index 或 trigger SQL。
- `app/src/server/review-real/migration.ts:48-59` 在 version=2 分支不重放 migration，然后直接进入上述弱 schema 检查。正确 `0002` 文本 hash 只能证明调用者提供的文件，不能证明 DB 当前的 `sqlite_schema` 仍与该文件一致。

**影响**

一个因错误恢复、混合 release、外部 writer 或手工操作而缺失关键 trigger/index/column 的 v2 库，仍会被当作合法写主。此时 `C334CE` 已验证的 Publication/Outbox REPLACE 防护、Audit 唯一前驱与各表不可变性可以完全不存在，运行时却不会在首次业务写前 fail closed。这会破坏唯一 Publication/Outbox 身份、审计链和可追溯性，因此为 P1。

**精确最小修正**

1. 定义唯一 final-schema canonical manifest：至少包含 `sqlite_schema` 中所有非 SQLite 内部的 `table/index/trigger` 的 `type,name,tbl_name,sql`，按确定性 Unicode code point 顺序排列，对闭合 JSON 计算 SHA-256。
2. 冻结与当前 `0001+0002` 精确应用结果对应的 final-schema SHA；额外、缺失或 SQL 字节不同均拒绝。
3. 在 version 1 成功提交 migration 后立即验证；对每个现成 version 2 库也在 Repository 可构造/首次写入前重新验证。
4. 指纹、user_version、`foreign_keys`、`recursive_triggers`、`database_list`、FK check 或 integrity 任一不符，统一失败关闭并禁止 Repository 业务写；不尝试自动删表、补 trigger 或带病运行。
5. 后继只需增加一个聚焦静态/临时库证据：正常 v2 命中；缺一个 trigger、改一个 index SQL、多一个未授权业务对象各在 Repository 写前被拒绝。遵循用户的低冗余测试要求，无需重跑其他后端套件。

## 6. 原 Snapshot P2 最终裁定

`C334CE` 保留的 P2 是 schema 本身没有联动 generation/parent 形状。当前 receiver 已在真正激活前强制：

- `projection.ts:352-354`：`generation=1` 当且仅当 parent 为 null；
- `projection.ts:362-365`：空 active 时候选 generation/hash 必须精确命中不可变 bootstrap pin；
- `projection.ts:366-371`：非空 active 时候选必须 generation=`active+1` 且 parent=当前 active manifest hash；
- `projection.ts:300-330`：收据对账从 active 向后遍历，每代 generation 必须与递减期望值一致，并精确结束于 bootstrap generation/hash，不完整链失败关闭。

因此，原 `snapshot generation-parent` **P2-01=CLOSED**。这个限定结论不外推为 receiver 全体安全 PASS。
