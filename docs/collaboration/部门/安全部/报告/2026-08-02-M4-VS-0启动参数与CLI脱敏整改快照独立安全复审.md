# M4 VS-0 启动参数与 CLI 脱敏整改快照独立安全复审

## 1. 唯一结论

本轮结论为 **FAIL**，`P0=0 / P1=1 / P2=0`。

两项整改中，启动附加 argv 边界已通过：`dev/start` 的 `--port`、`--hostname`和 positional 六组真实 npm 子进程均在 runtime readiness、Next 动态导入和 socket 监听前非零拒绝，并且 3000/3101 零监听。应用自身的 missing DB、forbidden env/secret、fixture path 和 migration drift 四类失败也都只输出四字段 allowlist JSON。

但统一 CLI 失败出口尚未完整闭合：合法 `npm start` 通过 runtime readiness 后动态进入 Next CLI，如果 Next 在 `listen()` 阶段失败，Next 先向 stderr 直接写出自己的“Failed to start server”、`Error` 和 stack/address/port 结构，当前 `runSafeCli` 没有把它收敛为唯一四字段 envelope。该路径命中任务 JSON 的失败条件“错误输出可泄漏 path/stack/URL/secret 或 reasonCode 非 allowlist”，因此必须保持 FAIL。

受限宿主拒绝 loopback bind 是环境能力负例，不说明正常 loopback 实现失败；同一次负例所观察的原始 Next 错误面仍是当前快照的实际输出控制事实。已 ACK 的 `TASK-20260802-FFC67A` 独立隔离收据另行证明正常 start 只监听 `127.0.0.1:3000`、health ready/local-only/externalCalls=0 且清理无残留；它不消除异常分支的原始输出。

## 5. CLI allowlist 与泄漏边界

### 5.1 已关闭的路径

- `security/log.ts` 第 3–62 行冻结 `CLI_REASON_CODES`，第 130–147 行对 `cli_failure` 只允许 `event/level/status/reasonCode/externalCalls`；当前 `runSafeCli` 不传 level，实得四字段。
- `security/cli.ts` 第 10–26 行只返回静态 allowlist reason，未知错误收敛为 `CLI_INTERNAL_ERROR`，SQLite 原生 code 收敛为 `SQLITE_FAILURE`。
- `security/cli.ts` 第 34–46 行的 catch 只将 `redactLogEvent()` 结果 JSON 写入 stderr，不写 `message`、stack、path、URL 或 secret。
- 真实 npm 子进程已覆盖 missing DB、forbidden env/secret、fixture path 和 migration ledger drift；四类都逐字满足四字段 JSON，扫描无绝对路径、stack、源码行列、URL 或注入 secret。

### 5.2 P1：Next 启动失败可绕过四字段出口

代码路径为：

```text
serve.ts runSafeCli
→ argv gate
→ assertRuntimeReady
→ dynamic import next-start/next-dev
→ Next CLI listen
→ Next CLI 内部直接写 stderr / 退出
→ runSafeCli 无法保证唯一四字段输出
```

本会话在默认受限宿主直接执行正常 `start` 时，runtime readiness 通过，随后宿主在 `listen 127.0.0.1:3000` 返回 `EPERM`。进程实际 stderr 含 Next 失败标题、原始 `Error`、stack frame 和 address/port 字段，没有收敛成 `event/status/reasonCode/externalCalls` 四字段 JSON。

`p1-acceptance.ts` 第 93–105 行启动 start 子进程并只计数捕获的 stdout/stderr，第 107–122 行由外层 `runSafeCli` 在子进程失败时输出安全 `CLI_INTERNAL_ERROR`。这只保护 `npm run test:p1` 这个外层验收命令，无法改变用户直接执行 `npm run dev/start` 时 Next 已经产生的错误输出。

`p1-cli.test.ts` 第 45–63 行对已选定负例强制四字段 envelope，但现有 10 个用例没有触发“argv 合法、runtime 已就绪、Next 进入后监听失败”分支。因此当前测试 PASS 不能证明统一 CLI catch 覆盖该分支。

**严重度：P1。** 当前证据没有显示真实 secret 或绝对路径已泄漏，但原始 Error/stack 已直接违反任务失败出口，且后续 Next 失败可能夹带路径或其他内部细节。

## 6. 正常 loopback、env 与 no-egress

### 6.1 代码审查

- Next dev/start 的 host/port 均由代码字面量传入 `127.0.0.1:3000`，没有把 CLI argv 或父进程 APP/REAL 变量传给 Next 作为覆盖。
- `p1-acceptance.ts` 的 child env 只传 HOME、TMPDIR、固定 PATH、`NODE_ENV=production` 和 `NEXT_TELEMETRY_DISABLED=1`，不继承 proxy、NODE injection、APP/REAL override 或 secret。

### 6.2 运行证据分层

1. 本会话的默认沙箱 start 以 `EPERM` 拒绝 bind，它证明宿主限制，不证明应用正常 loopback 失败。
