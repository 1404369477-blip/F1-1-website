## 2. 五项 P1 的关闭方式

### 2.1 唯一 data-native 输入与一次性 provenance

新增 `stories.input.json`，它是 12 条 synthetic 公开演示资料的唯一可维护输入。根对象、provenance 和每条 story 均使用 closed exact key set；精确要求 12 条、slug 唯一、分类/状态/tone 枚举合法、状态计数为 8/2/2。

生成器现在实际解析并遍历 `stories.input.json`：

- 已删除内嵌 `STORIES`；
- 已删除对 `app/src/features/stories/demo-data.ts` 的读取、SHA 前置和运行依赖；
- 旧前端文件路径与 SHA 只作为一次性转移 provenance 保存，`runtime_dependency=false`；
- 生成器和 validator 都要求目录内精确只有一个 `stories*.json` 输入；
- manifest 同时绑定输入字节 SHA、输入版本和一次性 provenance；
- validator 逐条核对输入到 Content、Summary、Publication、访问/媒体展示的精确投影，输入漂移后即使重绑外层 hash、但未重新生成领域图，仍会拒绝。

### 2.2 ReviewDecision hash-input exact

validator 对每条 ReviewDecision 从顶层字段重新构造唯一 expected object：

`review_decision_id / release_bundle_id / approved_bundle_hash / review_version / decision / canonical_json_rule_version / 五个 fence`。

它先要求 `decision_hash_input` 与 expected object 整体相等，再重算 `decision_hash`。`source_config_epoch`、`source_safety_epoch`、`authorization_version`、`policy_epoch`、`recovery_epoch` 五个 fence 分别单独分裂并重算内外层 hash 后，五项均被拒绝。

### 2.3 manifest / profile / ledger closed exact

validator 现在对以下对象执行整体 closed exact 校验和交叉绑定：

- manifest：root keys、contract、fixture、source task、lineage/status、artifact allowlist、hash scope、v0.3/M3 收据、唯一 story input、count、public ID、graph hash、Source identity和四项 capability；
- profile：双 profile ID、精确相对 SQLite 路径、contract、Source count/field count/allowlist/canonical hash、public graph count、capability、process rules、七个 import reason-code、六个 forbidden reason-code；
- ledger：完整 root object、profile/path/contract/fixture、manifest/graph hash、row count 和 capability；
- 交叉绑定：public profile path 与 ledger path 逐字相等，profile/ledger/manifest contract 相等，public graph count 与实际 projection count 相等。

外层 hash 被同步重算时，manifest `external_calls=1`、profile 绝对路径、M3 allowlist、允许 ATTACH、删除 forbidden，以及 ledger capability/count 漂移均被语义门拒绝。

### 2.4 DTO machine allowlist exact

`public-dto-mapping.json` 已从自然语言 value 改为封闭机器结构。每个公开字段精确使用：

```json
{"kind":"field|derived|constant","owner":"...","json_pointer":"...","transform":"..."}
```

validator 对整个 mapping 与内置 accepted allowlist 做 exact equality，并再次检查每个 feed/detail mapping 只能有四个机器键；公开字段 source pointer 不得包含 canonical/external/evidence/original URL、hash、fence、epoch、reviewer、decision reason、raw、internal、private、ledger 或 evidence ref token。

把 `publicId` 改指 `ReleaseBundle.canonical_payload.original_url` 并同步重算 artifact/manifest/ledger hash 后，validator 拒绝。

### 2.5 no-follow 安全原子输出

生成器所有 JSON 输出都经过固定 allowlist，目标只能位于当前机器包目录。写入流程为：

1. 对项目根、`data/`、输出目录和 generator 自身执行 `lstat`，拒绝 symlink 或非预期类型；
2. 用 `O_DIRECTORY + O_NOFOLLOW` 打开输出目录；
3. 对现有目标执行 `follow_symlinks=false` 检查，拒绝 symlink 和非 regular file；
4. 在同目录以 `O_EXCL + O_NOFOLLOW` 创建私有 `0600` 临时 regular file；
5. 完整写入、文件 `fsync`、同目录 `os.replace`、目录 `fsync`；
6. 失败路径精确清理临时文件。

影子副本中，输出 target symlink、输出 target directory、输出父链 symlink 均被拒绝；项目外 sentinel 保持 `SAFE`，没有被覆写。

## 7. 错题自检

- 首次完整临时探针执行在最终残留检查时发现：正式包此前的 `py_compile` 产生了 `__pycache__`，各影子副本复制了这些已有缓存。29 项语义与安全断言当时已经通过，但该次运行未计为“无残留”通过证据；随后精确删除正式包缓存，重新从干净正式包执行全部探针，取得 `TEMP_LEFTOVERS=0` 和 `TEMPORARY_DIRECTORY_CLEANED=true`。
- 没有把一次性旧前端 provenance 写成持续 app 依赖；generator 的实际输入只有 data-native JSON、v0.3 和 M3 冻结文件。
- 没有用同步重算外层 manifest/ledger hash 冒充语义拒绝；对抗探针主动重绑非目标收据，让 validator 到达对应 exact 门。
- 没有在 data 包内自称解决 root-of-trust；已把四个最终 root hash 明确交给后续开发 pin。
- 没有把数据部自测 PASS 写成审核放行；本报告唯一出口仍是安全部与测试部聚焦复验。
