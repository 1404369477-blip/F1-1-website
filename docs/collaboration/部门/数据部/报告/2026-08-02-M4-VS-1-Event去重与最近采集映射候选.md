# M4 VS-1 Event 去重与最近采集映射候选

## 1. 唯一 proposed 结论与边界

本报告关闭测试计划 [`TASK-20260802-28882C` §16](<[M5-HOME]/Documents/F1+1/docs/collaboration/部门/测试部/报告/2026-08-02-M4-VS-1-mock采集链路测试计划.md>) 中的两项数据缺口：

1. 为新 Content 定义版本化、可重算、与到达顺序无关的 `dedup_fingerprint` 输入和 SHA-256 算法；并定义两个并发 Content 归一为同一 Event 时的稳定 canonical tie-break、碰撞处理和算法变更策略。
2. 从既有 internal-only `SourceObservation` 只读派生 `last_collected_at`，固定成功谓词、时间/时区、null/unknown、并发快照和 keyset 分页口径；不增加 Source 字段，不写回 Base。

唯一 proposed 建议是：

- 新写入使用 `event-dedup-v1`。指纹输入只使用已经规范化的 `Content.content_kind`、`language`、`normalized_title`、`normalized_body` 和 `published_at` 的 UTC 日历日；不使用 Content ID、external ID、URL、capture 时间、updated 时间或 source epoch，避免到达顺序和易变元数据改变同一事件的归属。
- 指纹为 `SHA-256(canonical-json-v1(input))` 的 64 位小写十六进制文本。新 Event ID 由 `event-<dedup_fingerprint>` 派生；成员按 Unicode code point 升序稳定排序，`canonical_content_id` 始终为成员排序的第一项。并发事务不读取 rowid、插入顺序、本机时钟或 broker 顺序。
- v0.3 已冻结的 `event-synth-001/002` 及其既有 fingerprint 是历史 fixture anchors，按原值加载和重放；`event-dedup-v1` 只作用于新写入。这样不会改动冻结 data，也不会把旧 synthetic hash 误宣称为新算法产物。
- `last_collected_at` 只取 `SourceObservation.internal_only=true AND error_class='none'` 的最大成功 `observed_at`。`published_at` 是源内容发布时间，不参与该派生；`discovered_at` 只作为同一采集时刻的稳定次排序。没有成功观察时返回 `null`，展示状态为 `unknown`，不写占位时间。

本文是 proposed 数据映射，不修改 `data/mvp-contract-v0`、Spec、ADR、app 或 VS-1 既有蓝图，不新增领域实体、状态枚举、Source 字段或持久化的 `last_collected_at`。真实平台、Base、网络和 runtime worker 均不在范围内。

## 3. `event-dedup-v1` 指纹映射

### 3.1 精确输入对象

对每个通过 normalization、schema 和 Content hash 校验的新 Content，构造以下对象；对象 key 由 `canonical-json-v1` 排序，字段值不再做隐式清洗：

```json
{
  "content_kind": "<Content.content_kind>",
  "language": "<Content.language>",
  "normalized_body": "<Content.normalized_body>",
  "normalized_title": "<Content.normalized_title>",
  "published_day_utc": "<UTC YYYY-MM-DD or null>"
}
```

字段规则：

| 输入 key | 来源 pointer | 规则 |
|---|---|---|
| `content_kind` | `schema.json#/$defs/Content/properties/content_kind` | 原值；`post/article/video/image/thread` 等 enum 由 schema 校验 |
| `language` | `schema.json#/$defs/Content/properties/language` | 原值；不做大小写或 Unicode 正规化 |
| `normalized_title` | `schema.json#/$defs/Content/properties/normalized_title` | 使用 Content 已完成规范化的文本；不二次 trim、casefold 或删标点 |
| `normalized_body` | `schema.json#/$defs/Content/properties/normalized_body` | 使用 Content 已完成规范化的文本；不截断、不摘要、不读取 raw body |
| `published_day_utc` | `schema.json#/$defs/Content/properties/published_at` | `null` 保留为显式 JSON null；非空 RFC3339 date-time 先转 UTC，再取 `YYYY-MM-DD` |

明确排除 `content_id`、`source_id`、`external_content_id`、`external_url`、`canonical_url`、`capture_id`、`captured_at`、`content_version`、`content_version_hash`、`source_config_epoch`、`created_at`、`updated_at`、`source_evidence_url`。排除理由是：这些字段用于记录来源、版本、采集或运行状态，变化不应单独制造第二 Event；`source_id` 排除也保留跨来源同一事件被候选聚合的能力。该算法是保守的 exact-normalized match，近似语义相同但规范化文本不同的内容不会自动合并。

`published_at` 跨时区示例：`2026-08-02T00:00:00Z` 与 `2026-08-02T08:00:00+08:00` 都映射为 `published_day_utc="2026-08-02"`。无法解析的 date-time 在 Content schema 层拒绝，不能在指纹层默默按本地时区猜测。

### 3.2 编码、哈希与新 Event ID

`canonical-json-v1` 的规则来自 `state-machine.json#/canonical_json_rule`：UTF-8、Unicode code point key order、紧凑逗号/冒号、保留显式 null、不做 NFC/NFD、不允许 NaN/Infinity；SHA-256 对精确 compact UTF-8 bytes 计算。算法版本标识为 `event-dedup-v1`，不称 RFC 8785 JCS。

伪代码：

```text
published_day_utc = null
if content.published_at is not null:
    instant = parse_rfc3339(content.published_at)
    published_day_utc = instant.to_utc().date("YYYY-MM-DD")

input = {
  content_kind: content.content_kind,
  language: content.language,
  normalized_body: content.normalized_body,
  normalized_title: content.normalized_title,
  published_day_utc: published_day_utc
}
fingerprint = lowercase_hex(SHA256(canonical_json_v1_utf8(input)))
new_event_id = "event-" + fingerprint
```

输入对象的 key 顺序由 canonical codec 决定，不依赖代码语言的 map 插入顺序。算法实现必须拒绝缺失 required Content 字段、未知 key、非法 date-time 和非有限数字；不能以空字符串或 epoch zero 补值。

### 3.3 并发 canonical tie-break

同一 fingerprint 的成员候选排序键为：

```text
(content_id, content_version_hash, capture_id or "")
```

每一项按 Unicode code point 升序逐项比较；Content ID 按 schema pattern 已保证非空，因此第一项通常已经唯一。`canonical_content_id` 为排序后的第一项 `content_id`，`member_content_ids` 为同一排序结果去重后的 JSON array。算法不读取 `created_at`、`observed_at`、SQLite rowid、事务先后、worker ID、随机数或 broker delivery sequence。

Repository 操作必须在 `BEGIN IMMEDIATE` 中执行：

1. 先验证当前 Content、source epoch 和 candidate fingerprint。
2. `SELECT event WHERE dedup_fingerprint=:fingerprint`；不存在时用 `event-<fingerprint>` 插入空/单成员 Event。
3. 已存在时对旧 members 与新 Content 做集合并集，按上述排序生成新 members；`canonical_content_id` 取最小项。
4. 以 `WHERE event_id=:event_id AND dedup_fingerprint=:fingerprint` CAS 更新；`sqlite3_changes()=1` 才提交。重复成员是 no-op，重复投递返回同一 Event identity。
5. append-only `AuditEvent` 记录 operation/task、fingerprint、旧/新 member count 和 redacted reason；不记录原始正文。

因此，A/B 两个 Content 先后、反序或 20 路并发到达，最终 `event_id`、fingerprint、canonical ID 和 members 完全一致。若两个事务同时发现 Event 不存在，唯一 fingerprint 约束只允许一个 insert winner，另一个读回 winner 后走同一 union CAS；不能产生第二 Event。

### 3.4 碰撞、近似重复和变更策略

| 情况 | 判定 | 处理 |
|---|---|---|
| 同 fingerprint、canonical input byte 完全相同 | 正常候选重复 | 合并 members，`dedup_status=merged`；重复 member no-op |
| 同 fingerprint、canonical input byte 不同 | SHA 碰撞、codec bug 或数据损坏 | fail closed；不自动合并，写 `dedup_status=needs_review`/redacted AuditEvent，P1 诊断；不覆盖旧 Event |
| 不同 fingerprint、文本语义可能相同 | v1 的保守 false negative | 保持两个 Event，不跨 fingerprint 自动合并；需要产品接受新规则和迁移任务 |
| hash 输入字段或规范化规则变化 | 算法变更 | 新 contract version + 新 migration；旧 Event/fingerprint 原样保留，新写入使用新 algorithm id；禁止原位重算/覆盖 |
| legacy v0.3 fixture replay | stored fixture anchor | 依据 fixture 的 `event_id`/`dedup_fingerprint` 原值重放；测试 `EVENT-01/02/03` 不要求旧 hash 与 v1 公式相等 |

该策略不把 hash 碰撞、近似重复或算法迁移隐藏成成功。`Event` 现有字段已足以保存 v1 的 64 hex 值；算法版本通过 successor state-machine metadata 和 contract version 追溯，当前任务不增加 Event 列。

## 5. `last_collected_at` 只读派生

### 5.1 语义与输出映射

输出属于 Sources read model/API projection，不属于 `Source` domain schema：

```json
{
  "source_id": "<Source.source_id>",
  "last_collected_at": "<successful SourceObservation.observed_at normalized to UTC> | null",
  "last_collected_state": "known | unknown",
  "last_collected_observation_id": "<internal observation_id> | null"
}
```

其中 `last_collected_state` 和 observation ID 是 read-model/审计映射字段，不能写入 Source、Base 或 v0.3 schema。对外 DTO 若只需要合同已提到的时间，应只暴露 `source_id` 与 `last_collected_at`；`last_collected_state` 可用于 UI 明示 unknown，`last_collected_observation_id` 仅留在 internal trace，不公开。

成功观察谓词固定为：

```text
o.internal_only = true
AND o.error_class = 'none'
AND o.observed_at is a schema-valid RFC3339 date-time
```

`observed_at` 是 adapter 观察/采集发生时间；`published_at` 表示外部内容发布时间，可能为空，不可当作最近采集；`discovered_at` 表示发现时间，仅用于同一 `observed_at` 的稳定 tie-break。观察有 `error_class != 'none'` 时不提升 `last_collected_at`，但不抹除该失败观察；如果历史有成功记录，仍展示最近成功时间。

null/unknown 规则：

- Source 没有 observation，或所有 observation 都是错误：`last_collected_at=null`、`last_collected_state=unknown`。
- 不能用 epoch zero、Unix epoch、`"never"`、本机当前时间或 `published_at` 代替 null。
- Source 本身为 M3 disabled、paused、stopped 或未启用时，仍可只读显示历史成功采集时间；是否在 UI 隐藏由页面策略决定，查询不能借展示状态篡改数据。

### 5.2 确定性 SQL/查询

推荐在同一 read-only transaction 中用 window function 选择每个 Source 的最近成功观察：

```sql
WITH successful AS (
  SELECT
    o.source_id,
    o.observation_id,
    o.observed_at,
    o.discovered_at,
    ROW_NUMBER() OVER (
      PARTITION BY o.source_id
      ORDER BY
        julianday(o.observed_at) DESC,
        julianday(o.discovered_at) DESC,
        o.observation_id COLLATE BINARY ASC
    ) AS rn
  FROM source_observation AS o
  WHERE o.internal_only = 1
    AND o.error_class = 'none'
)
SELECT
  s.source_id,
  CASE WHEN ok.observation_id IS NULL THEN NULL ELSE ok.observed_at END
    AS last_collected_at,
  CASE WHEN ok.observation_id IS NULL THEN 'unknown' ELSE 'known' END
    AS last_collected_state,
  ok.observation_id AS last_collected_observation_id
FROM source_config_fixture AS s
LEFT JOIN successful AS ok
  ON ok.source_id = s.source_id AND ok.rn = 1
WHERE (:after_source_id IS NULL OR s.source_id > :after_source_id)
ORDER BY s.source_id COLLATE BINARY ASC
LIMIT :page_size;
```

实现规则：

1. `julianday()` 只用于把合法 RFC3339 instant 转为可比较的 UTC 数值；不使用 SQLite `localtime` 修饰符。repository 读取结果后把 `observed_at` 解析并输出 UTC RFC3339，原 observation bytes 不被更新。
2. `observed_at` 是 required；它相同且 `discovered_at` 不同，则按较新的 `discovered_at` 选 trace；两个时间也相同，则按 `observation_id` Unicode/BINARY 升序，确保跨到达顺序一致。时间 tie 不改变 `last_collected_at`，只稳定 observation reference。
3. `source_id` keyset cursor 使用 Unicode code point 升序；SQLite `BINARY` 对合法 UTF-8 source ID 的字节序与 code point 序一致。禁止 `OFFSET` 分页，避免新 Source 插入造成跳过/重复。
4. 列表全部 page 必须在一个 read snapshot 内执行；下一页复用同一 cursor/snapshot，或返回 snapshot token 由实现合同冻结。若使用独立查询，必须接受 read-time snapshot drift 并在 receipt 中记录，测试 golden 默认要求同一事务。
5. `:page_size` 为正整数且有实现上限；空页只表示没有更多 Source，不把 null 时间当排序最前/最后的伪采集值。

推荐索引（仅在 successor implementation migration 中执行，不在本任务落盘）：

```sql
CREATE UNIQUE INDEX source_observation_source_external_uq
  ON source_observation(source_id, external_id);

CREATE INDEX source_observation_last_success_idx
  ON source_observation(
    source_id,
    observed_at DESC,
    discovered_at DESC,
    observation_id ASC
  )
  WHERE internal_only = 1 AND error_class = 'none';

CREATE INDEX source_observation_error_idx
  ON source_observation(source_id, error_class, observed_at DESC);
```

如果 SQLite 版本/查询规划器不利用 partial index 的 `julianday` 排序，保留该索引做候选扫描，repository 在内存中用同一三段排序键复核；不把非确定性 `MAX(observed_at)` 文本比较当作最终答案。

### 5.3 派生 golden 与失败路径

| 输入 | 预期 |
|---|---|
| 同一 Source 两条成功观察，`observed_at` 先后不同 | 返回较新 instant 的 UTC `last_collected_at` |
| 同一 instant、`discovered_at` 不同 | 时间值相同；选择较新 discovered observation 作为 internal ref |
| observed/discovered 均相同、observation ID 不同 | 按 observation ID Unicode/BINARY 升序；结果与到达顺序无关 |
| 最新 observation `error_class=timeout`，更早有成功 | 返回更早成功时间；失败保留在 internal audit/observation，不冒充成功采集 |
| 只有 429/5xx/timeout/invalid fixture | `last_collected_at=null`、state=`unknown` |
| `published_at` 比 observed_at 更新/更旧/为空 | 结果不受影响；published_at 永不参与采集时间派生 |
| `observed_at` 为 `+08:00`、`Z`、`-05:00` 同一 instant | 统一输出 UTC；不按机器本地 timezone 变化 |
| Source 无 observation | left join 保留 Source；null/unknown，不丢 Source 行 |
| 新 observation 与列表并发提交 | 同一 read snapshot 不可半页混合；下一 snapshot 通过 cursor 可重复读取 |
| page size 0/负数/超限、cursor 非法 | 在 DTO 层拒绝；不执行无界查询、不写 DB |
| M3 59 shadow disabled | 只读派生可显示 null/unknown；不改变 enabled、epoch 或 seed hash |

## 8. 失败路径、验证边界与错题自检

### 8.1 失败/回滚路径

| 失败 | 处置 |
|---|---|
| 缺失 Content 指纹字段或非法 date-time | schema/normalization fail closed；不写 Event/Outbox；保留 redacted reason |
| canonical codec 产生未知 key、非有限数字或不同 bytes | 拒绝 hash；不降级到 host JSON serializer |
| fingerprint unique conflict / hash collision | 保留既有 Event，`needs_review` + AuditEvent；不覆盖 members/canonical |
| 两个并发 Event insert | 唯一 fingerprint winner；失败事务回滚后读回 winner；不使用 retry arrival order 选 canonical |
| stale source epoch/TaskEnvelope | 在 Event CAS 前拒绝；Content/Event 当前状态不变 |
| 观察查询遇到 null/invalid/error | schema rejects invalid；error 不算成功；无成功返回 null/unknown |
| 时区解析依赖机器 locale | 禁止 localtime；固定 RFC3339→UTC parser；解析失败 non-zero |
| 分页期间 Source/Observation 变化 | 同一 read snapshot + keyset cursor；不使用 offset 弥补 |
| 读取路径意外写 Source/Base | P0；事务回滚、记录 redacted audit、任务实现阻断 |
