## 审核队列与后台可用性

`ADMIN_NETWORK_FAILURE` 由浏览器取得 HTTP Response 前的 fetch 拒绝产生。正常收到 401 或 503 JSON 会显示其他状态或服务端原因码；审核列表读取本身不检查备份新鲜度。因此目前没有证据把审核网络错误和 GLM 验证错误归为同一根因。

22:38 后从 M5 沿真实 Tailscale 私网访问审核和设置页面均 HTTP 200，约 50 毫秒；22:41:38 不带会话的 `/api/admin/reviews`、`/api/admin/settings` 均正常返回 401 / `ADMIN_SESSION_REQUIRED`，约 47–72 毫秒。这只证明当时页面、API 传输和认证拒绝正常，不等于已登录列表可用。一次附带查询参数的诊断请求按严格路由规则返回 404，保留原始记录，不计入后台故障。证据：[私网 HTTP 检查](../../scratch/admin-health-20260911/private-http-checks.json)。

浏览器工具能列出已打开的审核台标签，但页面 DOM 与诊断命令超时，未取得已登录请求的状态、耗时和网络失败原因；没有提取 Cookie 或伪造会话。已请用户在原已登录页面刷新复核。

用户随后选择“出现不同错误”并补充模型详情截图，实际可见码仍为 `ADMIN_BACKUP_STALE`、Key 未配置；这份图未显示审核队列，故不能据此认定审核网络错误消失或改变。

22:48:24，主控复核固定脚本后经 M1 生产 Node 执行实际 v5 `ReviewRealRepository.list()`：先匹配 deployment、代码、DB dev/ino/权限，使用 `DatabaseSync(readOnly:true)` 和 `query_only=ON`，调用后回滚读事务并关闭。模块导入 131.165ms，列表 3946.159ms，100 项成功返回：published 65、approved_waiting_publish 21、source_updated 13、reconcile_wait 1；全过程 exit0。该样本证明当时仓储读取和映射可完成，不代表网络/会话/浏览器出口已通过，也不证明每次耗时均低于相同数值。见 [生产列表实测](../../scratch/admin-health-20260911/production-list-result.json)。
