## 旧链路泄漏的可复核原因

1. 2. runner 以 SSH 调用 M1 `~/F1-1-website/.admin-backup/bin/m1-snapshot-helper.mjs`，无 sourceDB 参数。helper 固定源库为 M1 `~/F1-1-website/app/.local/f1plus1-rss-real-private.sqlite`。本次使用只读 SQLite URI 查询，`PRAGMA user_version = 10`。迁移编号 0012 不等于 user_version=12。
3. helper 第 79–81 行只接受 `[3, 4]`。第 97–100 行先执行 SQLite online backup，到第 108 行验证时才抛 `SNAPSHOT_DATABASE_INVALID`；只有成功后才将 `.sqlite.stage` 重命名为 `.sqlite`。finally 只关闭源数据库，没有清理失败 stage。
4. M5 stderr 重复记录 `COMMAND_FAILED:/usr/bin/ssh:1` 和 `SNAPSHOT_DATABASE_INVALID`，调用栈准确指向 helper 81/108 行。runner 的 prune 仅在成功流程作用于 M5 points/objects，失败 stage 在 M1 上没有保留上限。
5. 14:47 盘点为 318 个 `.snapshot-<13位毫秒>-<UUID>.sqlite.stage`、636 个对应 `-wal`/`-shm`，另有 4 个最终 `snapshot-*.sqlite`。审计期间文件数由 955 增至 958。近期每组约 235 MiB；持续五分钟一次可新增约 66 GiB/日，这是按近期文件大小和配置周期估算，不是全天实测。

## 已实现的 v2 保留规则与运行限制

以下规则已随本次备份 v2 生产 materialized 版本核验身份，并完成一轮 RunAtLoad 和两轮自然周期；长期轮换边界仍以规则与独立失败场景验证为依据，不能由三轮等同证明 24 包或 7 天的长期运行。旧周期 `retain=8` 属于本次早期历史状态。

1. 同一恢复目标只保留一条被证明确实成功的周期备份生产链。替换时核对两机 LaunchAgent 和残留触发器，并在下一周期验证旧根目录不再增长。仅停止坏生产者不能算新备份验收通过。
2. M1 v2 SNAP 设置 `retain=24`，仅控制本 backupRoot 的已验证完整 packages 与引用关系明确的 objects；M5 `Application Support/F1Plus1/BackupObserver/cipher-cache` 保留当前包及另一完整包，共 2 份。未知、不完整、被改动或链接化的 cache 目录保留，不能强行计入可安全删除集；M1 已命名坏包可使预检/轮换失败，必须先调查。规则不覆盖 `.admin-backup`、release、所有 drill/scratch 或其他个人目录。数量上限不等于固定字节上限，最末可用独立恢复点与本次 rescue 在新链路验收前不删。
3. 本次保留的旧失败样本限 1 组，约 235 MiB；计划在 **2026-09-13 22:53（北京时间）前复核处置**。新 SNAP 已通过异机落点和恢复演练且本事故证据已归档后，可清除此唯一样本；若仍有未解决根因，记录延期原因和新日期，禁止重新按周期积累。未创建自动删除任务。每次失败清理自己创建的 stage；崩溃残留由独立清单核对处理，先验证锁/进程/身份，再删除确定无引用文件。不能以“超过某时长”单独证明可删；保留最近一次失败复现证据和错误收据。
4. Release 保留所有在用版本、一个已验证回滚版本和必要迁移恢复输入。部署成功后生成未引用候选清单，完成回滚/恢复核验后清理；不按目录名称或日期机械删除。
5. 隔离候选结束后保留源码差异、lockfile、构建身份、日志和验收证据；清理可重建的 node_modules/.next。正式运行包及未结束任务不套用此规则。
6. M1 源码容量预检已纳入数据库与 projection 的并存开销；M5 密文下载前要求至少 1 GiB、待下载大小及元数据余量，低空间在大型下载前失败。仍需观察实际目录增长和下载/恢复峰值，禁止通过删除最后有效恢复点腾空间。
7. M1 直接异机回执与应用演练回执按各自 7 天规则清理；M5 iCloud 收据仅删除严格超过 7 天、当前 owner、普通单链接、身份稳定且固定公钥验签通过的记录，保护当前/cache 包，未知内容和异常链接保留。归档的无覆盖硬链接发布在崩溃窗口可能留下 nlink=2；后续拒绝并保留，需人工核对，不能改写未知文件。
8. M1 backup-cycle/agent 日志与 M5 observer 日志在超过 5 MiB 时轮换，保留当前与 `.previous`；这是每轮检查阈值，单次写入或调度间隔可能短时超出。失败状态、最近一次失败收据和必要诊断材料保留，不把所有历史日志自动当作垃圾。
9. 异机证明改由 M5 SSH 拉取到有限本地 cache 后真实读取和签名，再向 M1 原子回传小收据；iCloud 仅附加归档。M5 归档最多 5 秒且在送达后执行，失败返回 `ARCHIVE_FAILED` 并保留已送达事实；M1 密文归档在合法登记后最多运行 60 秒，失败记录 `archiveStatus=failed / ICLOUD_ARCHIVE_FAILED`。归档失败不能伪装成功，也不应抹去已经验证的独立副本。

正常失败清理自己可识别的临时对象；SIGKILL、断电、远端失联或清理异常仍可能遗留锁、stage、远端 `.tmp`。未知/incomplete 文件需人工核对，已有锁不按年龄自动抢占。当前修复消除了已证实的旧链路持续泄漏，不能承诺整台机器或全部历史目录的磁盘占用绝对有界。

## 新 SNAP 已落盘的实现补强

以下补强已在 `app/src/server/backup-snapshot/core.ts` 落盘，有本地/隔离验证，且本次生产 runtime 已按固定 hash 验证并完成三轮实际周期。源码独立证据见 `scratch/backup-recovery-20260906/review-successor-20260906/final-review.json`；SSH transfer 独立复核见 `scratch/backup-recovery-20260906/off-host-transfer-review/independent-review.json`。部署身份与生产行为证据统一见上文正式目录，不能将三轮正常执行扩大为所有失败情形都已生产演练。

- stage 清理与 lock release 使用嵌套 try/finally，避免清理本身失败后直接跳过正常释放本 run 锁；锁仍需按身份验证。
- 容量预检计入 projection 总字节与 vacuum、明文 archive、加密 object 并存开销。
- 在创建大型产物前验证已有 package 集，避免因已知坏包反复先写大对象、再发现轮换失败。
- 完整 package 在本 run staging 内写好、同步，再原子落位；对象和目录写入补充同步。
- SIGKILL/断电无法依赖 finally；保留锁和可诊断的 run 身份，沿已审查的无活进程/同机身份恢复路径处理残留，不按超时单独抢锁。失败报告、运行日志和用户可见状态必须表达实际失败，不能继续复用前次成功状态宣称当前健康。

## 与手工部署/恢复的互斥边界

备份 v2 的 fence writer 使用 `recovery-fence.json.writer-lock`。旧 sealed release 中的手工 deploy/restore 入口不会因本次 backup-only 部署自动升级；之后执行这些操作时必须先停 backup 并确认周期、登记器与子进程已退出，再使用已核验纳入同一 mutex 的新版工具。工作区 `withRecoveryFenceWriterLock` 已用于登记与新版部署初始化，不能据此声称旧生产工具全部兼容。不存在可直接照抄的通用 `locked-deploy`/`locked-restore` 命令，实际入口与产物身份见 [macOS 部署说明](../../deployment/macos/README.md)。
