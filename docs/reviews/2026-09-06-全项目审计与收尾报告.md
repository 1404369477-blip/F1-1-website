## 备份 v2 的运行与保留边界

以下后继行为已随本次备份部署与三轮验收核收，不能回写为早期旧周期已经使用这些规则：

1. M1 固定运行包先校验闭包，生成一致性 SNAP；M5 使用固定 `home-mac` SSH 读取精确加密包，在本地 Application Support 实读并签名，将小收据返回 M1 `backups/off-host-receipts`。M1 验证独立读回与真正的隔离应用演练，再合法登记恢复点并在共享 mutex 内刷新 fence。
2. M1 SNAP 设置 **retain=24**，约束本备份根的已验证完整包与其引用的密文对象。M5 专用 cache 保留**当前包及另一份完整包，共 2 份**。这些是数量规则，不能由包数直接推导固定存储字节或实际恢复点覆盖时长。
3. 小收据按 **7 天**规则清理；M5 iCloud 归档保护当前/cache 包，并要求本格式、当前 owner、普通单链接、稳定文件身份及固定公钥验签有效。未知文件、无效签名、链接和不完整 cache 不自动清理。M1 的直接回执及应用演练回执也有各自的 7 天清理规则。
4. M5 小收据归档在向 M1 送达后执行，独立子进程最多 5 秒；失败明确返回 `archiveStatus=ARCHIVE_FAILED`，保留 `receiptReturnedToM1=true`。M1 iCloud 密文镜像在成功登记后执行，最多 60 秒，失败记录 `archiveStatus=failed / ICLOUD_ARCHIVE_FAILED`。**iCloud 是附加归档，目录出现或 rsync 成功均不作为独立副本已验证的证明。**
5. 运行日志在超过 **5 MiB** 时轮换，保留当前文件和 `.previous`；这是周期检查阈值，单次追加与检查间隔会产生短时超出。旧历史日志、其他目录、未知残留不包含在该规则内。

正常失败会清理本次可识别 staging，并保持已提交 cache 可复用；已存在收据不得更新观察时间。SIGKILL、断电、清理失败、未知/不完整文件、未验证历史包或异常链接可能留下残留或阻断下一轮。不得按“过了多少分钟”直接抢锁或广泛删除；需核对进程、文件身份、打开句柄和保留证据后处置。因此本轮修复消除了已证实的旧周期泄漏，**未证明整个磁盘绝对有界**。

M1 iCloud 的 `objects/`、`packages/` 是此 producer 的专用镜像，当前实现使用 `rsync --delete-after` 同步源集合。该目标子树不能承载人工文件或唯一恢复材料；目标端源集合外条目会被删除，不能套用 M5 cache 的未知文件保留承诺。当前 rescue 与事故证据应保留在独立路径。

## 后续手工部署与恢复必须遵守的互斥边界

新登记器和工作区新版部署入口共享 `recovery-fence.json.writer-lock`，由 `withRecoveryFenceWriterLock` 执行。**旧 sealed release 内的手工 deploy/restore 工具不会因本次 backup-only 切换自动获得新 mutex。** 后续部署、恢复或人工登记前，应先停备份调度并确认周期、登记器及其子进程已退出，再使用已核验兼容同一 mutex 的新工具；未证实兼容时不得与新周期并行写 fence。

“locked 工具”描述的是该已核验行为，不是一个已经存在的通用 `locked-deploy` 或 `locked-restore` 命令。具体入口、产物 SHA 和停止/恢复收据必须随实际操作登记；禁止热改旧 sealed 文件、手工覆盖 fence 时间或无条件删除 writer-lock。详细入口见 [macOS 部署说明](../../deployment/macos/README.md)。
