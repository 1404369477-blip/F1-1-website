## 结论与最少充分方案

**推荐继续使用现有 `p-backup-live` 和 `backup_recovery_point`，将周期登记收敛为“验证并追加一份备份边界”，移除该路径的恢复锚点激活。** 保持不新增 `p-restore-live` 或扩大 backup 权限。优先复用原表并争取零迁移，但这是待实验证明的实现目标；不周期性暂停业务，不把 `backup_worker` 变成恢复操作者。

权限层已具备所需能力；单纯放宽 `assertRecoveryPointBinding()` 或跳过其调用不充分。登记必须增加面向备份包自身的绑定验证，证明 DB、投影、writer/recovery 身份与演练证据一致。原严格激活绑定函数保留，不增加 `allowStaleAnchor`、`skipBinding` 一类绕过参数。

这是**职责、checkpoint 与执行收据语义的窄范围 successor**：现有登记会创建/推进 singleton anchor，并返回 `bindingPassed=true`；改成只追加备份记录后，该字段不能静默沿用成“已激活恢复点”的暗示。须经主控/产品确认后继职责与收据语义，再按既有生产变更流程落地。静态 policy 与字段形状显示可复用的路径；必须先证明现字段完整承载 v2 身份、backup transaction authorizer 可用、旧新 reader 与 restore 兼容，才能确认无需迁移。任一证明失败均回到有界 successor 设计，不得为零迁移削弱语义；也不能据此推导生产变更已获准。

## 职责与修改点（拟议）

### 1. 周期登记只追加 backup checkpoint

在 `runBackupRecoveryPointRegister()` 完成全部只读预检后，只创建 `backup_worker` handoff，用当前 phase 对应的既有 `p-backup-*` 经 gateway 插入原表。移除周期路径中的 `restoreHandoff`、`ensureProjectionAnchor()`、`ensureOutboxHead()` 和为补头而创建的 telemetry handoff；backup 操作自身的 gateway 审计照旧保留。

各 phase 使用同一“备份登记”语义；disabled/paused 也不再通过周期登记隐式激活恢复锚点。现有 disabled 两轮测试应改为验证两条备份记录与 anchor **未变**。真正 restore 继续在已允许的 disabled/paused 下完成 anchor 激活，使用原严格绑定函数。不得保留一个按 phase 偷换成功含义的接口。

建议 CLI 成功收据显式使用后继版本，如 `backup-recovery-point-register-receipt-v2`，声明 `backupBindingPassed=true`、`activationApplied=false`；沿用已有 recoveryPointId、operationId 等身份。它是执行收据，不新增领域实体。调用 wrapper 与证据解析器必须同时切换；不能将老 v1 的 `bindingPassed` 文案偷偷重新解释。

### 2. 验证包自身，再核对当前登记授权

在 `recovery.ts` 增加一个范围明确的只读 backup binding helper（名称待实现确定），由登记工具调用。复用现有 `validateRecoveryPointReceipt()` 和稳定文件读取/演练校验，不削弱原 `assertRecoveryPointBinding()`。

必须在 handoff/DB 写入前验证：

1. latest、manifest、packageId、contentHash、keyId、恢复根、成员集合/字节数/SHA 逐项相符；恢复目录与原 DB、备份根隔离且为允许的普通文件。重新核验 restored DB 与投影成员，不能只信任传入 `BackupReport.ok=true`。
2. 从**恢复出的 DB**读取 schema 指纹、control writer/recovery epoch、writer authority；这些字段与备份 receipt 的绑定必须来自该包。当前实现直接读取运行库身份，不能在期间发生 epoch 变化后给旧快照贴上新身份。
3. 从同包 active pointer 和 generation envelope 验证公开身份，并在同包 DB 的 `projection_outbox` / `projection_delivery_receipt` 中找到匹配 generation + manifest 的成功投递证据，沿用现有签名/收据验证能力。DB 缺匹配记录或 pointer 超前时拒绝整包登记，不改成空 pointer、不改 anchor。保守首版要求可核验成功收据；已激活但 DB 尚未落收据的竞态留给下一周期重做。
4. 复算 checkpoint；校验恢复包内容与上述身份绑定。当前 live DB 的 schema、writer/recovery epoch、writer authority 必须与包内一致；不要求 live 业务行哈希与快照完全一致，因为采集可在快照后继续写入。若身份已切换，拒绝本轮并从新身份重拍，禁止自动改写 receipt。
5. 异机副本必须有同一 package/content/key 身份的独立读取验证。当前 `remoteReceiptSha256` 由 package/content/drillCode/keyId 本地拼出，不能单独证明已异机可恢复；A03 的逐周期证据须接入或作为本后继硬依赖。缺证据时可继续保留快照，不能生成合法新鲜登记或更新 fence。
6. 沿用本轮已修的 elapsedMs 有限非负、缺失拒绝、超过 14,400,000 拒绝；不截断、不默认零。`recovery_point_at` 保持实际快照边界，`completed_at` 应使用可验证的登记/演练完成时刻，不能让新执行时间刷新旧数据的新鲜度。向 `validateRecoveryPointReceipt` 传入可信 now 与 expected schema/release/manifest/epochs。

现有快照先 DB 后投影的顺序可能在并发发布时生成不一致包。最小处理为上述匹配验证失败即整轮拒绝并重新快照；不为了接受旧包直接改表或放宽一致性。若连续自然周期都无法通过、从而不能满足 900 秒窗口，再单独设计可验证的快照协调机制；本草案不提前引入全局锁或停站方案。

### 3. 写入、重复与 fence

- 只读预检通过后，沿用 gateway request/authorize，并优先让唯一 backup insert 使用现有 `runMutationTransaction()`（`gateway.ts:1733–1764`）：该方法在同一事务内生成 permit、执行写入、postcheck fence 并完成 operation。当前 helper 的 mutate 与 postcheck 是两个调用，不宜把“之后再检查”当成同事务证明。精确 expected control version、epochs、schema/release/manifest 必须在写入时重新核对，覆盖预检后身份变化；无需增加 raw transaction 或新 writer。若该方法实际不支持 backup 的 authorizer context，先在本地明确差异并复审，禁止绕过。
- `backup_recovery_point` 的三个唯一约束继续有效。重试同一 package 时，先只读核对已有整条身份；完全相同则可复用已有记录，不建立新 operation/publication，不提高 recoveryPointAt。不同则确定失败。
- **同内容新周期在本 successor 内解决，不延期、不长期拒绝。** 既有 SNAP 允许同内容按新的真实快照边界重签 manifest。拟定新域 `f1plus1-backup-checkpoint-v2`：`SHA256(domain + "\n" + canonical-json-v1(payload))`；payload 精确包含 `checkpointVersion=2`、已验证的 `packageId`、`backupManifestSha256`、`contentHash`、实际 `recoveryPointAt`、`writerEpoch`、`recoveryEpoch`、`schemaSha256`、`generation`、`projectionManifestSha256`、`projectionPointerSha256`。日期必须来自本周期一致快照/重签证据，并与 packageId、manifest、异机读取、演练报告相互绑定，不能使用重试时间或调用方提供的当前时间。内容相同但真实周期/package 不同会得到不同 checkpoint；同 package 重试保持同一 checkpoint。
- 旧 `f1plus1-common-checkpoint-v1` 算法、历史行及 hash 原字节保留。v2 执行收据必须标明 checkpoint 算法身份；reader/restore 根据可验证的 manifest 与版本证据选择算法并复算，不可凭 hash 外形猜测或在 v2 失败后无条件降级为 v1。现表没有独立算法版本列，因此“原字段 + 外部不可变收据”能否支持历史/新包完整恢复是强制兼容实验；若无法无歧义恢复，须停下提出最小 additive successor，不能只求 insert 成功。
- 只有合法记录可查询、包身份验证通过且仍在新鲜度/当前 writer 门内，才允许刷新 fence。**fence 单调且登记无权打开 ready**：旧包晚提交或重试不得使 `lastSuccessfulRecoveryPointAt` 倒退；当前 `writerReady=false` 必须保持 false，缺失/无效 fence 也不能由登记隐式创建 ready=true。若实际恢复流程尚未建立 ready，本轮最多留下经验证的备份记录，明确返回“已登记、未刷新 fence/等待恢复授权”，不宣称整体成功。
- DB 提交到 fence 原子替换间必须防范 epoch、writer authority、ready 的变化。复用**已经证明覆盖相同写入者集合的 single-writer 保护**：在其保护内重新读取最新 control/ready/fence、比较当前身份及恢复点单调性，完成文件原子替换后再释放。仅 backup cycle 的 run lock 或单次替换原子性不足以证明安全；相关 control/ready writer 必须参与同一保护，或已有等效机制能机械阻止检查后变更。当前代码尚未证明存在这样的跨 DB/文件保障，后继必须做最小并发实验；无法证明时禁止刷新 fence，保留可恢复的登记记录和明确失败原因。不得先更新再发现竞态后声称已安全回退。
- 数据库写成功、fence 写失败时重试复用同一记录；重新核对**当前** epoch/authority/ready 与已存在较新 fence，不能复用上次检查结果。禁止再插一份、删除旧记录或直接写成功时间；旧包仍可保留审计，但不刷新更近的恢复点。
- backup checkpoint 是“这份包可恢复”的证据；anchor 是“当前恢复激活位置”的证据。返回备份登记成功不宣称完整生产恢复完成，也不自动切 phase、writerReady、公开 pointer 或恢复策略。现有 fence writer 会无条件写 writerReady=true，因此不可原样用于后继刷新路径；须改为上述受保护、保持 ready、单调推进的受限行为，实际恢复设置 ready 的入口另行保留。

## 保持不变与失败路径

RPO ≤900 秒、RTO ≤4 小时、加密与异机要求、恢复演练、原表/trigger/policy、gateway 身份与预算/审计要求、生产停用开关及 signed runtime identity 全部保留。静态 view 命中不代替新鲜度或异机真实性。

| 触发 | 预期结果 |
| --- | --- |
| live/backlog 正常新包，旧 anchor 不同或缺失 | backup 可追加；anchor/phase/公开 pointer 全部不动 |
| DB 与投影跨时点、receipt 缺失、成员/hash/签名不符 | 写前确定失败，整轮重拍，不提升 fence |
| 快照后 writer/recovery/schema/release 改变 | 预检或 gateway CAS 拒绝；保留失败原因 |
| 异机验证失败、演练缺失/超时、恢复点超龄 | 不登记新鲜成功，不抬 fence；保留快照与失败收据 |
| 相同 package 重放 / 并发登记 | 复用已核对的记录或唯一约束确定拒绝，无第二条备份 |
| DB 已提交，fence 写失败 / 进程崩溃 | 下次核对同一记录及当前身份/ready/单调性后重试，失败继续可见 |
| DB 提交后 epoch/authority 改变，或 ready 变 false | 禁止旧登记刷新 fence；不覆盖 false、不宣称整体成功 |
| 旧包重试晚于较新 fence 提交 | 不降低恢复点时间，不重开 ready，不重写为旧身份 |
| restore 在 live 被调用 | 原 policy 仍拒绝；不得由 backup handoff 获得 activate permit |

## 最少验收矩阵

1. full schema10 disposable：disabled、paused、backlog、live 各一次登记成功；每次严格比较 anchor、control、公开文件前后不变。另测 anchor 缺失/旧 checkpoint/旧 generation；只允许 backup 行与既有 gateway 元数据变化。
2. 同一运行链两次自然形状的“快照→异机读→恢复演练→登记”，第二轮有真实 DB 增量，generation 可不变；证实无需 restore handoff/telemetry 补头。运行 operator 的 imported identity 必须是固定候选。
3. 反例逐项覆盖：篡改 report、成员 hash、恢复库 control、DB/投影错代、缺投递 receipt、错误 key、异机假成功、release/schema漂移、预检后 epoch 变化。验证拒绝时无新增 backup/fence 成功；写前反例另核对零 handoff/零持久化变化。
4. elapsedMs 缺失、负数、NaN、Infinity、恰好四小时、超过四小时；旧 recoveryPointAt + 新完成时间仍超龄拒绝，不因耗时取整或时间改写放行。
5. 同 package 重试幂等；**同内容、不同真实快照周期/package 两轮均成功追加不同 v2 checkpoint**；伪造新时间或未重新验证旧包被拒绝。覆盖 v1 旧包、v2 新包、未知算法、缺版本证据、旧新 reader/restore 交叉读取；历史行和原唯一约束不改写。
6. fence 竞态必测：DB 提交后、文件替换前修改 epoch/authority；相同窗口将 ready 改 false；较新 fence 已提交后旧包晚写；首次 fence 缺失；DB 成功而替换失败后的重试。证明单调性、false 不被打开及 single-writer 保护涵盖真实写入者；仅顺序执行测试或模拟 run lock 不算通过。
7. 权限反证：backup_worker 的 projection_pointer/activate 被原 gateway/trigger 拒绝；live restore 仍失败。原 restore binding 的错误 anchor/generation/hash 负例继续通过。
8. 固定 Node24 本地与 M1 隔离 staging 的 runtime closure/hash/import 验证；主路径及关键失败测试后，未参与实现的 Agent 独立审查。不能用本草案或单次 exit=0 标为生产闭环。

## 部署、回退与待决策

依赖顺序：主控当前快照调度恢复与逐周期收据 → 本职责/收据 successor 确认 → 本地实现与独立审查 → A03 独立异机证据接线与完整隔离验证 → 固定完整 runtime + wrapper + parser 同候选核收 → 经授权切登记入口 → 实测新鲜合法登记及至少下一自然周期。

零迁移路径仅在现字段承载、backup transaction authorizer、旧新 reader/restore 兼容实验全部通过后才可冻结为 schema10 部署；未通过时须先修订最小 successor 并重新授权，不能照草案直接切换。保留旧备份包；旧 runtime、wrapper 与 last-good fence 原样留作回退。仅切回旧登记程序会重新遭遇 live 阻断，因此回退应明确进入“快照继续、登记未恢复”的可见状态，不能宣称恢复了健康。不得回滚/删除已追加合法记录，也不得手工把旧 fence 改成当前时间。切换前分别验证旧/新 reader 对既有记录兼容。

主控需要一次性裁定的窄问题：**是否接受周期登记在所有 phase 均只追加经验证备份、从不自动激活 anchor，并以 v2 执行收据区分登记通过与恢复激活？** 本次确认范围包含上述 backup checkpoint v2 与同内容真实新周期成功、旧算法读兼容、fence 单调且不打开 ready，以及 zero-migration 的条件化验证门。A03 若无可用逐周期证据来源，应继续标阻断，不以放宽 offHostVerified 解决。

本文件没有执行任何上述代码修改、DB 写入、迁移、发布或生产切换。完整 restored DB/投影业务一致性、逐周期异机证据、暂停态成功、v1/v2 恢复兼容、跨 DB/fence single-writer 保障、并发/崩溃和生产自然周期尚需后继候选提供运行证明。
