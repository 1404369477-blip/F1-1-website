# F1+1 存量优先确定性安全初审与条件自动发布实施合同 v0.3

## 1. 版本关系、作用域与当前状态

本合同取代v0.2作为现行实施入口。v0.2保留不可变历史；其中“full/fallback各自嵌入对方最终manifest SHA”“互钉manifest SHA”和对应`RB-11`身份语义全部失效。

v0.2的以下部分继续作为本合同组成部分：v5 singleton与operation closed union；fresh/legacy/audit/outbox producer；phase/collector writer-lock栅栏；fallback人工能力和硬禁能力；sender producer allowlist；pre/post-COMMIT双层回退；备份、quiesce、DB锁；灾难恢复、再升级及除manifest配对外的负例。冲突时以`ADR-M5-BACKLOG-AUTO-PUBLISH-003`和本文为准。

当前M1仍为v4；0005、v5 schema fingerprint、full/fallback、pair receipt、stage verifier与pair verifier均未实现。runtime保持`disabled`。

## 2. 绝对禁止的递归身份

两份release manifest均不得出现以下字段或语义等价别名：

```text
pairedManifestSha256
fullManifestSha256
fallbackManifestSha256
pairReceiptSha256
stageReceiptSha256
pairVerifierReceiptSha256
deploymentManifestSha256
manifestSelfSha256
```

manifest的content/release root输入也不得包含这些值。pair receipt不得包含自身最终SHA、stage/pair-verifier/deployment receipt SHA。任何实现通过字段排除、占位值、二次回填、反复迭代或固定点搜索保留双向最终SHA关系，都不符合本合同。

## 3. `canonical-json-v1`

本任务相关的compatibility input、两份manifest、pair receipt和stage/pair-verifier receipt统一采用：

1. 输入必须为UTF-8、无BOM、有效Unicode scalar；字符串在进入canonicalizer前必须已经NFC，不一致即拒绝。
2. schema key均为ASCII；对象key按ASCII byte严格升序输出。数组顺序由各schema固定，不排序推断。
3. raw JSON parser必须在普通对象化前检测每个object level的duplicate key；duplicate、unknown、missing key全部拒绝。每个closed key精确出现一次，不使用默认值补齐。
4. 仅允许null、boolean、string和JSON safe integer。禁止浮点、指数表示、`-0`、NaN/Infinity和整数范围外数值。
5. string escaping采用JSON标准最短有效转义；禁止改变字符串字节含义。SHA字段精确为小写64hex；Git object ID使用项目构建时冻结的精确小写hex长度。
6. canonical对象输出为无额外空白的单行JSON；文件字节精确为`UTF8(canonical-json-v1(value) + "\n")`，文件末尾恰好一个LF。

verifier必须逐字比较重新生成的canonical文件字节；可解析但非canonical的JSON也拒绝。

### 4.2 root公式

```text
 migrationSelectorRootSha256 = SHA-256(UTF8(canonical-json-v1(migration.items)))
 nodeTargetRootSha256        = SHA-256(UTF8(canonical-json-v1(nodeTarget)))
 operationContractRootSha256 = contracts.operation.artifactSha256

pairContractInputBytes = UTF8(canonical-json-v1(pair-contract-input-v1))
pairContractRoot       = SHA-256(pairContractInputBytes)
```

`migration.selectorRootSha256`必须等于上式，`nodeTargetRootSha256`由完整closed nodeTarget对象复算；operation root必须等于被manifest closure固定的operation contract artifact文件SHA。两份manifest必须携带同一`pairContractRoot`并携带足以从冻结artifact复算上述对象的字段。只有root相等不足以构成一对release；最终pair身份由外部pair receipt SHA确定。

## 5. 两份独立release manifest

### 5.1 唯一角色

manifest schema精确为`f1plus1-v5-paired-release-manifest-v1`。full的`releaseRole`只能为`full_v5`；fallback的`releaseRole`只能为`v5_manual_only_fallback`。pair verifier要求两个角色各出现一次，两个manifest path、dev/inode、最终SHA和release root全部互异。

运行名称`v5-manual-only-fallback`可以作为UI/运维显示文案；安全字段只使用下划线形式的closed role，不接受别名。

### 5.2 每份manifest的closed顶层字段

```text

pairContractRoot
```

`runtimeFiles`、`nextBuild`、`productionDependencies`与`node`延续现行release manifest的完整closure语义，并由新schema逐层closed。`capabilities`使用closed enum：

| key | `full_v5` | `v5_manual_only_fallback` |
| --- | --- | --- |
| `internalAutoReview` | `contract_gated` | `forbidden` |
| `internalAutoPublish` | `contract_gated` | `forbidden` |
| `phaseEnterOrResumeBacklogLive` | `fresh_contract_gated` | `forbidden` |
| `collector` | `phase_contract_gated` | `forbidden_pre_network` |

`contract_gated`描述release具备受合同约束的代码能力，不表示runtime已启用。full仍以`phase=disabled`部署。

## 6. canonical `release-pair-receipt-v1`

### 6.1 生成时点与位置

只有两份manifest均已封存并取得最终文件SHA后才生成pair receipt。receipt是两个release closure之外的第三份owner-only文件；它不写入任一release目录，也不计入任一content/release root。

### 6.2 closed schema

顶层key精确为：

```text
schemaVersion                 = "release-pair-receipt-v1"
generationRule               = "pair-receipt-from-two-final-independent-manifests-v1"
pairContractRoot             = lower-64hex
gitCommit                    = lower-hex
gitTree                      = lower-hex
migrationSelectorRootSha256  = lower-64hex
schemaUserVersion            = 5
schemaFingerprintSha256      = lower-64hex
operationContractRootSha256  = lower-64hex
nodeTargetRootSha256         = lower-64hex
fullReleaseRole              = "full_v5"
fullManifestSchemaVersion    = "f1plus1-v5-paired-release-manifest-v1"
fullManifestSha256           = lower-64hex
fullContentRootSha256        = lower-64hex
fullReleaseRootSha256        = lower-64hex
fallbackReleaseRole          = "v5_manual_only_fallback"
fallbackManifestSchemaVersion= "f1plus1-v5-paired-release-manifest-v1"
fallbackManifestSha256       = lower-64hex
fallbackContentRootSha256    = lower-64hex
fallbackReleaseRootSha256    = lower-64hex
```

receipt生成器只能从已经canonical验证的compatibility input和两份manifest读取这些值。它必须验证shared字段逐字一致、role各一、manifest/release roots互异，再输出：

```text
pairReceiptBytes  = UTF8(canonical-json-v1(closed receipt对象) + "\n")
pairReceiptSha256 = SHA-256(pairReceiptBytes)
```

receipt没有`pairReceiptSha256`字段。最终SHA由外部统筹任务和production deployment manifest分别记录。pair receipt变化时必须产生新文件/新SHA/新部署锚，禁止把新SHA写回旧manifest或receipt。

## 7. 文件身份与replacement fence

### 7.1 私有文件门

在M1上，下列文件都必须是deployment manifest指定的绝对路径，且路径不能由HTTP、请求体、自由CLI参数或后续环境变量覆盖：

- full/fallback manifest；
- pair receipt；
- full/fallback stage receipt；
- 独立pair-verifier receipt。

每个文件必须满足：owner UID精确、普通文件、非symlink、mode`0600`、`nlink=1`、绝对规范路径、`realpath(path)=path`。pair receipt及stage/pair-verifier receipt的realpath必须位于两个release root之外。parent目录必须是owner控制且不可被group/world写。

### 7.2 no-replacement读取

verifier按以下固定次序处理每个文件：

1. 对deployment manifest固定路径做`lstat`，记录dev/inode/uid/mode/nlink/size；
2. 以no-follow、read-only FD打开；立即`fstat`并与lstat逐项相等；
3. 从同一FD完整读取一次，计算最终文件SHA，解析duplicate key并验证canonical/closed schema；
4. 读取后再次`fstat`，所有记录字段与首次fstat相等；
5. 在保持FD打开时再次`lstat+realpath`路径，确认仍指向同一dev/inode且权限/链接数不变；
6. 相关FD保持打开直到pair验证完成；迁移入口使用的manifest/receipt FD保持到0005 COMMIT或ROLLBACK之后。

任一truncate/append/replacement/rename/symlink/hardlink/chmod/chown/size或inode漂移全部失败关闭。单纯SHA相同但inode/path发生替换也拒绝。

## 8. M1双stage与独立pair验证

### 8.1 每个release独立stage

在M1、生产DB之外，从同一fresh一致性v4备份恢复两个隔离副本，分别执行：

- `full_v5`：manifest/closure verifier、v4→v5、v5 opener、phase disabled、合同指定HTTP/DB smoke；
- `v5_manual_only_fallback`：先由同候选、同SHA的专用migration入口把第二份v4隔离副本迁至精确v5，再执行manifest/closure verifier、fallback opener、人工HTTP review、fresh publish/correct/withdraw、producer合法outbox same-delivery sender，以及internal/system/enter-resume/collector pre-network硬禁负例；fallback runtime本身不取得migration授权。

每边输出一个strict `release-stage-verification-v1`：

```text
schemaVersion, releaseRole, pairContractRoot,
manifestSha256, contentRootSha256, releaseRootSha256,
gitCommit, gitTree, migrationSelectorRootSha256,
schemaUserVersion=5, schemaFingerprintSha256,
operationContractRootSha256, nodeTargetRootSha256,
stageDatabaseIdentityHash, sourceBackupManifestSha256,
verifierArtifactSha256, smokeContractVersion,
smokeResultRootSha256, smokeStatus="pass",
productionDatabaseTouched=false, collectorExternalCalls,
createdAt
```

fallback receipt的`collectorExternalCalls`必须为0；full receipt分别记录smoke内允许的loopback调用与collector探针调用，不能合并计数。两个stage DB path/dev/inode必须彼此不同且都不同于production DB；任一触碰production路径即FAIL。

### 8.2 独立pair verifier

pair verifier不是full/fallback runtime入口。其artifact SHA由外部deployment manifest固定。它接收外部锚定的：

```text
expectedPairReceiptSha256
expectedFullManifestSha256
expectedFallbackManifestSha256
expectedFullStageReceiptSha256
expectedFallbackStageReceiptSha256
```

verifier重新读取compatibility artifacts、两份release closure、两个manifest、pair receipt和stage receipts；复算所有root/最终SHA，验证角色唯一、shared字段相等、receipt字段逐字来自manifest、两个stage PASS且属于同一pair。成功后输出strict `release-pair-stage-verification-v1` receipt，至少固定上述五个expected SHA、pairContractRoot、pairVerifierArtifactSha256、两个smoke result root、`productionDatabaseTouched=false`和`status="pass"`。该receipt不包含自身SHA或deployment manifest SHA；先封存并取得receipt最终SHA，再生成production deployment manifest。receipt SHA不写回release manifest或pair receipt。

## 9. production deployment manifest与0005入口

production deployment manifest必须在prepare阶段由外部任务锚定最终文件SHA，并closed记录：三个核心expected SHA、对应绝对路径、两个stage receipt SHA/path、pair-verifier receipt SHA/path、pair verifier artifact SHA、唯一production DB identity/path、backup receipt、runtime仍disabled。待验证文件不能提供自己的expected值。

0005入口只消费security层从已验证deployment manifest生成的不可变授权对象；repository/migration函数不接收可独立传入的path或SHA。HTTP、环境变量、请求体、普通CLI参数和release文件都不能覆盖授权对象。

固定执行顺序：

1. 在打开production DB前完成§7、§8和deployment manifest全部验证；
2. 保持关键FD打开，quiesce全部writer/worker/sender并取得DB写锁；
3. 重验授权对象中的`expectedPairReceiptSha256 + expectedFullManifestSha256 + expectedFallbackManifestSha256`与当前FD字节；
4. 在同一transaction执行0005及v0.2全部data/audit/outbox验证；
5. COMMIT前再次fstat/path复核。漂移使transaction整体ROLLBACK，随后只按v0.2层A证明DB仍v4；
6. COMMIT后full只能使用receipt中的精确full SHA；full失败时fallback只能使用同一receipt中的精确fallback SHA。仅pairContractRoot相同、receipt不同的release不能替换。

## 10. identity负例矩阵

| ID | 输入 | 必须结果 |
| --- | --- | --- |
| PI-01 | 任一manifest嵌入对方/自身/pair/stage/deploy最终SHA | build/verifier拒绝，不生成pair receipt |
| PI-02 | duplicate/unknown/missing key | raw parse/strict schema拒绝 |
| PI-03 | BOM、空白、key顺序、转义、NFC、LF或uppercase hash不canonical | 字节比较拒绝 |
| PI-04 | full/fallback role重复、交换、别名、同path/inode/SHA/root | pair verifier拒绝 |
| PI-05 | pairContractRoot shared但Git/tree/migration/schema/operation/Node任一漂移 | verifier拒绝，不能凭root字符串放行 |
| PI-06 | pair receipt字段与任一manifest不一致 | receipt SHA/field复算拒绝 |
| PI-07 | receipt位于release closure、receipt写回manifest或重建后复用旧receipt | closure/path门拒绝 |
| PI-08 | expected三个SHA缺失、从待验证文件回读或可由HTTP/env/CLI覆盖 | deployment/migration入口拒绝 |
| PI-09 | mode≠0600、owner错、nlink≠1、symlink、realpath错、parent可写 | 打开前拒绝 |
| PI-10 | open前后或COMMIT前发生replace/truncate/append/chmod/chown/hardlink | FD/path fence拒绝；未提交migration回滚 |

| PI-13 | pair verifier artifact/receipt SHA错或未独立重算 | migration入口拒绝，DB保持v4 |

同时保留v0.2的`RB-01..10,12..13`和v0.1全部安全/并发/发布负例。原`RB-11`由`PI-01..14`完整取代。

## 11. 有限构建与废弃规则

```text
freeze compatibility input
  -> compute pairContractRoot
  -> independently build/hash full manifest
  -> independently build/hash fallback manifest
  -> generate/hash external pair receipt
  -> external task/deployment anchors 3 SHA
  -> M1 stages each release
  -> independent pair verifier
  -> only then permit prepare/0005 gate
```

第2、3步互不依赖。任一manifest或closure变化时，旧pair receipt、两份stage receipt、pair-verifier receipt和deployment permit全部废弃；从变化release的build开始重做。receipt不可原地改写后沿用旧SHA，release也不可在同一内容寻址路径静默替换。
