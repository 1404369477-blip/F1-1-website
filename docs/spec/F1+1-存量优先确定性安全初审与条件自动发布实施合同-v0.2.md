# F1+1 存量优先确定性安全初审与条件自动发布实施合同 v0.2

## 1. 版本关系与现行状态

本合同完整取代 v0.1 作为实施入口。v0.1 保留不可变历史，其中以下两条已失效：

- “回到已知/现行 manual-only runtime，保留 v5 表并由旧代码忽略”；
- “prepare 阶段验证旧 manual runtime 回退命令”。

v0.1 的确定性安全闭集、operation closed union、fresh binding、legacy provenance、phase/collector单 writer-lock 栅栏、存量 oldest-first、approved-only CAS、每批单 snapshot/outbox、same-delivery reconcile、last-known-good、source-independent snapshot key和逐源 stop fence仍作为本合同的组成部分。发生文本冲突时，以本合同及 `ADR-M5-BACKLOG-AUTO-PUBLISH-002` 为准。

当前 app opener精确只接受 `user_version=1..4`，collector repository只接受1或4，现行 review migration验证精确v4 fingerprint；这些事实不满足v5运行。当前M1仍为v4，full v5 release、`v5-manual-only-fallback`、migration 0005及本合同验收均未实现，runtime保持`disabled`。

## 2. v5 持久合同保持项

### 2.1 singleton与业务门

0005仍只新增一张singleton运行真值表：

```text
auto_publish_policy(
  policy_id="auto-publish",
  phase=disabled|backlog|live|paused,
  policy_epoch=positive integer,
  backlog_cutoff_at=UTC timestamp|null,
  max_batch=1..20,
  updated_at=UTC timestamp
)
```

默认值为`phase=disabled, policy_epoch=1, backlog_cutoff_at=null, max_batch=20`。Decision不增加policy_epoch字段；系统发布在同一事务重跑安全闭集并CAS当前epoch。v5可重建既有`admin_operation`、`audit_event`和`projection_outbox`以加入closed union/fresh/provenance/producer绑定；这不增加第二业务真值、第二审计账或第二队列。禁止复制业务DB、`ATTACH`、双写和down migration。

### 2.2 operation闭集

所有v5新写严格使用下列矩阵；`legacy_http_shaped_unknown`只由migration产生且迁移后只读：

| operation | channel | actor | fresh |
| --- | --- | --- | --- |
| `revision|approve|reject`（人工） | `http_post` | manifest唯一operator | null；session/Origin/CSRF仍必需 |
| `publish|correct|withdraw|auto_publish_control` | `http_post` | manifest唯一operator | 持久fresh binding必需 |
| `revision|approve|reject`（自动） | `internal_auto_review` | `system-auto-review-v1` | null |
| `auto_publish_batch` | `internal_auto_publish` | `system-auto-publish-v1` | null |
| pre-v5合法operation | `legacy_http_shaped_unknown` | 唯一primary AuditEvent actor | 不补造 |

internal行的method/path/status/HTTP response均为null，只写closed internal result；HTTP行必须为精确POST、operation-specific path和200..599 status。人工高风险mutation把operation/type/actor/request/resource/action/controlAction/fresh evidence/verified/expires在同一事务持久绑定。任一矩阵交叉、actor覆盖、fresh缺失/错绑/过期/重放或legacy新写均在领域mutation前拒绝。

### 2.3 phase、collector与系统发布

`disabled→backlog`和collector claim继续共用同一SQLite writer-lock栅栏：phase事务在一个`BEGIN IMMEDIATE`中重读singleton/source fence、证明0个running slot并原子写cutoff/phase/audit；collector在自己的`BEGIN IMMEDIATE`中先读singleton，`backlog|paused`时0 slot并在DNS/socket/HTTP前返回。barrier必须分别强制验证claim先锁与phase先锁。

系统发布只从当前candidate选择，CAS current source revision/full hash、latest Bundle、approved Decision、唯一queued Publication、phase/epoch/cutoff/source fence和上一outbox；每批1..20且只创建一份全量snapshot和一条outbox。response unknown只对同一delivery做receipt reconcile；公开reader始终使用last-known-good。非空media在缺机器可判定rights/license/policy字段时固定`MEDIA_POLICY_UNKNOWN/waiting`。上述语义在fallback中全部硬关闭，在full v5中也只有operator fresh启用phase后才可运行。

## 3. 双release构建与身份合同

每个可迁移候选必须同时产出：

```text
fullRelease.releaseRole      = "v5-full"
fallback.releaseRole         = "v5-manual-only-fallback"
full.schemaUserVersion       = 5
fallback.schemaUserVersion   = 5
full.schemaFingerprint       = fallback.schemaFingerprint = exact-v5-fingerprint
full.migrationSetHash        = fallback.migrationSetHash = hash(0001..0005 exact bytes)
full.pairedManifestSha256    = fallback.manifestSha256
fallback.pairedManifestSha256= full.manifestSha256
```

两个manifest还必须固定同一Git commit/tree、共享schema/repository模块content root、各自release root和全文件SHA、Node/runtime身份、DB opener policy、四通道operation矩阵、fresh binding schema、outbox producer binding schema、允许LaunchAgent/进程集、receiver loopback身份、public active root及stage receipt SHA。实际64hex、path、dev/inode/uid/nlink和LaunchAgent label均为构建/部署显式输入；任一仍Unknown时prepare失败。

full与fallback必须从同一candidate构建、一起stage、一起保留。任一release单独构建、manifest未互钉、migration/schema模块字节不同、release root可变或stage receipt不属于同一候选，都不允许接触生产DB。

## 4. DB opener闭集

| release | 唯一可打开DB | 必须拒绝 |
| --- | --- | --- |
| 现行v4 release | `user_version=4`且精确v4 fingerprint | v5、未知版本、fingerprint不符 |
| full v5 | `user_version=5`且精确v5 fingerprint | v4、未知版本、fingerprint不符 |
| `v5-manual-only-fallback` | `user_version=5`且同一精确v5 fingerprint | v4、未知版本、fingerprint不符 |

三者都必须existing-only打开manifest精确path/dev/inode/uid/nlink，`database_list`精确为`main,temp`，禁止symlink/hardlink/`ATTACH`/请求级路径覆盖，使用单writer和合同指定WAL/synchronous策略。opener失败发生在启动listener、scheduler、worker或外联之前。

旧v4 release不提供“忽略v5新增表”的兼容模式。0005 COMMIT后即使尚无自动业务写，普通代码回退也只能使用fallback；任何v5业务写后同样如此。

## 5. `v5-manual-only-fallback`能力闭集

### 5.1 允许能力

- 只读health、phase、候选、Decision、Publication、Projection、outbox/receipt和audit状态；
- manifest operator经真实HTTP POST执行人工`revision|approve|reject`；
- manifest operator经session/Origin/CSRF与持久fresh binding执行`publish|correct|withdraw`；
- manifest operator经fresh `auto_publish_control`执行`pause|stop`；
- 在§6 producer门内，由single sender投递或reconcile既有outbox。

人工HTTP路径、DTO、OperationReceipt、actor和AuditEvent仍按v5 closed union写入。fallback不可把operation降写成旧11列形态或legacy channel。

### 5.2 硬关闭能力

- `internal_auto_review`、`internal_auto_publish`、`system-auto-review-v1`、`system-auto-publish-v1`业务operation为0；
- `start_backlog|enter_live|resume_backlog|resume_live`始终拒绝且phase/cutoff/epoch/audit增量为0；
- collector、refiner、automatic reviewer、automatic publisher不得加载或被fallback manifest列为允许进程；
- 对collector脚本、repository claim或等价入口的误调用，在running slot、DNS、socket和HTTP前返回`FALLBACK_COLLECTOR_DISABLED`，`externalCalls=0`；
- raw queued Publication扫描、系统CAS发布、新snapshot/outbox创建为0。

fallback启动若看到`phase=backlog|live`，先进入control/read-only安全态。此时只允许只读和fresh `pause|stop`；人工内容mutation、sender新lease均为0。operator成功持久化`phase=paused`并重验DB/integrity/audit/outbox后，才开放§5.1的人工内容能力。fallback不得自行把phase改为paused，也不得以system actor代写control。

## 6. fallback sender与outbox producer绑定

### 6.1 v5 producer字段

0005对既有`projection_outbox`重建或加列，使每条outbox持久绑定：

```text
producer_operation_id  NOT NULL REFERENCES admin_operation(operation_id)
producer_channel       derived-and-trigger-checked
producer_operation_type derived-and-trigger-checked
producer_actor_ref     derived-and-trigger-checked
```

运行真值只取FK指向的immutable operation；派生列如落盘必须由trigger保证逐字一致。outbox、snapshot、Publication和producer operation在新写时同一事务提交。migration对pre-v5 outbox利用现有publication/snapshot/delivery与primary publish AuditEvent反查唯一旧publish operation；匹配计数不等于1、actor/entity/delivery不一致或旧operation无法迁移时，0005整体回滚。

### 6.2 fallback lease集合

fallback sender只可lease：

1. `producer_channel=legacy_http_shaped_unknown`且`producer_operation_type=publish`的迁移前既有outbox；
2. `producer_channel=http_post`、type为`publish|correct|withdraw`、actor为manifest operator、fresh binding与snapshot/Publication精确相等的fallback人工新outbox。

`internal_auto_publish`、unknown/缺失/重复producer、错actor、错fresh、错snapshot、错Publication或表外type全部不得lease。fallback启用前已经被full v5的internal actor创建但未收敛的outbox保留原字节并形成blocker；fallback只读显示并保持public last-known-good，等待重新进入匹配full v5处理，不能伪装成人工outbox。

sender只做传输状态机：优先对`reconcile_wait`执行同一delivery receipt GET，明确404后才可重投同一签名package；成功/终态状态仍写现有outbox/receipt/audit。它不能创建Decision、Publication、Projection、snapshot或outbox，不能改producer绑定，也不能提高generation。receiver endpoint必须为manifest精确loopback，其他地址拒绝。

这里的sender service identity只用于投递audit，不等于两个system auto actor。fallback验收分别报告：`system-auto-review-v1/system-auto-publish-v1 operation=0`、collector `externalCalls=0`、sender允许的loopback delivery/reconcile调用数。

## 7. 固定prepare、迁移与启动顺序

### 7.1 同候选stage

1. 构建full v5与fallback并互钉manifest SHA。
2. 从fresh一致性备份恢复隔离副本；在该副本完成一次v4→v5、full/fallback opener、人工HTTP/DB、fresh/audit、outbox/sender和§10负例演练。
3. 记录stage receipt，至少含两个manifest SHA、v4/v5 fingerprint、migration hash、各操作计数、0-system/0-collector门和恢复结果。stage失败不进入生产prepare。

### 7.2 生产停写和备份

1. 生成SQLite一致性备份，不复制活跃DB/WAL/SHM作为备份；记录恢复点UTC、hash/manifest、`backupAge<15m`并在隔离位置验证v4 fingerprint/integrity/audit/outbox。
2. 记录生产DB path/dev/inode/uid/nlink、v4 fingerprint、audit tail、public active generation、outbox/receipt集合和两个release manifest。
3. quiesce Admin HTTP writer、collector、refiner、automatic reviewer/publisher、sender。等待在途HTTP结束；所有`ingest_run.running`必须终态。sender lease必须先沿同一delivery收敛，或持久化为可证明的`reconcile_wait`后关闭。任一状态Unknown时停止。
4. 卸载所有可写LaunchAgent并取得唯一DB写锁；再次验证没有writer/running slot/active lease。

### 7.3 migration原子边界

1. 锁内重验唯一DB identity、`database_list=main,temp`、无`ATTACH`、`user_version=4`、精确v4 fingerprint、integrity、audit/outbox和备份freshness。
2. 在一个migration transaction内执行0005，重建operation/audit/outbox及singleton；复制旧值/storage class/byte identity，保持旧canonical audit hash，不重算旧event hash。
3. COMMIT前验证`user_version=5`、精确v5 fingerprint、row count/ID/FK、legacy provenance、fresh nullness、operation closed union、outbox producer唯一绑定、audit chain和singleton默认disabled。
4. 任一失败执行ROLLBACK；只有再证明DB精确回到v4且identity/audit未漂移，才可进入层A并启动旧v4。无法证明时保持卸载。
5. COMMIT成功后进入层B；再以只读v5 opener重验同一inode/fingerprint/integrity/data/audit/outbox，旧v4从此禁止打开该DB。

### 7.4 启动与fallback切换

1. 先启动full v5，仍为`phase=disabled`；完成listener前opener、capability、DB/audit/outbox和零自动operation健康门。
2. full健康门失败：停止full及其worker，保持DB/增量不变，验签配对fallback manifest后启动fallback。
3. fallback只打开同一v5 inode；phase为disabled/paused时按§5运行，phase为backlog/live时按control/read-only安全态运行。
4. fallback失败：所有writer/sender保持关闭，public继续last-known-good，进入人工恢复。不得尝试旧v4 release或自动恢复迁移前备份。

## 8. 两层回退执行表

| 边界 | 允许动作 | 禁止动作 | 数据结论 |
| --- | --- | --- | --- |
| 0005 COMMIT前 | transaction ROLLBACK；精确v4复核后重启配对v4 release | 不明状态下旧代码试开 | DB仍v4，audit/outbox/identity无漂移 |
| 0005 COMMIT后 | 停full，验签并启动`v5-manual-only-fallback` | v4 release、down migration、恢复旧备份、复制/ATTACH/双写 | 同一v5 inode，保留全部v5增量 |
| full与fallback均不能安全开v5 | 经明确灾难恢复授权恢复迁移前备份 | 将备份恢复称为普通rollback或无损 | 明确丢失窗口与audit fork |

## 9. 灾难恢复与再升级

### 9.1 恢复迁移前备份

仅在v5 DB不可恢复，或full和fallback都因精确schema/data安全原因无法打开时使用。执行前：

- 停止Admin、所有worker、sender和receiver切换，冻结public last-known-good；
- 只读封存故障v5 DB/WAL/SHM、release manifests、logs、receipt、audit tail并计算SHA；
- operator记录明确授权、恢复点UTC、预计/实际丢失起止、故障v5 audit tail、备份v4 audit tail、active generation和receiver receipt集合；
- 新建可追踪recovery/fork identity，禁止把恢复后v4 chain与故障v5 chain静默拼接或重算。

恢复点之后的v5 operation、Decision、Publication、Projection、snapshot、outbox、receipt和audit全部属于可能丢失集合。`RPO≤15m`只在备份年龄与恢复演练门真实满足时成立；仍需报告实际丢失窗口。恢复出的v4 DB只由精确v4 release在隔离恢复分支打开；完成public/outbox/receipt人工一致性裁决前不允许新发布。

### 9.2 返回full v5

从fallback返回同schema full v5：quiesce fallback Admin/sender、锁同一DB、验证v5 fingerprint/integrity/audit/outbox和新配对manifest，再以disabled/paused启动full；保留fallback期间全部人工增量。若下一release需要schema>v5，先接受新的migration successor并预构建相同新schema的manual-only fallback，禁止让任何release打开自己不理解的DB。

从灾难恢复v4返回主线：先完成public/receiver/outbox裁决，再重新执行§7的双构建、fresh备份、quiesce和v4→v5。不存在v5→v4 down migration。

## 10. 定向验收与负例

只在未来实现任务中执行；本产品合同没有产生运行收据。

| ID | 验收 | 精确出口 |
| --- | --- | --- |
| RB-01 | 0005 COMMIT前故障 | ROLLBACK后v4 version/fingerprint/audit/outbox/identity相等；v4 opener成功 |
| RB-02 | 0005 COMMIT后旧release | v4 opener在listener/写入前拒绝v5，业务增量0 |
| RB-03 | 双opener | full/fallback只开精确v5；v4/unknown/错fingerprint/错inode全拒绝 |
| RB-04 | fallback operation矩阵 | 人工revision/approve/reject和fresh publish/correct/withdraw成功；internal/system/enter-resume组合增量0 |
| RB-05 | fallback进程与网络 | collector/refiner/auto reviewer/publisher进程0；collector running slot=0、DNS/socket/HTTP=0、`externalCalls=0` |
| RB-06 | phase故障态 | backlog/live DB只开放read/control；fresh pause/stop后进入paused；无自动代写 |
| RB-07 | pre-v5 outbox | migration唯一producer回填，fallback sender same-delivery成功/reconcile |
| RB-08 | fallback人工outbox | fresh HTTP producer同事务绑定，sender投递；无第二snapshot/outbox |
| RB-09 | illegal outbox | internal/unknown/重复/错producer不得lease，public保持last-known-good |
| RB-10 | full→fallback | 同一inode/version/fingerprint，full已提交v5 operation/audit/outbox逐项保留 |
| RB-11 | manifest pairing | 错Git tree、错migration/schema hash、错paired manifest或错release root均启动前拒绝 |
| RB-12 | disaster restore | 报告恢复点、可能丢失集合、v5/v4 audit tails与fork identity；不宣称普通无损回退 |
| RB-13 | re-upgrade | fallback人工增量保留，锁内验证后full在disabled/paused启动 |

另保留v0.1的operation closed-union、fresh错绑/重放、legacy provenance、双writer-lock barrier、媒体policy unknown、single snapshot/outbox和same-delivery全部负例。任一项Unknown时运行态保持disabled，迁移/load/cutover不得继续。
