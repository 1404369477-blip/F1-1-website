# Agent 协作规则

> 这是所有 AI Agent 共用的工作规则。`AGENTS.md` 和 `CLAUDE.md` 只做入口,不要重复写长规则。

## 读取策略

为节省上下文,先读必要文件,不要一上来全量读取整个仓库。

| 场景 | 必读 | 按需读 |
|------|------|--------|
| 每次开始任务 | `docs/spec.md`、`docs/progress.md` 最新记录 | `docs/overview.md`、`docs/roadmap.md` |
| 技术选择 / 新依赖 | `docs/spec.md`、`docs/decisions/` | `docs/conventions.md` |
| 接续中断工作 | `docs/handoff.md`、`docs/progress.md` | 相关代码和决策记录 |
| 大改方向 | `docs/spec.md`、`docs/roadmap.md`、`docs/decisions/` | `docs/overview.md` |
| 写代码 | `docs/spec.md`、`docs/conventions.md` | 相关代码、测试、已有相似实现 |

`docs/spec.md` 是当前唯一开发准绳。其他文档如果和 Spec 冲突,以 Spec 为准,并提醒用户同步修正。

## 开发节奏

1. **Foundation**:只搭地基,不选技术栈,不写业务代码。
2. **Spec v0**:先写清楚问题、用户、场景、边界和成功标准。
3. **Risk Check**:先找最大风险,可能是需求、UI、数据、权限、成本或技术可行性。
4. **Spec v1**:冻结 MVP 合同,写清功能范围、技术路线、验收标准和不做什么。
5. **Kickoff**:用户确认后再初始化 `app/`,补齐命令、环境变量示例和首次可运行验证。
6. **Build Loop**:一次只做一个功能切片,计划 → 实现 → 验证 → 更新进度 → commit。

## 执行前拆分与委派

- 主 Agent / 统筹部在开始任何非琐碎执行前,必须先判断任务能否拆成边界清晰、可独立交付、可独立验收的子任务,再决定由自己执行还是委派。
- 用科斯定理比较委派的沟通、交接、冲突与复核成本和自行执行成本。委派总成本更低时,优先分配给职责匹配的部门、子 Agent 或用户已授权的外部 Agent;不要为了形式上的多 Agent 强行拆分高耦合工作。
- 主 Agent 默认负责目标澄清、方案与边界、任务分配、冲突裁定、证据审核、最终验收和向用户反馈;执行层负责实际实现与落地,审核层必须独立验证且不得替执行层修复。
- 用户明确要求主 Agent 只做统筹、审核和反馈时,主 Agent 不得再主动新增实现、部署、测试或外部写入动作。已经开始且无法安全中断的动作只允许自然收口、保留现场并交由执行层接管;主 Agent 仅核收结果。
- 适合委派的任务至少要写清目标、允许写入范围、禁止触碰范围、输入与依赖、验收出口、回退方式和 1–3 个失败路径。共享脏工作区、共享 schema/API、密钥、权限、生产或付费动作存在冲突时先阻断,不得让多个 Agent 盲目并发。
- 外部 Agent（包括 Grok 等）的输出只能作为候选证据;必须保留可复核来源或运行收据,并由主 Agent 或独立审核层复核后才能进入正式方案、代码或生产。
- 只有琐碎、局部、立即可逆且委派成本明显更高的工作,主 Agent 才可直接执行;完成回报中要说明为何没有委派。

## 阶段门槛

- **进入 Spec v1 前**:必须说清目标用户、核心场景、MVP 范围、不做什么、验收标准和主要风险。
- **进入 Kickoff 前**:必须完成风险检查,把结论写入 `docs/spec.md` 或 `docs/decisions/`,并确认是否需要 UI 原型、数据验证或技术小实验。
- **初始化 `app/` 前**:必须得到用户确认的技术路线,重要选择写入 `docs/decisions/`;同时定下 `app/` 内部布局——源码、测试、配置各放哪——写入 `docs/conventions.md`,此后所有代码和测试按此归位,不要随手乱放。
- **进入 Build Loop 前**:项目必须能以空骨架启动或通过最小验证。

## 改动前检查

- 写代码或改文件前先看当前变更状态,确认有没有用户或其他 Agent 留下的未提交改动。
- 不要覆盖、删除或回滚不属于本次任务的改动;如果这些改动影响当前任务,先向用户说明再继续。

## 改动分级

- **A 级:高风险**。删除数据、改权限/认证/支付/密钥、发送消息、调用付费 API、改部署、跨多文件大重构。先写方案和回退方式,等用户明确确认。
- **B 级:用户可感知**。功能、UI、文案、单模块业务逻辑。动手前简述意图,做完验证。
- **C 级:局部可逆**。文档、注释、typo、测试、小范围整理。可直接做,但仍要说明结果。

## 安全边界

- 未经用户确认,不提交 `.env`、token、密码、私有链接、手机号、邮箱、身份证等真实敏感信息;必须出现时优先用示例、脱敏或环境变量。
- 新增依赖前先说明用途、替代方案和风险。
- 不理解的代码先问,不要直接删。
- 大改先更新 `docs/spec.md`;如果 Spec 与其他文档冲突,以 Spec 为准并提示同步修正。
- 涉及删除、付款、授权、发送消息、发布内容、生产配置和外部付费 API 时,必须先让用户明确确认。
- 实验脚本、调试输出、临时大文件放 `scratch/`(用完即弃,不提交);**正式测试是代码,属于 `app/`**,按 `docs/conventions.md` 定的布局归位,不要丢进 `scratch/`。

## 完成标准

完成必须同时满足:

- 改动符合 `docs/spec.md`。
- 已验证,并说明怎么验证。
- 更新 `docs/progress.md`。
- 一个完整功能切片完成后应提交;如果暂不提交,说明原因。
- 需要交接时更新 `docs/handoff.md`。

## 变更控制

长期维护产品的大改不要直接进代码。先在回复或 `docs/spec.md` 里说明:

- 改什么
- 为什么改
- 影响哪些页面、数据、接口或文件
- 如何验证
- 如何回退

用户确认后,再更新 Spec 和代码。

## UI / 设计可视化确认

凡涉及 UI、交互、视觉呈现、页面布局、设计稿、用户体验路径的节点,设计产出不能只交文字说明、ASCII 线框、Markdown 表格或抽象结论;必须提供用户可直接判断的可视化预览。

- 优先使用 OpenDesign 等专用设计工具生成可编辑设计产物或 artifact。
- 如果当前会话未热加载 OpenDesign MCP、OpenDesign 没有 active project、权限不足或工具连接失败,必须明确说明失败原因,并用本地 HTML + PNG 截图、Figma、可打开图片预览等方式兜底。
- OpenDesign 接入时,先确认本机 OpenDesign App 是否运行,再确认 daemon 健康状态;不要假设默认端口一定是 7456,应从 OpenDesign 日志或本机监听端口确认实际 daemon URL。
- 若 OpenDesign artifact 写入提示没有 active project,要求用户在 OpenDesign 内创建或点进项目,或使用兜底方案交付,不能卡住节点。
- 未安装 / 未运行 OpenDesign、权限不足、连接失败或 MCP 未热加载时,主动询问用户是否需要帮忙安装 / 启动 / 授权 / 注册 MCP / 重载或新开会话。
- 用户不想处理 OpenDesign 或不愿意重载 / 新开会话时,不得卡住,应按用户偏好直接选择本地 HTML + PNG、Figma 或可打开图片预览。
- 设计回报必须同时包含设计说明文档路径和可视化预览路径;若使用兜底方案,写清 OpenDesign 当前状态和后续恢复条件。
- 用户确认设计视觉或交互方向前,不得进入正式实现。用户只反馈功能方向 OK 但 UI 未确认时,只能推进功能可行性或技术评估。

## 本项目协作覆盖规则

- 本项目的 UI / 设计可视化要求高于协作层通用默认值。凡涉及 UI、交互、视觉呈现、页面布局或用户体验路径,统筹部必须在 TASK 的交付物和验收出口中显式写入可视化预览与用户确认门禁;设计部不得按“未明确提出则不预览”的通用默认值省略。
- 研究部负责公开证据、事实核验和不确定性说明;产品部负责吸收证据、做范围与系统决策并维护 Spec / 系统 ADR。研究部不直接冻结产品合同。
- 设计部提交设计说明、可视化产物和交互证据;涉及 Spec 合同变化时由产品部吸收并走确认流程,避免多部门并发修改同一产品合同。

### 后续开发派单全局验收硬门

用户于 2026-08-09 明确确认：开发部必须高度贴合已冻结视觉设计，并落实 [初版全功能追踪矩阵](spec/F1+1-初版全功能追踪矩阵-v0.1.md) 中所有已确认的 Function ID。统筹部创建任何开发任务时，TASK JSON 的正文、验收出口和失败路径必须逐项绑定以下内容；缺一项时不得把任务派成可完成出口：

1. **设计身份**：冻结设计的版本号、固定路径和完整 SHA-256；实现候选不得引用可变 Demo、口头描述或“最新版本”代替精确身份。
2. **功能覆盖**：本任务涉及的每个 Function ID、矩阵精确行和当前状态；统筹部必须跨开发任务保证全部已确认 Function ID 均有实施或明确阻断归属，禁止通过波次划分静默遗漏、合并或改名。
3. **真实用户出口**：每个 Function ID 的真实路由、操作入口或 operator 入口，以及从输入到结果的可达链路；组件存在、静态分支和测试专用入口不算真实出口。
4. **状态与恢复**：正常状态、loading/empty/error/404/partial/offline 等适用状态、失败 reason、重试/回退/清理和恢复到可继续操作位置的完整链；只验证 happy path 不得完成。
5. **视觉证据矩阵**：运行中真实候选的 1440、1024、390 三档 × 深色、浅色两主题证据，并逐项映射冻结视觉锚点和 Function ID；截图、浏览器断言与候选代码/数据必须绑定同一版本和 hash。
6. **完成禁区**：占位内容、隐藏调试入口、DRAFT 控件、静态复制、人工注入、组件预留、`NOT_RUN`、SKIPPED、TODO 或只有开发自测时，相关 Function ID 继续保持 `P1-blocker` 或原用户门禁，开发任务不得 `complete`。
7. **视觉缺口回退**：任一 Function ID 缺视觉锚点、冻结设计无法表达真实状态，或实现需要改变已确认视觉时，开发部必须立即 `block` 并退回设计部补锚点；开发部不得自行补画、猜测或静默偏离。

开发部的 `complete` 回报必须按 Function ID 给出产物、六格视觉证据、真实入口/状态/恢复验证和未验证项。统筹部在上述字段不完整时不得核收；测试部与设计部必须对同一候选独立复验，不能用历史快照 PASS、占位证据或其他任务的 `NOT_RUN` 代替。

### Admin 双端能力与入口恢复全局硬门

用户于 2026-08-09 确认：Admin 在 Mac 与 iPhone 必须具备全部后台操作能力，日常采用方案 C（私有日常入口 + 默认关闭的受控应急入口），并接受两端安装私有网络客户端。后续产品、设计、安全、数据、开发 TASK 的正文、验收出口和失败路径必须同时满足：

1. **双端功能等价**：每个已确认 Admin Function ID 必须同时绑定 Mac 与 iPhone 的真实入口、状态链、失败恢复和完成证据；禁止以移动端、触屏、窄屏或客户端限制为由删减、隐藏或永久降级功能。
2. **允许的适配**：两端可以采用不同布局、导航层级、手势和信息密度；适配后仍须保持同一操作语义、结果、审计收据与恢复能力。
3. **高风险再认证**：删除、发布、撤回、权限、凭证和应急切换等高风险动作可增加 fresh re-auth、二次确认或设备级验证；再认证只能作为安全门，成功后两端都必须能完成对应操作。
4. **日常私有入口**：Mac 与 iPhone 均以已安装的私有网络客户端进入日常 Admin；具体供应商、协议、身份、会话和设备准入继续由产品/安全合同冻结，不能把隐藏 URL、`robots.txt`、前端路由或仅登录页当作网络隔离。
5. **受控应急入口**：应急入口默认关闭，后续合同必须定义开启授权、强认证、时限、最小暴露、审计、撤销与关闭后验证；用户未另行确认前，禁止把它写成长期开启的公网后台或日常备用入口。
6. **冗余、备份与恢复**：后续合同采用标准级冗余；RTO 保持 `≤4 小时`，最终 RPO 为 `≤15 分钟`。产品、安全、数据、开发任务必须逐项绑定：
   - 由合同明确的一致性机制生成备份，使数据库、WAL/日志和关联 manifest 对应同一可恢复边界；禁止把运行中的 SQLite 主文件或活跃 DB/WAL/SHM 文件直接复制后当作有效备份。
   - 备份频率、成功时间线和可恢复点证据必须证明任意数据损失窗口 `≤15 分钟`；过期、缺档或无法形成恢复点时立即进入失败状态。
   - 备份必须加密保存到与主机故障域分离的异机位置；具体存储、密钥托管、轮换、保留和删除策略由后续产品/安全合同冻结，不能把长期公网 Admin 入口当作恢复设施。
   - 每个备份集必须有可校验的 hash 和 manifest，至少绑定备份身份、生成时间、恢复边界、文件集合、字节数、schema/格式版本、加密或密钥版本及保留策略；hash、manifest、文件或解密条件不一致时禁止恢复或宣称成功。
   - 必须在隔离目标上执行恢复演练，验证完整性、一致性、可启动性、RPO `≤15 分钟`、RTO `≤4 小时` 和业务恢复点；只验证“备份命令成功”不得完成。
   - 备份失败、恢复点超龄、hash/manifest 不匹配、异机保存失败、解密失败或恢复演练失败必须产生可判定失败状态和告警，并保留重试、升级、回退及人工处置收据。
   未经用户另行确认，禁止升级为数据库双活、跨地域双活或长期公网备用入口，也不得用这些能力绕过上述一致性备份与恢复证据。
7. **完成与核收**：产品合同必须有双端功能映射和恢复边界；设计必须提供 Mac/iPhone 的完整操作视觉与关键状态；开发必须在同一候选上交两端逐 Function ID 的真实可达证据。任一端存在功能删减、隐藏调试、占位、`NOT_RUN` 或只有静态稿时，相关任务不得 `complete` 或 ACK。

上述决定只冻结后续合同和派单硬门，不代表 Admin、私有网络、应急入口、生产认证、跨网络访问、标准级冗余或任何真实外部能力已经实施或放行。
