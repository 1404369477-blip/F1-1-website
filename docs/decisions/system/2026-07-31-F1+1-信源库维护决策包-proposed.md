# F1+1 信源库维护决策包（proposed）

> “先 A、后 D”的窄范围架构路线已由独立 [ADR-SOURCE-001](./2026-08-01-F1+1-信源库A到D演进路线-accepted.md) 接受；本文件整体仍为 `proposed`，其中字段、阈值、表单、迁移和运维细节没有随路线一并 accepted。本文件不创建或修改真实飞书资源，也不授权任何真值或采集器切换。

## 0. Proposed 结论

1. **[已接受决策｜ADR-SOURCE-001｜2026-08-01]** **D 作为目标形态、A 作为 Base 真值建立后的起步阶段**。先建立 Base 单一业务真值并在独立门禁后进入 A 在线直读；A 稳定后验证 Base 到本地 last-known-good 只读快照，再经独立门禁进入 D。
2. **[已接受决策｜ADR-SOURCE-001]** B、C 不作为当前信源库主路线。**[产品建议]** 原比较理由保持不变：B 的手机录入摩擦与用户已确认场景冲突，C 为 59 条记录提前引入移动服务、鉴权和运维。
3. **[已接受决策｜ADR-SOURCE-001]** D 的本地文件严格由 `Base → 本地` 单向生成，只是可重建的 Collector 读模型；本地修改永远不能反写或裁决业务状态，Base 始终是唯一业务真值。
4. **[产品建议]** 手机最短入口只有 `raw_url` 必填、`capture_note` 可选；规范化、查重、分类和证据补全放到后续维护流程。
5. **[用户已确认｜2026-07-31]** 新信源完成 URL 规范化与信源查重后，在平台适配器已有合法授权和可用能力时立即进入采集队列；不等待账号身份或 F1 相关性核验，全部拟公开内容仍须人工审核。
6. **[已验证事实]** 当前清单共有 59 个唯一 X 账号 URL；这些既有记录的身份状态、可监控性和最终启用结果仍未验证。

只有 [ADR-SOURCE-001](./2026-08-01-F1+1-信源库A到D演进路线-accepted.md) 所列的 A→D 顺序、单一真值、单向快照和独立切换门禁已 accepted；本包其余内容及本包自身状态继续保持 `proposed`。路线接受不授权真实飞书资源创建、账号授权、59 条导入、Base 业务真值切换、A/D provider 切换或自动公开。

## 4. A / B / C / D 选择

### 4.1 清晰选择

| 方案 | 当前产品结论 | 主要理由 | 阻断或代价 |
|---|---|---|---|
| **A｜飞书 Base 单一业务真值** | **短名单；D 的起步阶段** | 手机表单最薄、维护实体最少、符合单人维护 | 采集器读取依赖飞书 API；故障时没有独立 last-known-good 发布集合 |
| **B｜Git JSONL 单一业务真值** | **当前不推荐** | 审计、diff、迁移和采集器读取清楚 | 纯方案手机录入步骤最多；增加临时入口又引入交接维护 |
| **C｜SQLite 单一业务真值** | **当前后置** | 事务、唯一约束、查询和批处理强 | 59 条规模下收益不足以覆盖手机 Web 入口、TLS、鉴权、托管和备份成本 |
| **D｜飞书真值 + 本地只读快照** | **目标方案，产品首选** | 保留手机表单体验；飞书短时不可用时采集器仍可读最后正确集合；快照可版本化 | 比 A 多一个只读同步作业、凭证、告警、全量对账和恢复责任 |

### 4.2 A / D 短名单权衡

**[已验证事实｜S3]** 研究矩阵得分为 D 90.8、A 88.6、B 71.6、C 67.8；移除尚未确认的待验证维度后，排序仍为 D 90.3、A 88.0、B 72.2、C 67.2。评分属于研究判断，不是产品实测或用户批准。

| 决策维度 | A | D |
|---|---|---|
| 手机录入 | 飞书表单 | 与 A 相同 |
| 业务真值 | Base | Base |
| 采集器读取 | 在线查询 Base | 读取本地 last-known-good 快照 |
| 飞书短时故障 | 本轮信源读取停止并告警 | 保留旧快照继续读，同时暴露 `snapshot_age` |
| 数据一致性 | 组件少 | 需全量校验、原子替换和单向冲突规则 |
| 日常维护 | 较低 | 比 A 多同步、凭证与监控 |
| 退出能力 | `.base` / CSV 导出 | A 的导出 + 版本化发布快照 |

### 4.3 已接受的 A → D 路径（实施细节仍 proposed）

**[已接受决策｜S4]** A 先行、稳定后进入 D；**[产品建议]** 当前实施分解为：

1. 先按 A 的字段合同建立唯一业务真值与手机入口；
2. 在不切换采集器的情况下，开发只读全量同步并生成影子快照；
3. 验证分页完整性、唯一性、筛选条件、校验和、原子替换、过期提示和恢复；
4. 用户另行确认切换后，采集器才读取本地 last-known-good 快照；
5. 如果同步成本或授权条件不成立，停留在 A，不增加第二套业务写入口。

路线顺序与跨阶段不变量以 S4 为准。资源创建、Base 业务真值切换、A `base_direct` 切换和 D `base_snapshot` 切换仍需分别确认或授权；本节的字段与操作细节继续保持 proposed。

## 5. D 的单一真值与同步合同（Base 真值切换后）

### 5.1 强制不变量

1. **[产品建议]** 只有 Base 可以修改信源的存在、身份验证、启用、停用、拒绝、证据和优先级。
2. **[产品建议]** 同步方向固定为 `Base → 本地只读快照`；禁止本地反写、双向合并或“以最新修改时间为准”。
3. **[产品建议]** 冲突时 Base 无条件胜出；本地快照可删除并从 Base 全量重建。
4. **[产品建议]** 本地文件只包含满足用户确认后的 `publish_predicate` 的采集集合，不承载候选、拒绝、停用记录或完整业务审计。
5. **[产品建议]** Collector 只读明确版本的完整快照，不能把飞书 API 空响应、缺页或同步失败解释为“白名单已清空”。

### 5.2 快照发布合同

每次同步按以下顺序执行：

1. 读取全部非 tombstone Base 记录，并确认分页结束条件与总量；
2. 对全部业务记录先校验 `source_id`、稳定账号 ID 和当前 canonical URL 的全局冲突；冲突项进入隔离，涉及当前启用集合时阻断新快照；
3. 使用唯一的 `publish_predicate_id/version/digest` 过滤；
4. 校验 schema、必填字段、允许枚举、记录数和 destructive delta；
5. 在临时位置生成排序稳定的完整快照与 manifest；
6. 只有整版校验和一致性读取检查通过才原子替换 last-known-good；
7. 采集器读取新 `source_config_version`；所有采集任务携带 expected version，旧版本在途结果只记审计，不更新当前信源状态或生成新内容；
8. 周期性全量对账，事件订阅未来只能触发同步，不能充当业务真值。

manifest 最少包含：

- 单调 `source_config_version`、`snapshot_id`、`generated_at`；
- `base_revision/read_watermark`、读开始/结束时间；
- `publish_predicate_id/version/digest`；
- schema 与 `normalizer_version`；
- Base 记录 ID、记录数、内容校验和；
- `previous_snapshot_hash`。

**[unknown]** Base API 是否提供满足要求的一致性 revision token 尚未验证。若没有，发布前至少执行稳定排序的读前/读后 watermark 校验，或连续两次全量读取摘要一致；任何一项不一致都不发布新快照。

### 5.3 故障处理

| 故障 | 安全状态 | 恢复 |
|---|---|---|
| Base/API 不可用 | 保留 last-known-good；标记快照变旧并告警 | 权限或服务恢复后全量读取和对账 |
| token 失效 / scope 不足 | 同步停止，不覆盖快照 | 重新授权后全量同步；不得静默降级为匿名抓取 |
| 缺页、记录数异常、schema 错误、全局唯一性冲突 | 阻断受影响的启用集合或整版发布 | 回 Base 或查询逻辑修正后重跑 |
| 本地快照被手改 | 校验和失败，采集器拒绝新文件 | 从 Base 全量重建；禁止反写 |
| 删除量、启用集合缩减或关键 high 来源变更超出已定义 delta 门槛 | 保留 last-known-good，等待 Base 内批准记录 | 复核变更事件；批准后重跑，误操作则先恢复 Base |
| Base 误删 | 由于日常只允许软删除/tombstone，未批准硬删除不得进入发布 | 用 Base 历史或覆盖全部业务记录的独立备份恢复，再重新生成快照 |
| 授权受限、主体转换等紧急停用 | 使用只减不增的运行安全 deny overlay 立即阻断对应来源 | 追加审计并尽快回写 Base；overlay 不能新增、改身份或成为长期真值 |

**[unknown]** `snapshot_age` 告警/停止阈值、destructive delta 阈值和完整备份的频率、保留期、异地副本、校验与恢复演练周期，需结合采集周期、值班能力与业务容忍度确定。D 在这些参数形成明确合同前不能激活。

### 5.4 真值切换与唯一读取提供者

任何时刻最多只有一个 `active_source_config_provider`；Collector 运行时必须恰有一个，门禁间隙允许停止。每次切换递增 `source_config_epoch`：

| 阶段 | 业务真值 | active provider | 旧路径规则 |
|---|---|---|---|
| 迁移前 | legacy 清单 | `legacy` | 仍按现状维护 |
| Base 影子导入 | legacy 清单 | `legacy` | Base 只影子，不参与正式采集 |
| Base 真值已切、A provider 未切 | Base | `none / paused` | legacy 冻结；Collector 停止，不得继续按 legacy 采集 |
| Base 真值切换后（A） | Base | `base_direct` | legacy 冻结为只读证据，禁止修改或合并 |
| D 切换后 | Base | `base_snapshot` | `base_direct` 休眠；本地只读快照供采集 |

Base 真值切换和 A 读取 provider 切换是两个独立门禁；两项均获批准后可以原子提交，但一次事务不能代替两次授权。若 Base 已先成为真值而 A 门禁尚未通过，Collector 停止。D → A 回滚只把 provider 切回 `base_direct` 并读取当前 Base；若直读不可用，只能使用与明确 Base revision 对应的已批准快照或停止。任何回滚都不能恢复 legacy 旧名单、撤销 Base 中的停用/删除，或把旧 epoch 的在途结果写回当前状态。

### 5.5 配置真值与运行遥测

`Base → 本地` 单向合同只承载信源配置。Collector 产生的最近采集时间、错误和延迟写入独立的追加式运行遥测存储，不反写 Base，也不参与 `publish_predicate`。后台信源管理页未来可以只读联接 Base 配置与运行遥测，以满足 Spec 的最近采集状态查看要求；运行凭证没有修改 Base 配置的权限。

## 6. 手机候选最短录入流程（待真机验证）

### 6.1 目标流程

```text
X 帖子 / 账号页
  → 复制当前帖子或账号页分享链接
  → 打开已收藏的飞书表单
  → 粘贴 raw_url
  → 可选填写 capture_note
  → 提交
```

**[产品建议]** 手机表单只展示：

- `raw_url`：必填；
- `capture_note`：可选。

其余字段由系统规范化或在桌面复核视图维护。规范化器接受 `x.com/<handle>` 与 `x.com/<handle>/status/<id>`，从帖子 URL 提取 handle，并生成账号主页 canonical URL；无法识别的短链或异常格式保留原文并进入错误状态。表单不得要求用户在手机上选择实体类别、手写 canonical URL、填写证据或理解内部状态机。

### 6.2 重复与无效提交

- **[产品建议]** 提交先生成候选记录，再由规范化流程去掉跟踪参数并计算 canonical URL。
- **[产品建议]** 只有 `platform_account_id` 一致时才自动关联现有 `source_id`。仅 canonical URL 命中且缺少稳定账号 ID 时进入 `needs_review`，防止 handle 被新主体复用后误合并。
- **[用户已确认｜2026-07-31]** 规范化有效且查重确认为新信源后，不等待身份或 F1 相关性核验；已有合法授权且能力可用的适配器通过检查后立即入采集队列。
- **[产品建议]** 查重命中既有稳定账号 ID 时追加 `capture_event` 并关联既有信源，不创建第二个业务信源，也不擅自改变既有信源的人工停用状态。

## 7. 已确认的新增生效门禁

### 7.1 确认记录

**[用户已确认｜2026-07-31]** 手机提交新信源后，完成 URL 规范化与信源查重即进入适配器检查；适配器已有合法授权且能力可用时立即开始采集。账号身份或 F1 相关性未核验不阻断采集。

**[产品建议]** 上述决定映射为：`identity_status=unknown`、`relevance_status=unknown` 或 `verification_status=pending` 均不阻断采集。

该确认只决定信源何时开始采集。A→D 路线已由 S4 accepted；真实 Base 创建、Base 业务真值切换、A `base_direct` 切换和 D `base_snapshot` 切换仍未授权，具体资源状态与实现能力也仍待验证。

### 7.2 采集入队条件

新业务信源同时满足以下条件时，受控门禁立即创建一次激活操作：

1. `normalization_status=valid` 且 `canonical_url_valid=true`；
2. `dedup_status=unique`；
3. `adapter_status=ready`、`adapter_authorization_status=valid` 且 `monitorability=monitorable`；
4. `source_stop_status=clear`，没有人工停用、合规停用、授权停用或平台停止锁。

**[产品建议]** 配置存储的同一事务只完成三件事：写入 `collection_onboarding_status=activation_pending`、保持 `enabled=false`、追加具有唯一 `onboarding_operation_id` 的 transactional outbox 事件。dispatcher 使用该不可变操作 ID 幂等投递；`onboarding_attempt` 只做遥测，重试复用同一操作 ID。队列确认接收后，受控状态迁移才写 `collection_onboarding_status=queued` 和 `enabled=true`。若消费者早于状态确认拿到任务，只能无副作用重试，不得调用平台。

入队不代表首次采集成功，也不代表来源身份已核验。所有任务同时携带 `source_config_epoch` 与 `source_safety_epoch`；每次平台调用和结果提交前必须读取当前门禁，旧 epoch 或停止状态任务转为 blocked/cancelled，不能继续请求平台或写入当前结果。

### 7.3 阻断与失败状态

| 条件 | 写入字段与值 | `enabled` | 行为 / 重入 |
|---|---|---:|---|
| URL 无法规范化 | `normalization_status=invalid`；`collection_onboarding_status=normalization_failed` | false | 保留原始输入和原因；修正输入后新建捕获操作 |
| 仅 URL 命中且主体归属不明 | `dedup_status=needs_review`；`collection_onboarding_status=dedup_needs_review` | false | 不自动合并；人工确认主体后从查重步骤重入 |
| 稳定账号 ID 命中既有信源 | `dedup_status=linked_existing`；`collection_onboarding_status=linked_existing` | 沿用既有值 | 关联既有记录，当前操作终止；不创建新信源、不覆盖人工停用 |
| 适配器缺失 | `adapter_status=missing`；`collection_onboarding_status=blocked_adapter_missing` | false | 记录并告警；适配器获准上线后从适配器检查重入 |
| 授权无效或失效 | `adapter_authorization_status=invalid/expired`；`source_stop_status=authorization`；`collection_onboarding_status=blocked_authorization` | false | 递增 `source_safety_epoch`，停止调用并告警；重新授权验证后重入 |
| 平台受限或能力不可用 | `adapter_status=unavailable`；`source_stop_status=platform`；`collection_onboarding_status=blocked_platform` | false | 递增 `source_safety_epoch`，记录证据并告警；能力恢复后重入 |
| 入队失败 | `collection_onboarding_status=queue_failed` | false | 保留同一 `onboarding_operation_id` 幂等重试 |
| 首次采集执行失败 | `last_collection_status=failed`；`collection_onboarding_status=collection_failed` | true | 记录失败与次数并告警；若授权/平台已失效则先转对应 blocked 状态，否则幂等重试 |

`collection_onboarding_status` 的正常迁移为 `validating → activation_pending → queued → collecting → active`。`normalization_failed` 与 `linked_existing` 是当前捕获操作的终态；`dedup_needs_review`、三个 `blocked_*`、`queue_failed` 与 `collection_failed` 只能按上表恢复条件重入。除 `queued/collecting/active/collection_failed` 外，新信源必须保持 `enabled=false`。

### 7.4 公开审核门禁

**[用户已确认｜2026-07-31]** 所有拟公开内容继续经过人工审核；未经人工通过不得公开。

**[产品建议]** 所有采集到且拟公开的内容先进入 `review_status=pending`。每次内容编辑生成不可变 `content_revision` 与 `content_hash` 并把审核状态重置为 pending；审核事件记录 `reviewer/approved_at/approved_content_hash`。唯一服务端公开门禁要求当前待发布 hash 与人工批准 hash 完全一致。公开任务以 `content_id + content_revision` 幂等；`pending/rejected/failed`、hash 不一致或 `publish_failed` 均不得公开，也不能复用旧版本批准。采集入队、采集成功、中文整理完成或来源后来通过身份核验，都不能替代人工批准。

## 8. 最小字段合同

### 8.1 手机捕获字段

| 字段 | 必填 | 写入方 | 规则 |
|---|---:|---|---|
| `raw_url` | 是 | 用户 | 原样保留手机粘贴内容 |
| `capture_note` | 否 | 用户 | 只写为何想加入；不承载身份结论 |

每次提交生成一条追加式 `capture_event`，最小字段为：

| 字段 | 规则 |
|---|---|
| `capture_id` | 每次提交的稳定事件 ID，同时作为幂等键 |
| `raw_url` / `capture_note` | 保留当次用户输入 |
| `captured_at` | 平台生成时间 |
| `normalization_status` | `pending / valid / invalid / needs_review` |
| `normalization_error` | 失败原因；成功时为空 |
| `dedup_status` | `pending / unique / linked_existing / needs_review` |
| `dedup_match_source_id` | 命中既有稳定账号时填写；否则为空 |
| `source_id` | 可靠关联后填写；未关联时为空 |

### 8.2 业务真值字段

| 字段组 | 字段 | 规则 |
|---|---|---|
| 稳定身份 | `source_id` | 项目内稳定主键，创建后不因 handle 改名而变化 |
| 平台定位 | `platform`、`platform_account_id`、`handle`、`display_name` | `platform_account_id` 只在可靠取得后填写；handle 不作为长期身份事实 |
| URL | `raw_url`、`canonical_url`、`canonical_url_valid`、`normalizer_version` | raw 保留输入；canonical 去跟踪参数；有效性和规范化规则必须版本化 |
| 接入查重 | `dedup_status`、`dedup_match_source_id` | 当前接入判定同步到业务记录；每次尝试的原始结果仍保留在对应 `capture_event` |
| 临时分类 | `entity_type`、`content_focus`、`priority` | 当前值均为 provisional；priority 只安排复核顺序 |
| 后续验证 | `verification_status` | proposed 值：`pending / confirmed / rejected`；用户已确认它不作为新信源采集入队前置条件，仍用于后续身份与证据维护 |
| 身份证据 | `identity_status`、`identity_evidence_url`、`evidence_checked_at`、`verification_note` | `verified` 必须有第一方或权威证据；无证据保持 unknown |
| F1 相关性 | `relevance_status` | proposed 值：`unknown / qualified / rejected`；需要稳定观察窗口和抽样依据 |
| 可监控性 | `monitorability` | `monitorable / restricted / unavailable / unknown`；页面能打开不等于可持续监控 |
| 采集准备 | `adapter_status`、`adapter_authorization_status`、`authorization_checked_at/expires_at` | `adapter_status=unchecked/ready/missing/unavailable`；授权为 `unknown/valid/invalid/expired`，有效期必须覆盖实际调用时刻 |
| 激活操作 | `collection_onboarding_status`、`onboarding_operation_id` | 状态枚举及重入规则见第 7.3 节；操作 ID 创建后不可变，重试不更换 |
| 生命周期与停止锁 | `lifecycle_status`、`enabled`、`manual_disable_at`、`source_stop_status`、`source_safety_epoch` | 停止状态 `clear/manual/compliance/authorization/platform`；人工或安全停用优先，恢复必须显式通过对应受控流程 |
| 运行状态（派生读模型） | `last_collection_status`、`last_collection_at` | 由独立追加式运行遥测生成，不属于 Base 配置真值、不参与 predicate、不反写 Base |
| 审计 | `created_at/by`、`updated_at/by`、`change_reason` | 批量改动、拒绝、停用、恢复和改名必须写原因 |
| 迁移 | `migration_batch_id` | 59 条首次迁移统一标记，便于回滚与对账 |

### 8.3 默认值、写入方与状态迁移

手机提交后统一初始化：

```text
normalization_status = pending
dedup_status = pending
verification_status = pending
identity_status = unknown
relevance_status = unknown
monitorability = unknown
adapter_status = unchecked
adapter_authorization_status = unknown
collection_onboarding_status = validating
source_stop_status = clear
source_safety_epoch = 1
lifecycle_status = proposed

```

- 表单只写 `capture_event` 的用户输入字段；
- 规范化器只写 URL、`canonical_url_valid`、`normalization_status/error` 和 `normalizer_version`；查重器只写 `dedup_status/dedup_match_source_id`；
- 身份、相关性、生命周期、证据和人工启停只由 Base 中受控维护流程修改；
- 适配器检查只写能力、授权和可监控性结果；`monitorability=monitorable` 由同一次自动检查得出，表示当前适配器能在合法授权与平台控制内持续采集，不需要人工核验账号身份或 F1 相关性；
- 第 7.2 节条件全部满足时，受控门禁按 transactional outbox 合同立即启动激活，不读取身份或相关性状态作为前置条件；
- 用户可随时手工停用；停用时原子写 `manual_disable_at`、`source_stop_status=manual`、`enabled=false` 并递增 `source_safety_epoch`。自动门禁不得重新启用，恢复必须由人工显式操作；
- 同步器和 Collector 对以上配置字段只有读取权限；
- 每次状态迁移同时追加 `source_change_event`，并校验当前 `publish_predicate_id/version/digest`。

### 8.4 追加式历史实体

Base 业务真值至少包含以下关联实体或等价的不可变记录；它们和当前值一起进入完整备份：

| 实体 | 最小内容 |
|---|---|
| `capture_event` | 第 8.1 节字段；记录每次手机捕获和规范化结果 |
| `source_change_event` | `event_id/source_id/actor/changed_at/reason/before_hash/after_hash/evidence_url` |
| `source_alias` | `source_id/platform/old_handle_or_url/new_handle_or_url/valid_from/valid_to/evidence_url` |
| `source_tombstone` | `source_id/deleted_at/by/reason/evidence_url/previous_record_hash` |

Base 的有限历史功能不能替代这些长期业务事实。

### 8.5 采集集合发布谓词

```text
canonical_url_valid = true
AND dedup_status = unique
AND adapter_status = ready
AND adapter_authorization_status = valid
AND authorization_checked_at WITHIN adapter_policy.max_auth_age
AND (authorization_expires_at IS NULL OR authorization_expires_at > now)
AND monitorability = monitorable
AND enabled = true
AND manual_disable_at IS NULL
AND source_stop_status = clear
AND verification_status != rejected
AND relevance_status != rejected
AND lifecycle_status IN (proposed, active)
```

`identity_status=unknown`、`relevance_status=unknown` 与 `verification_status=pending` 不阻断该谓词，并必须继续显示在内部记录和内容审核证据中，不得被 UI 或同步器伪装为已确认官方来源。后续身份或相关性复核为拒绝时，必须在同一事务写 rejected、`enabled=false`、停止原因，递增 `source_safety_epoch` 并追加移除/取消 outbox 事件；谓词显式排除 rejected，防止部分提交或乱序回放重新启用。`lifecycle_status=active` 仍只用于完成身份、相关性和监控验证的记录。

该谓词只决定信源是否发布给 Collector，不决定内容是否公开。`publish_predicate` 只在一个版本化位置定义，A 的 Base 查询、D 的快照生成、故障恢复和迁移切换都引用同一版本，禁止各组件自行复制条件。

## 9. 维护、删减与溯源原则

### 9.1 新增与查重

1. 手机只捕获原始 URL；系统生成 canonical URL，并追加 `capture_event`。
2. 优先以平台稳定账号 ID 识别主体；仅 URL 命中且缺稳定 ID时只能标记 `needs_review`，不能自动合并。
3. 同一稳定账号 ID 的重复提交追加捕获事件，不创建第二个业务信源。
4. 新增来源的身份、相关性、可监控性和启用是四个不同判断，不用一个模糊“已审核”字段代替。

### 9.2 改名与分类变化

1. `source_id` 永不随 handle 改名；通过 `source_alias` 保存旧 handle、旧 URL、有效期和迁移证据。
2. 分类可以修正，但必须保留前后值、操作者、时间和原因。
3. 组织体系下的多个不同账号默认独立维护；只有获得平台账号 ID 和业务合并依据后才提议合并。

### 9.3 停用、拒绝与删除

1. 优先使用 `enabled=false`、`lifecycle_status=paused/retired` 或 `verification_status=rejected`，并保存理由。
2. 长期停更、身份冲突、主体转换、内容漂移、授权受限或重复来源进入复核，不直接硬删除。
3. 硬删除只用于确认的误录、重复或必须删除的合规场景；执行前追加 `source_tombstone`，保存原因和必要证据，并确认备份可恢复。
4. D 的发布快照中移除记录不等于删除 Base 业务事实。

### 9.4 溯源与审计

1. 身份判断必须指向第一方或权威证据 URL，并记录核验时间。
2. Base 历史、Git 快照和数据库时间戳只能证明“记录发生过变化”，不能证明账号身份真实。
3. Base 单条记录历史公开说明有 180 天保留边界；长期判断必须进入业务字段和独立备份。
4. D 的 Git/本地快照记录采集集合如何变化，不替代 Base 中的候选、拒绝、停用和完整证据。
5. 真实 token、应用密钥和权限凭证只保存在受控密钥环境，不进入 Base 业务字段、快照、Git 或日志。
