# ADR-SOURCE-001：信源库先 A、后 D 演进路线（accepted）

> 本 ADR 只接受“先 A、稳定后进入 D”的窄范围系统路线。它不把关联的整份 proposed 决策包升级为 accepted，也不授权创建真实飞书资源、导入数据、切换业务真值或切换采集器。

## 1. 上下文与证据

- **用户确认凭据：** [`TASK-20260801-24D860`](../../collaboration/tasks/TASK-20260801-24D860.json) 记录用户于 2026-08-01 明确接受上一轮提出的“先 A、后 D”路线。
- **方案研究：** [《飞书多维表格与本地信源库维护方案比较》](../../collaboration/部门/研究部/报告/2026-07-31-飞书多维表格与本地信源库维护方案比较.md) 定义 A 为飞书 Base 单一业务真值并由采集器在线直读，D 为同一 Base 真值向本地 last-known-good 只读快照单向发布。
- **详细候选合同：** [《F1+1 信源库维护决策包》](./2026-07-31-F1+1-信源库维护决策包-proposed.md) 仍为 `proposed`；其中字段、阈值、迁移细节、故障参数及其他建议不因本 ADR 自动 accepted。
- **项目准绳：** [`docs/spec.md`](../../spec.md) 仍为 Spec v0 草案。

2026-08-01，统筹部只读运行 `lark-cli auth status --json --verify`：用户身份为 verified、token valid，已授予的 scopes 包含 Base create/read/update 等能力。该检查没有访问或创建任何 Base，因此只证明当前身份、token 与租户级 scope 状态；具体 Base 是否存在、资源级权限、表/表单状态和 API 实际读取仍未验证。项目没有获准创建真实飞书资源或初始化 `app/`。

## 2. 已接受决定

信源库按以下顺序演进：

1. **先进入 A：** 建立飞书 Base 作为唯一业务真值；只有独立门禁通过后，采集器才从当前 provider 切换为在线直读 Base 的 `base_direct`。
2. **A 稳定后准备 D：** 保持 Base 为唯一业务真值，新增只读同步器，严格按 `Base → 本地 last-known-good 快照` 单向生成影子快照。
3. **验证后进入 D：** 只有 D 的实现、故障与恢复验证通过且用户另行确认切换，采集器才从 `base_direct` 切换为读取 `base_snapshot`。

这项接受决定排除 B、C 作为当前信源库主路线。它不接受 proposed 包中的所有字段设计、具体阈值、工具选型或迁移操作。

## 3. A 阶段边界

### 3.1 A 的目标状态

- 飞书 Base 是唯一可修改信源存在、启停、验证、证据与优先级的业务真值。
- 采集器的活动读取提供者为 `base_direct`，只读取经过完整校验并满足生效谓词的 Base 配置。
- legacy 清单在 Base 业务真值切换后冻结为只读迁移证据，不能继续维护、合并回 Base 或恢复为第二业务真值。

### 3.2 A 之前必须分别通过的门禁

以下动作互相独立，前一项完成不授权后一项：

1. **真实资源门禁：** 用户另行授权创建或使用真实 Base、表单、应用与账号权限。
2. **Base 业务真值切换门禁：** 完成影子导入、59/59 对账、schema/唯一性/状态校验、备份与可恢复性验证后，由用户明确确认把业务真值从 legacy 切到 Base。
3. **A 采集器切换门禁：** `base_direct` 完成完整读取、权限失败、缺页、配置变化、在途任务失效与安全停止测试后，由用户明确确认切换 active provider。

本 ADR 自身没有通过以上任一执行门禁。

Base 业务真值切换和 A provider 切换可以在两项门禁都已分别批准后原子提交，但一次提交不能代替两次授权。若 Base 已先成为业务真值而 A provider 门禁尚未通过，legacy 立即冻结，Collector 保持停止；不得继续从 legacy 采集。

## 4. D 阶段进入条件

D 只有同时满足以下条件才能提出切换：

1. A 已实际运行，并达到另行定义且经验证的稳定窗口；本 ADR 不预设窗口时长或阈值。
2. Base 继续是唯一业务真值，真实 API 权限、凭证轮换和完整读取能力有效。
3. 只读同步器已验证全量分页、schema、唯一性、生效谓词、校验和、原子替换、版本 manifest、`snapshot_age`、last-known-good 保留和全量对账。
4. 已完成 Base/API 不可用、授权失效、缺页、空响应、破损快照、删除异常、旧版本在途任务和恢复演练；失败不得覆盖最后正确快照。
5. 已确定并验证快照过期、停止、告警、备份与恢复阈值。
6. 开发可行性复核和独立测试通过，用户再明确确认把 active provider 从 `base_direct` 切到 `base_snapshot`。

任何条件未满足时都停留在 A；不能以“目标路线已接受”代替 D 切换门禁。

## 5. 跨阶段强制不变量

### 5.1 单一真值与同步

1. A、D 两阶段的唯一业务真值始终是 Base。
2. D 的同步方向只能是 `Base → 本地只读快照`；本地文件、Collector、运行遥测和安全 overlay 均不得反写、合并或裁决 Base 业务状态。
3. 本地快照只是发布给 Collector 的可重建读模型，不保存完整候选、拒绝、停用和业务审计事实。
4. 任一时刻最多只有一个 `active_source_config_provider`；Collector 运行时必须恰有一个，门禁间隙允许停止。provider 切换必须递增 `source_config_epoch`，旧 epoch 任务不得更新当前结果。

### 5.2 故障行为

1. API 空响应、缺页、读取中断、schema 错误或权限失败不得解释为业务集合已清空。
2. A 的在线读取失败时，不得按残缺页面继续采集，也不得把已冻结 legacy 清单恢复为当前真值；没有与当前 Base 状态一致的获准读取结果时停止并告警。
3. D 的同步失败时保留最后通过完整校验的快照，标记新鲜度并告警；不得发布部分、空或未校验快照。
4. 任何故障处理都不能绕过平台授权、人工停用、合规停止或公开内容人工审核门禁。

### 5.3 回滚

1. **D → A：** 只回切读取 provider；Base 继续是业务真值。只有 `base_direct` 当前可用且已通过切换检查时才能回切，否则继续使用仍在安全期限内的获准快照或停止。
2. **A 切换失败：** Base 业务真值切换前可以撤销影子导入并继续使用 legacy；Base 已成为业务真值后，不能静默回到旧 legacy 名单，必须从 Base 恢复或停止，并另走用户门禁。
3. 回滚不得撤销 Base 中已经生效的停用、拒绝、删除或证据变化，也不得引入第二写入口。

## 6. 授权边界

### 6.1 本次已接受

- 信源库采用先 A、后 D 的演进顺序。
- A 阶段以 Base 为唯一业务真值，并以 `base_direct` 作为通过门禁后的采集器读取方式。
- D 阶段继续以 Base 为唯一业务真值，只增加 Base 到本地 last-known-good 快照的单向只读发布，并以 `base_snapshot` 作为通过门禁后的读取方式。
- Base 业务真值切换、A 采集器切换、D 快照切换是三个需要实现验证和用户确认的独立门禁。
- 单一真值、禁止反写、故障安全和回滚不恢复旧真值是跨阶段不变量。

### 6.2 本次未授权 / 未接受

- 登录、授权、创建、修改、导入、分享或删除任何真实飞书 Base、表单、应用、权限或记录。
- 把现有 59 条候选导入真实 Base，或把其临时分类当成身份与启用结论。
- 执行 Base 业务真值切换、A `base_direct` 切换或 D `base_snapshot` 切换。
- 初始化 `app/`、实现同步器、部署任务、调用真实平台、采购额度或上线。
- 接受现有 proposed 决策包中的全部字段、阈值、成本、备份周期、稳定窗口、表单设计或迁移细节。
- 自动公开内容；“采集”与“公开”继续由人工审核门禁隔离。

## 7. 影响与未验证项

- **正向影响：** 先用较少组件验证 Base 真值与手机维护，再用只读快照增加运行韧性；A 失败时不会被迫同时排查同步器，D 也不新增业务写入口。
- **代价：** A 阶段依赖 Base API 在线可用；D 增加同步、凭证、告警、全量对账、备份和恢复责任。
- **未验证：** 真实飞书权限与资源、A 在线读取实现、稳定窗口、D 同步与快照、故障恢复阈值、运行成本和三次切换均未验证或授权。

## 8. 变更与替代规则

本 ADR 为 `accepted`，后续不得原地修改其核心路线、真值、不变量或授权边界。若要改为跳过 A、取消 D、引入双向同步、更换业务真值或合并切换门禁，必须新建 draft/proposed ADR，经用户确认后将本 ADR 标记为 `superseded`。
